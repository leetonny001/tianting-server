## 1. 背景与目标

### 1.1 背景

PRD-core 定义了一期核心业务和 H5 的页面清单（第 5 节），PRD-social 定义了好友、拉黑、通讯录和群管理的数据与规则，但两者都不写信息架构、布局、视觉和交互细节。H5（tianting-web）、PC（tianting-desktop，Tauri 壳加载 tianting-web）、Android（tianting-android，Kotlin + Compose）、iOS（tianting-ios，Swift + SwiftUI）要按同一份规范实现，需要一份各端共用的交互规范。

### 1.2 目标

1. 定义各端统一的信息架构（消息 / 通讯录 / 我）和页面交互，**参考微信的信息架构和交互习惯**，降低用户学习成本。
2. 定义天听自有的视觉规范（设计 token、浅色 / 深色、气泡、头像），各端共用，对比度可自动验证。
3. 在 PRD-core、PRD-social 之上细化界面，**不改变它们的业务规则**；本 PRD 对冻结的 PRD-core 第 5、7 节等的改动全部列在第 14 节，作为 v1.3 变更；需要服务端或 SDK 新增的能力列为缺口（第 7 节）。

### 1.3 里程碑与实施顺序

| 里程碑 | 端 / 仓库 | 本 PRD 的范围 |
|---|---|---|
| **M3** | H5（tianting-web），服务端 + sdk-ts | 窄屏 + 浅色；桌面浏览器居中显示手机宽度；基础聊天、通讯录与社交（S-7 ②）；全部 `【M3】` AC |
| **M4** | PC（tianting-desktop）+ H5 | 宽屏三栏、深色模式、表情、草稿、删除失败消息、Tauri 专项；客户端群管理（S-7 ②）；全部 `【M4】` AC |
| **第二批** | 服务端 + 三套 SDK + H5 / PC | PRD-admin 第二批带来的客户端提示：禁言、消息被删除、封禁、系统通知（X-6 ②）；全部 `【第二批】` AC。与 PRD-core v1.3 第二批变更、协议、SDK 一起交付 |
| M5 / M6 | Android（Kotlin）/ iOS（Swift） | 按本 PRD 的交互和视觉实现 M3 + M4 的全部页面（PRD-social 10.4 节：原生 SDK 首版就含社交）；验收用 3.6 节的对应写法 |

> 分享会（M8）的最低要求是 M3（PLAN 第 8 节）。第二批与 M4 的先后由 DECISIONS 第 4 节的开发顺序决定，本 PRD 不规定。

### 1.4 品牌与知识产权约束（强制）

**参考微信的信息架构和交互模式，但不复制微信的商标、图标、品牌色和视觉资产。**

| # | 规则 | 验证 |
|---|---|---|

### 2.1 通用约定

| 项 | 约定 |
|---|---|
| AC 格式 | `- AC-UI-{功能点两位数}-{序号}{验证层}{里程碑}{端}：…`，与 `tools/trace.py` 的 `AC_RE = AC-[A-Z]+-\d+-\d+`、行首匹配 `^- (AC-…)` 兼容。**验证层标记紧跟编号**（`rest[:8]` 能识别）：【前端】【后端】，不标为端到端；人工验证写作 **（手工）**（与 `trace.py` 的判定一致，v0.1 的【手工】作废）。非功能 AC 编号为 `AC-UI-90-n`（v0.1 的 `AC-UI-NF-n` 不符合正则，作废） |
| 里程碑标记 | 【M3】【M4】【第二批】，每条 AC 必有一个 |
| 端标记 | **【Web】** = 只在 Web（H5 / Tauri）上有意义的写法（DOM、`document.title`、`sessionStorage`、计算字号、`scrollWidth`、Playwright 专用手段）；原生端的等价要求见 3.6 节对应表，不另编 AC 号。**未标【Web】的 AC 各端都要满足**：Web 用 Playwright / 组件测试，原生端用各自的 UI 测试（Compose UI Test、XCUITest），按同样的输入和预期执行 |
| 测试视口 | **窄屏** = 375×812（M3 默认，未注明视口的 M3 AC 都在此视口验证）；**最小** = 320×568；**桌面** = 1280×800（M3：居中手机宽度）；**宽屏** = 1280×800 且 `(hover: hover) and (pointer: fine)`（M4，【宽屏】AC 只在此验证）。原生端用各自的默认测试设备（3.5 节） |
| 测试用户 | alice、bob、carol、dave、eve 是已导入用户，昵称与 userId 相同，除非 AC 另有说明；`zhangsan` 的昵称为"张三"、`lisi` 的昵称为"李四"（通过演示登录的昵称或管理接口导入设定）；`nobody` 是不存在的 userId。"开放模式 / 好友制"同 PRD-social 第 6 节 |
| 数据来源 | 界面只通过 SDK（`IMClient`）取数据和发命令，不直接操作 WebSocket；SDK 行为以 [SDK 设计说明](../sdk/README.md) 和 PRD-social 第 10 节为准 |
| 显示名 | **用户显示名** = 我给他设的备注（我这一侧好友边上有备注时，只在本机显示，PRD-social 5.5 节）> 昵称 > `userId`。昵称来源：单聊会话名用 `conv.name`（服务端已带对方昵称，C-19）；好友、申请、黑名单项用同步数据里的 `profile`；其余（群消息发送者、"我"、资料卡）用 `users` 缓存（PRD-social F-SOC-10）。**群显示名** = `conv.name`。下文"显示名"均指此规则 |
| 可测试性 | Web：关键元素提供稳定的 `data-testid`；消息元素暴露 `data-status`（`queued` / `sending` / `sent` / `failed`）。原生：Compose 用 `Modifier.testTag`，SwiftUI 用 `accessibilityIdentifier`，取值与 `data-testid` 相同 |
| 时间格式 | 沿用 F-MSG-06 规则 4（聊天页与会话列表两套格式），一律以服务端时间为准 |
| 负向断言 | "不出现 / 收不到"指操作完成后 **2 秒内**不出现（与 PRD-social 5.6 节一致） |

### 3.5 原生端规范（R-UI-16）

1. **单位**：本 PRD 中的尺寸单位 px 在 Compose 中按 **dp** 1:1、在 SwiftUI 中按 **pt** 1:1 换算；字号 px → Android `sp`、iOS 按 Dynamic Type 的基准字号（`font.body` 16 ≈ `.body` 17pt，允许取平台最接近的文本样式）。
2. **允许平台惯例覆盖的 token**：顶栏高度（Android 64dp / iOS 44pt）、标签栏高度（Android `NavigationBar` 80dp / iOS `TabView` 49pt）、确认框和底部菜单的系统样式（`AlertDialog` / `.alert`、`ModalBottomSheet` / `.confirmationDialog`）、系统字体。**颜色、头像、气泡、间距、文案不允许覆盖**。
3. **字体缩放**：支持系统字体放大到 200%（Android `fontScale = 2.0`、iOS Dynamic Type 到 `accessibility3`）；放大后文本可以换行，但"发送""同意""确定"等主要按钮不能被截断或遮挡，消息内容不能被截断。
4. **测试标识**：`testTag` / `accessibilityIdentifier` 与 Web 的 `data-testid` 同名。
5. **默认测试设备**：Android Pixel 7 模拟器（API 34）；iOS iPhone 15 模拟器（iOS 17+）；最小宽度验证 Android 320dp 宽的自定义 AVD、iOS iPhone SE（第 3 代，375pt）。

1. 触发：窄屏长按气泡 500ms；宽屏右键气泡。按下后手指移动超过 10px 取消长按（避免滚动误触，R-UI-26）；用 Pointer Events 实现；窄屏气泡设置 `-webkit-touch-callout: none` 和 `user-select: none`。
2. 菜单出现在气泡上方；气泡上方到消息列表顶边的空间小于菜单高度时出现在下方。点菜单外关闭。
3. 菜单项（按消息状态）：
   | 菜单项 | 出现条件 | 里程碑 | 行为 |

   | 复制 | 所有文本消息 | M3 | 把消息全文写入剪贴板，提示"已复制"；失败提示"复制失败，请长按文字手动复制" |

### F-UI-10 输入区（M3，细化 F-MSG-01 / F-MSG-06）

**规则**

### F-UI-22 主题：浅色（M3）/ 深色（M4）

**规则**
1. 所有颜色只通过 6.1 节的 token 使用，组件中不出现硬编码色值（lint 检查）；内联 SVG 图标一律使用 `currentColor`，lint 规则豁免 token 定义文件和第三方许可证文件（R-UI-41）。
2. **M3 只做浅色**：深色 token 已定义并通过对比度检查（6.2 节），但 M3 不读取系统深色设置、不提供切换，任何系统主题下都显示浅色。
3. **M4**：默认"跟随系统"（`prefers-color-scheme`）；"设置 → 外观"可手动指定，偏好存 `localStorage` 的 `ui.theme`（`system` / `light` / `dark`，非敏感数据，不受 D4 限制）。系统主题变化时（跟随系统模式下）实时切换，不需要刷新。

### F-UI-33 未知会话、被移出 / 退出 / 解散的会话（M3；`reason = left` 为 M4）

**背景**（R-UI-03）：sdk-ts 收到 `convRemoved` 时直接删除会话，C-37 规定 `convs` 不再返回被移出的群；直接打开一个不在会话列表里的 `convId` 时，界面行为过去没有定义。

**规则**
1. 路由中的 `convId` 用 SDK 的严格解析函数 `parseConvIdStrict(convId, self)`（G-UI-03）解析；**不得用现有的 `parseConvId` 判断路由**（它不校验格式、不判断参与者）：
   | 情况 | 处理 |
   |---|---|
   | 格式非法（抛出 `invalid`） | 跳转到 `/chats`，轻提示"会话不存在" |
   | 单聊且当前用户不是参与者（抛出 `notParticipant`） | 同上（本地判断，不发请求） |
   | 单聊、参与者含我、不在会话列表 | 临时会话（F-CONV-03）：标题用对方显示名（资料缓存，没有时 `userId`），可以发送；同时 `loadHistory` 按 G-UI-26 请求最新一页，有历史消息时显示并补进会话列表；返回 4032（正常情况下已被本地拦截）时按"格式非法"处理 |
   | 群聊、在会话列表 | 正常 |
   | 群聊、本次登录期间被移出（SDK 会话快照 `removed: true`，G-UI-21） | 标题保留快照中的群名（不带成员数）；列表底部提示 + 输入区禁用条（规则 2、规则 4：`dissolved` 显示"群聊已解散"） |
   | 群聊、不在会话列表、没有快照 | 先 `loadHistory`：SDK 向服务端发 `sync` 请求最新一页（G-UI-26，不在本地提前返回），**`sync` 返回前显示加载状态（F-UI-20），不显示输入框、也不显示任何"不在该群"类提示**；成功则正常显示（SDK 把会话补进列表）；返回 4033 → 标题"群聊"，显示规则 2 的"你已不在该群"；返回 4043 → 标题"群聊"，列表居中显示"群聊不存在或已解散"，输入区禁用条"群聊不存在或已解散" |
2. 被移出时的提示（M3，`reason` 缺失、为 `removed` 或为不认识的值；`dissolved` 按规则 4 在 M3 就显示"群聊已解散"）：列表底部插入居中提示"你已不在该群"（与 AC-GRP-03-3 一致）；输入区替换为禁用条"你已不在该群，无法发送消息"（AC-GRP-02-5）；顶栏"更多"仍可进入聊天信息页（F-UI-12 规则 4）。重连比对生成的快照没有 `reason`（规则 3），所以离线期间被解散的群在本次登录内也显示"你已不在该群"；刷新后再打开时 `sync` 返回 4043，按规则 1 显示"群聊不存在或已解散"。
3. **SDK 会话快照**（G-UI-21，DECISIONS 第 3 节"SDK 收到被移出群时保留会话的展示信息"）：收到 `convRemoved` 时，SDK 从会话列表移除该会话（会话列表行为不变），但保留 `{convId, name, type, removed: true, reason?}` 快照，**保留到本次登录结束**（退出登录、被踢、刷新页面后清除）；已加载的消息保留在内存中可以继续查看。
   - **重连或刷新会话列表时也生成快照**：`convs` 应答会整体覆盖会话列表（重连后的首次拉取、`refreshConversations`、SDK 内部补拉），服务端不为离线期间的移出补发 `convRemoved`。因此 SDK 用新列表与旧列表比对：原来在列表里、新列表里没有的**群会话**同样生成快照（`removed: true`，`reason` 缺失），并发出 `convRemoved` 事件，界面按规则 2 处理；单聊不处理；新列表带 `truncated: true`（C-03）时不做此推断（会话可能只是被挤出前 500 个）。
   - **重新被拉进群时清除快照**：收到同一群的 `convAdded` 时清除该群快照，会话按正常会话显示，停在该群聊天页时输入区恢复。
4. **按 `reason` 区分**（PRD-social V-11；批次按一致性复审 D-02）：

   | `dissolved`【M3】 | 群聊已解散 | 群聊已解散 |
   | `left`（本人在其他端退群）【M4】 | 你已退出该群聊 | 你已退出该群聊 |

   "群聊已解散"在 M3 随管理接口解散（PRD-admin F-ADM-24 第一批、PRD-social F-SOC-26 的 M3 部分：`DELETE /admin/groups/{id}`、群 ID 不复用、`convRemoved.reason`）交付，M4 起客户端解散（`groupDissolve`、最后一人退群自动解散）同样适用。M3 不会产生 `left`；M3 构建若收到 `left`，按"不认识的值"显示。
5. 都不显示成员数，都不能发送；已在本页的输入内容不保留。

### 9.5 非功能验收标准

- AC-UI-90-1【前端】【M3】【Web】：用户 `xss1` 的昵称为 `<img src=x onerror=alert(1)>`，他发来的消息、他所在的群名同样设为该字符串、我给他的备注设为 `<b>x</b>`、他发来的好友申请附言也为该字符串：会话列表（名称和摘要）、聊天页（标题和发送者名）、通讯录、新的朋友、资料卡、`document.title` 中都原样显示文本；不弹窗；页面不发出对 `x` 的任何请求；DOM 中没有 `<img src="x">` 和 `<b>` 元素。
