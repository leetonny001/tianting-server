## 1. 背景与目标

### 1.1 背景

一期管理能力只有给业务服务端用的管理接口（`/admin/*`，静态密钥 `X-Admin-Key`），运营、客服没有界面可用。要替换 fx-sport / ab77 / android 中的腾讯云 IM，后台需要覆盖腾讯 IM 控制台和 REST API 的常用能力：查用户、踢下线、封禁、群管理、禁言、删消息、系统消息。

**约束**：`X-Admin-Key` 只能留在服务端（PRD-core 第 6 节、ADMIN.md），浏览器里绝不能出现。后台必须有自己的运营人员账号体系。后台操作的对象是真实用户的聊天数据，**一次越权或一个泄露的会话，影响的是全体用户**，所以安全要求高于 IM 客户端。

### 1.2 目标

1. 给运营 / 客服 / 审核一个桌面浏览器后台，替代"找开发调接口"。
2. 后台自身做到：独立账号 + 强制二次验证、按角色授权、所有操作可追溯、敏感数据默认不可见。
3. 后台服务可以独立于 IM 节点部署和扩容，不扩大 IM 对外端口的攻击面。

### 1.3 成功标准

| 指标 | 目标 | 度量方法 |
|---|---|---|
| 安全 | 浏览器侧（构建产物、HAR、Cookie、Storage）找不到管理密钥；第 4.1 节 AC 全部通过 | 自动化测试 + 上线前渗透测试 |
| 可追溯 | 100% 写操作、100% 消息内容查看都有审计记录 | 用例：每类操作执行后查审计 |
| 效率 | 客服"查用户 → 踢下线 / 禁言"全流程 ≤ 30 秒 | 手工走查 |
| 性能 | 列表 / 搜索 P95 ≤ 1 秒（100 万用户、10 万群） | 压测 |

## 2. 角色与权限

### 2.1 角色

| 角色 | 典型用户 | 职责 |
|---|---|---|
| 超级管理员 `super_admin` | 负责人（Frank）、技术负责人 | 后台账号与角色管理；拥有全部业务权限 |
| 运营 `operator` | 运营同学 | 用户导入、建群、群设置、系统推送 |
| 客服 `support` | 客服 | 查用户、查在线设备、强制下线、禁言 |
| 内容审核 `moderator` | 审核专员 | 查看消息内容、删除违规消息、封禁、禁言、敏感词 |
| 审计员 `auditor` | 安全 / 合规 | 只读：查看审计日志；不能做任何业务操作 |

一期为**固定角色**，一个账号只能有一个角色；自定义角色放 P1。

## 4. 功能需求

> 每个功能点：描述 → 规则 → 验收标准（AC）。【后端】指 BFF 或 im-server，【前端】指后台 H5；未标注的为端到端。

### 4.1 后台自身的登录与安全

#### F-ADM-01 后台账号登录（P0）

**描述**：运营人员用后台自己的账号登录，**密码 + TOTP 二次验证（强制）**。是否接公司 SSO 见 D-ADM-02。

**规则**
1. 账号名：小写字母、数字、`.`、`_`、`-`，3～32 位；一个账号对应一个真人，禁止共用。
2. 登录分两步：① 账号 + 密码；② 6 位 TOTP（RFC 6238，30 秒步长，允许前后各 1 个步长的时钟偏差）。第 ② 步通过后才发放会话。第 ① 步通过后得到的"半登录"状态只能调用 TOTP 校验接口，5 分钟内有效。
3. 同一个 TOTP 码在有效期内只能使用一次（防重放）。
4. 首次登录（账号由超管创建）：必须先修改初始密码，再扫码绑定 TOTP，才能进入后台。绑定时发放 10 个一次性恢复码，只显示一次。
5. 账号或密码错误、账号不存在、账号已停用，**统一提示"账号或密码错误"**，响应时间差 ≤ 100ms（防账号枚举）。
6. 第一个超管只能通过命令行创建（`admin-console bootstrap`），网页上没有"注册"。
7. 登录成功、失败、锁定、TOTP 失败都写审计（F-ADM-06）。

**验收标准**
- AC-ADM-01-1：账号、密码、TOTP 都正确时进入首页；浏览器收到会话 Cookie。
- AC-ADM-01-2【后端】：只通过密码步骤、未通过 TOTP 时，调用任一业务接口（如 `GET /console/api/users`）返回 HTTP 401。
- AC-ADM-01-3【后端】：不存在的账号、错误密码、已停用账号三种情况，响应体完全相同（同一错误码、同一 msg），三者平均响应时间相差 ≤ 100ms（各 20 次取均值）。
- AC-ADM-01-4【后端】：同一个 TOTP 码第二次提交返回失败。
- AC-ADM-01-5【后端】：TOTP 用前一个、后一个步长的码可以通过；用前两个步长的码失败。
- AC-ADM-01-6【后端】：半登录状态 5 分钟后（测试时钟）提交正确 TOTP，返回失败，需重新输入密码。
- AC-ADM-01-7【前端】：新建账号首次登录，依次强制进入"修改密码"→"绑定二次验证"页，未完成前访问任何后台地址都跳回该步骤。
- AC-ADM-01-8：用恢复码代替 TOTP 可以登录一次；同一个恢复码第二次使用失败。
- AC-ADM-01-9【后端】：登录成功、密码错误、TOTP 错误各执行一次后，审计里各有一条记录，包含账号、IP、结果；**审计里不出现密码或 TOTP 码明文**。

#### F-ADM-02 后台会话（P0）

**规则**
1. 会话存在**服务端共享存储**里（一期 BFF 数据库，集群化换 Redis），Cookie 里只放随机会话 ID（≥ 128 位熵）。BFF 进程本身无状态，多实例部署时任意实例都能识别会话。
2. Cookie：名称 `__Host-adm_sid`，`HttpOnly`、`Secure`、`SameSite=Strict`、`Path=/`，不设 `Domain`。前端 JS 读不到会话 ID，**会话凭证不放 localStorage / sessionStorage**。
3. 过期：空闲 30 分钟过期；绝对有效期 12 小时（到点必须重新登录）。
4. 登录成功时生成新的会话 ID（防会话固定）；退出登录、修改密码、被停用、角色被修改时，**服务端删除该账号的会话**（修改密码时保留当前会话，删除其他会话）。
5. CSRF：所有非 GET 请求必须同时满足 ① 请求头 `X-CSRF-Token` 与会话绑定的令牌一致；② `Origin` 头等于后台自身域名。GET 请求不得有副作用。
6. 同一账号最多 3 个并发会话，超出时最早的会话失效。
7. 生产环境只允许 HTTPS，开启 HSTS。

**验收标准**
- AC-ADM-02-1【后端】：登录响应的 `Set-Cookie` 包含 `HttpOnly`、`Secure`、`SameSite=Strict`、`Path=/`，名称以 `__Host-` 开头，没有 `Domain`。
- AC-ADM-02-2【前端】：登录后在页面执行 `document.cookie`、遍历 `localStorage` / `sessionStorage`，都找不到会话 ID。
- AC-ADM-02-3【后端】：最后一次请求后 29 分钟（测试时钟）请求成功；31 分钟后请求返回 401。
- AC-ADM-02-4【后端】：持续每 10 分钟请求一次，第 12 小时零 1 分钟时返回 401。
- AC-ADM-02-5【后端】：登录前先拿到的会话 ID，登录后不再有效（登录后 Cookie 值与登录前不同，用旧值请求返回 401）。
- AC-ADM-02-6【后端】：点击退出后，用退出前的 Cookie 重放请求返回 401。
- AC-ADM-02-7【后端】：不带 `X-CSRF-Token`，或令牌错误，或 `Origin` 为其他域名的 POST 请求返回 403，业务操作未执行，审计记录 `result=denied`。
- AC-ADM-02-8【后端】：两个 BFF 实例共用一个存储，在实例 A 登录后，请求发到实例 B 成功；在 B 退出后，A 也返回 401。
- AC-ADM-02-9【后端】：同一账号第 4 次登录后，第 1 次登录的会话返回 401。
- AC-ADM-02-10【前端】：任一请求返回 401 时跳转登录页，并提示"登录已过期，请重新登录"。

#### F-ADM-03 密码策略与登录失败锁定（P0）

**规则**
1. 密码 12～128 个字符；不能包含账号名；不能在常见弱密码表（Top 10000）里；不强制字符种类组合（按 NIST SP 800-63B）。
2. 存储：Argon2id 加盐哈希；任何日志、审计、接口响应都不出现密码或其哈希。
3. 不强制定期改密；新密码不能与最近 5 次相同。
4. 锁定：同一账号 15 分钟内连续失败 5 次（密码或 TOTP 都算），锁定 15 分钟；锁定期间即使密码正确也拒绝。超管可以手动解锁（写审计）。
5. 按 IP 限流：同一 IP 每分钟最多 20 次登录尝试，超出返回 429。
6. 失败计数、锁定状态存在共享存储里，多实例一致。
7. 账号被锁定时，站内提示超管（P1：邮件 / IM 通知）。

**验收标准**
- AC-ADM-03-1【后端】：设置密码 `abc12345678`（11 位）失败；`password1234`（在弱密码表中）失败；包含账号名的密码失败；12 位随机字符成功。
- AC-ADM-03-2【后端】：数据库里密码字段以 `$argon2id$` 开头；相同密码的两个账号哈希值不同。
- AC-ADM-03-3【后端】：连续 5 次输错密码后，第 6 次用正确密码 + 正确 TOTP 登录仍被拒绝，提示"账号已锁定，请 15 分钟后再试"；15 分钟后（测试时钟）可以正常登录。
- AC-ADM-03-4【后端】：失败 4 次后成功登录一次，计数清零，再失败 4 次不锁定。
- AC-ADM-03-5【后端】：同一 IP 1 分钟内第 21 次登录请求返回 HTTP 429。
- AC-ADM-03-6【后端】：在实例 A 失败 3 次、在实例 B 失败 2 次后，账号被锁定。
- AC-ADM-03-7【后端】：修改密码时使用最近 5 次用过的密码之一，返回失败。
- AC-ADM-03-8【后端】：故意在登录、改密请求里使用特征串密码 `Pw-CANARY-7f3a…`，执行后扫描 BFF 日志和审计表，找不到该特征串。

#### F-ADM-04 后台账号与角色管理（P0）

**规则**
1. 只有 `admin.manage` 可以：新建账号（账号名、显示名、角色、初始密码由系统随机生成并只显示一次）、修改角色、停用 / 启用、重置密码、重置二次验证、解锁。
2. 重置密码 / 重置二次验证后，该账号所有会话失效，下次登录按"首次登录"流程处理。
3. 账号不能删除，只能停用（保证审计里的操作人始终可查）。
4. 规则 2.2 第 4 条：不能改自己的角色、不能停用自己、不能停用最后一个启用的超管。

**验收标准**
- AC-ADM-04-1：超管新建客服账号，新账号首次登录后只能看到客服权限内的菜单。
- AC-ADM-04-2【后端】：运营账号调用新建账号接口返回 403 / 4030。
- AC-ADM-04-3【后端】：把在线的客服账号改为审计员后，该账号原有会话立即返回 401；重新登录后按审计员权限。
- AC-ADM-04-4【后端】：停用账号后，该账号会话立即失效，再登录提示"账号或密码错误"。
- AC-ADM-04-5【后端】：唯一的超管尝试停用自己或修改自己的角色，返回 4000，状态不变。
- AC-ADM-04-6【后端】：账号管理页没有删除操作；直接调用删除接口返回 404 或 405。

#### F-ADM-05 权限控制（RBAC，P0）

**规则**：见第 2.2 节矩阵。每个后台接口在代码里声明所需权限点，未声明的接口默认拒绝（白名单）。

**验收标准**
- AC-ADM-05-1【后端】：自动化测试遍历全部 `/console/api/*` 路由 × 5 个角色，实际结果与第 2.2 节矩阵逐格一致（有权限 ≠ 403，无权限 = 403）。
- AC-ADM-05-2【后端】：新增一个未声明权限点的路由，测试启动时失败（或该路由对所有角色返回 403）。
- AC-ADM-05-3【前端】：客服登录后，侧边栏不出现"系统通知""账号管理""审计日志"；直接输入这些页面的地址显示"无权限"页。
- AC-ADM-05-4【后端】：无权限的请求在审计中记为 `result=denied`，包含请求的动作和目标。

#### F-ADM-06 操作审计日志（P0）

**规则**
1. **记录范围**：所有写操作；所有消息正文查看（F-ADM-08）；登录 / 登出 / 失败 / 锁定；权限拒绝；审计日志本身的查询与导出。纯列表浏览（无正文）不记录。
2. **字段**：`id`（UUIDv7）、`ts`、操作人（账号 ID、账号名、角色）、来源 IP（经 `ADM_TRUSTED_PROXIES` 解析的真实客户端 IP）、User-Agent、`action`（枚举，如 `user.ban`）、目标（类型 + ID，如 `user:u1`、`conv:group:g1`）、参数摘要（脱敏）、理由、结果（`success` / `failure` / `denied` + 错误码）、`requestId`。
3. **不记录**：密码、TOTP、会话 ID、CSRF 令牌、管理密钥、**消息正文**、推送 `data` 全文（只记长度和哈希）。
4. **只能追加**：BFF 访问审计表的数据库账号只有 INSERT 和 SELECT 权限；每条记录包含上一条记录的哈希（哈希链），提供校验命令发现篡改或删除。P1：同步到外部只追加存储（对象存储 WORM / 日志平台）。
5. **先写审计再返回**：写操作的审计写入失败时，操作视为失败（返回 5000），不允许"操作成功但没留痕"。
6. **与 im-server 关联**：BFF 调用 im-server 时带 `X-Request-Id` 和操作人 ID（在签名范围内，见 G-ADM-03），im-server 自己的管理接口审计里也能看到是哪个后台账号发起的。
7. **查询**：按时间范围（必填，最长 31 天）、操作人、动作、目标、结果筛选；倒序游标分页；查询本身写一条审计。
8. **保留期**：在线保留至少 1 年（不低于《网络安全法》要求的 6 个月），之后归档（见 D-ADM-08）。

**验收标准**
- AC-ADM-06-1：客服对用户 u1 执行强制下线（理由"测试"），审计新增一条记录：操作人为该客服、action=`user.kick`、目标 `user:u1`、理由"测试"、结果 success、IP 为测试机 IP。
- AC-ADM-06-2【后端】：im-server 返回错误（如 4042 用户不存在）时，审计记录 result=failure、错误码 4042。
- AC-ADM-06-3【后端】：用 BFF 的数据库账号执行 `UPDATE` / `DELETE` 审计表，数据库报权限错误。
- AC-ADM-06-4【后端】：直接在库里删除中间一条审计（用高权限账号），运行校验命令，输出被破坏的记录位置并以非 0 退出。
- AC-ADM-06-5【后端】：让审计写入失败（测试注入），执行禁言，接口返回 5000，im-server 侧该用户未被禁言。
- AC-ADM-06-6【后端】：查看一条消息正文后，审计记录中找不到该消息正文（用特征串消息验证）。
- AC-ADM-06-7【后端】：同一操作在 BFF 审计和 im-server 审计中的 `requestId` 相同，im-server 记录中带有后台账号 ID。
- AC-ADM-06-8【前端】：审计员按"操作人 = 某客服、动作 = 强制下线、最近 7 天"筛选，只出现符合条件的记录；时间范围超过 31 天时无法提交。
- AC-ADM-06-9【后端】：审计员查询审计日志后，审计中新增一条 action=`audit.query` 的记录。
- AC-ADM-06-10【后端】：页面和接口上都没有修改、删除审计的入口；对审计接口发 `DELETE` / `PATCH` 返回 404 或 405。

#### F-ADM-07 敏感操作二次确认（P0）

**规则**
1. 所有写操作都弹确认框，写清对象和影响（例如"将强制 u1 的 3 个在线设备下线"）。
2. 以下**高危操作**额外要求**重新验证（输入当前 TOTP）**，验证通过后 5 分钟内同一会话的高危操作免再次输入：封禁、解散群、全员通知、删除消息、开启消息正文查看（F-ADM-08）、账号与角色管理、重置他人二次验证、审计导出（P1）。
3. 解散群、全员通知额外要求**手动输入确认文字**（群 ID / "全员发送"），防误点。
4. 封禁、禁言、强制下线、删除消息、解散群、消息正文查看必须填写理由。
5. 重新验证的要求在 BFF 校验，前端只负责弹框。

**验收标准**
- AC-ADM-07-1【后端】：会话中从未重新验证时，直接调用解散群接口返回 401 / 4017（需要重新验证），群未解散。
- AC-ADM-07-2：输入正确 TOTP 后解散群成功；4 分钟内再封禁一个用户不需要输入 TOTP；6 分钟后（测试时钟）再次封禁需要输入。
- AC-ADM-07-3【前端】：解散群弹窗中，输入的群 ID 与目标不一致时"确认"按钮不可点击。
- AC-ADM-07-4【后端】：封禁、禁言、强制下线、删除消息不带理由或理由少于 2 字时返回 4000，操作未执行。

#### F-ADM-08 数据脱敏与敏感查看留痕（P0）

**规则**
1. **消息正文默认不可见**：消息列表默认只显示元数据（时间、发送者、seq、类型、长度），正文显示为"••••"。
2. 查看正文需要 `msg.read`，并且每次进入一个会话的正文查看都要：填写理由（工单号 / 举报编号 / 说明）+ 重新验证（F-ADM-07）。授权以"会话"为单位、有效 15 分钟；超时或切换到另一个会话需要重新申请。
3. 每次授权写一条审计：会话 ID、理由；每次翻页加载正文写一条审计：seq 范围、条数（不写正文）。
4. 正文查看页面显示**水印**：后台账号名 + 当前时间，平铺覆盖消息区域。
5. 一期不提供消息导出、复制按钮（P1 再评估导出）；正文区域禁用右键菜单只是辅助，不作为安全保证。
6. 其他字段：userId、昵称、群名正常显示；终端用户的 IP、设备标识等如以后提供，列表中按 `a.b.*.*` 脱敏。
7. 合规边界见 D-ADM-04：是否允许查看单聊正文需要拍板（可能只允许查看被举报的内容）。

**验收标准**
- AC-ADM-08-1【后端】：客服（有 `msg.meta`、无 `msg.read`）查询会话消息，响应中每条消息没有 `body` 字段（不是前端隐藏，是接口不返回）。
- AC-ADM-08-2【后端】：审核员不提交理由、或提交理由但未重新验证，请求正文返回 4000 / 4017，响应中没有正文。
- AC-ADM-08-3：审核员申请查看会话 A 的正文后，可以看到 A 的正文；15 分钟后（测试时钟）再加载返回 4017；用 A 的授权请求会话 B 的正文返回 403。
- AC-ADM-08-4【后端】：申请一次、翻 3 页后，审计中有 1 条 `msg.read.grant`（含理由）和 3 条 `msg.read.page`（含 seq 范围）。
- AC-ADM-08-5【前端】：正文查看页截图中可以看到包含账号名和时间的水印。

#### F-ADM-09 浏览器侧安全（P0）

**规则**
1. **管理密钥只在 BFF 的服务端配置里**；前端代码、构建产物、接口响应、Cookie 中都不能出现。
2. 用户可控内容（昵称、群名、消息正文、推送内容）一律按纯文本渲染，禁止 `dangerouslySetInnerHTML` / `innerHTML`（后台用户权限高，存储型 XSS 的危害比客户端更大）。
3. 响应头：`Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; frame-ancestors 'none'`（不允许内联脚本）；`X-Content-Type-Options: nosniff`；`Referrer-Policy: no-referrer`。
4. 可选：BFF 只允许配置的来源网段访问（`ADM_ALLOWED_CIDRS`，如公司内网 / VPN），见 D-ADM-01。
5. 前端依赖跑 `npm audit`（高危阻断），与服务端 S11 一致。

**验收标准**
- AC-ADM-09-1【前端】：在构建产物（`dist/`）和一次完整操作流程的 HAR 中，搜索管理密钥原文和 `X-Admin-Key`，结果为 0。
- AC-ADM-09-2：导入昵称为 `<img src=x onerror=alert(1)>` 的用户、发送同样内容的消息，在后台用户列表、详情、消息正文页都原样显示该字符串，不弹窗、不发出对 `x` 的请求。
- AC-ADM-09-3【后端】：任一页面响应头包含上述 CSP，且含 `frame-ancestors 'none'`；在其他域名的 iframe 中嵌入后台，浏览器拒绝加载。
- AC-ADM-09-4【后端】：配置 `ADM_ALLOWED_CIDRS=10.0.0.0/8` 后，来自 `192.168.1.10` 的请求返回 403（含登录页）。

### 4.2 用户

#### F-ADM-10 用户搜索与详情（P0）

**规则**
1. 搜索：按 userId 精确 / 前缀、昵称前缀；结果显示 userId、昵称、头像、注册时间、是否在线、封禁 / 禁言标记。

**验收标准**
- AC-ADM-10-1：存在 `u100`、`u101`、`u2`，搜索 `u10` 返回 `u100`、`u101`，不返回 `u2`。
- AC-ADM-10-2：昵称为"小明"和"小明明"的用户，搜索"小明"两个都返回；搜索"明"不返回（前缀匹配）。

- AC-ADM-10-5：搜索不存在的 userId 显示"没有找到用户"；搜索关键字为空白时不发请求。

#### F-ADM-11 用户导入（P0）

**规则**
1. 两种方式：表单单个添加；上传 CSV（列：`userId,nickname,avatar`，UTF-8，有表头），单文件 ≤ 5000 行。
2. 先在 BFF **整体校验**（规则同 F-USER-01：userId 格式、昵称 ≤ 32、头像 ≤ 512、文件内重复以最后一条为准），任何一行不合法则整个文件不提交，列出所有出错行号和原因（最多显示前 100 条）。
3. 校验通过后预览前 20 行和总行数，确认后按每批 500 调用 `POST /admin/users/import`。
4. 中途某批失败：停止后续批次，显示"已成功 N 批 / 共 M 批"；因为导入是 upsert，可以整文件重新提交。
5. 已存在的 userId 会被更新昵称和头像，预览中标明"将更新 K 个已有用户"（P1，依赖批量查询）。

**验收标准**
- AC-ADM-11-1：上传 1200 行合法 CSV，确认后显示成功 1200；im-server 收到 3 次导入调用（500 + 500 + 200）。
- AC-ADM-11-2：第 7 行 userId 含空格、第 30 行昵称 33 字，提示两条错误（行号 + 原因），im-server 未收到任何导入调用。
- AC-ADM-11-3：上传 5001 行提示"单个文件最多 5000 行"，不提交。
- AC-ADM-11-4【后端】：模拟第 2 批返回 5000，结果显示"已成功 1 批 / 共 3 批"，第 3 批未调用；审计记录总行数、成功批次、失败错误码。

#### F-ADM-12 强制下线（P0）

**规则**：调用现有 `POST /admin/users/{userId}/force-logout`，语义不变（踢掉全部连接、此前签发的 token 全部作废，业务方重新签发即可恢复）。必须填理由；确认框中显示当前在线设备数。页面明确提示"业务方重新签发凭证后用户即可再次登录；要阻止登录请使用封禁"。

**验收标准**
- AC-ADM-12-1：u1 有 2 个在线连接，客服填理由后强制下线，两个连接都收到 `kicked/banned` 并以 4012 关闭；详情页在线设备变为 0。
- AC-ADM-12-2：强制下线后，用业务方重新签发的 token 可以正常连接。
- AC-ADM-12-3【后端】：对不存在的用户强制下线，页面提示"用户不存在"（4042），审计 result=failure。

#### F-ADM-13 封禁 / 解封（P0，新能力）

**描述**：与强制下线的区别：封禁期间**无法再签发 token**，业务方也绕不过去。对应腾讯 IM 的"账号封禁"。

**规则**
1. 封禁时长：1 小时、1 天、7 天、30 天、永久；必须填理由。
2. 封禁立即生效：踢掉全部在线连接（`kicked/banned`，4012，客户端文案沿用"账号已被下线"）；此前签发的 token 作废。
3. 封禁期间调用 `POST /admin/users/token` 返回 HTTP 403 / **4034 USER_BANNED**（新错误码），响应带 `bannedUntil`（永久为 `null`）。业务方据此提示用户。
4. 到期自动解封（不需要定时任务改状态：签发时按当前时间判断）；手动解封立即生效。解封后需要业务方重新签发 token。
5. 封禁不改变用户资料、群成员关系、历史消息。
6. 重复封禁以最后一次为准（覆盖到期时间和理由），审计里两次都有。
7. 管理接口同步开放给业务服务端（`POST /admin/users/{userId}/ban`、`/unban`），业务方也可以封禁。

**验收标准**
- AC-ADM-13-1：u1 在线，审核员封禁 1 天，u1 所有连接收到 `kicked/banned` 并以 4012 关闭。
- AC-ADM-13-2【后端】：封禁期间签发 u1 的 token 返回 403 / 4034，`bannedUntil` = 封禁时间 + 1 天（±5 秒）；永久封禁时 `bannedUntil` 为 `null`。
- AC-ADM-13-3【后端】：封禁前签发、尚未过期的 token 连接，收到 `kicked/banned`，以 4012 关闭。
- AC-ADM-13-4【后端】：封禁 1 小时，61 分钟后（测试时钟）签发 token 成功并能连接。
- AC-ADM-13-5：手动解封后立即可以签发 token；详情页封禁状态消失，审计中有 `user.unban`。
- AC-ADM-13-6【后端】：封禁后 u1 仍然在原有群的成员列表中；解封并重新登录后能看到封禁前的历史消息。
- AC-ADM-13-7【前端】：客服账号看不到"封禁"按钮；用户列表中被封禁的用户显示"已封禁"标记和到期时间。

- AC-ADM-22-1：1500 人的群，成员列表每页 50 人，翻到第 30 页共 1500 人，无重复。
- AC-ADM-22-2：加入 3 人，在线的新成员收到 `convAdded`；成员数 +3。
- AC-ADM-22-3：移除 1 人，该成员收到 `convRemoved`，之后在该群发言返回 4033。
- AC-ADM-22-4：一次粘贴 1200 人加入，分 3 批调用并全部成功；群成员数正确。
- AC-ADM-22-5：群已有 1999 人时加入 2 人，提示"群成员最多 2000 人"（4130），一个都没有加入。

#### F-ADM-23 群设置（P0）

**规则**：修改群名、`historyVisible`（调用现有 `PATCH`）。修改 `historyVisible` 的确认框说明"只影响之后的查询：打开后，所有成员（包括已入群的）都能看到入群前的历史"。

**验收标准**
- AC-ADM-23-1：群名改为"新名字"后，成员下次拉取 `convs` 显示新名字。
- AC-ADM-23-2：把 `historyVisible` 从关改为开后，入群前的消息对该成员可见（`sync` 能拉到入群前的 seq）。
- AC-ADM-23-3【前端】：群名清空或超过 50 字时，保存按钮不可点击并提示。

#### F-ADM-24 解散群（P0，新能力）

**规则**
1. 高危操作：理由 + 重新验证 + 输入群 ID 确认。
2. 解散后：在线成员收到 `convRemoved`（新增 `reason: "dissolved"`）；群从所有成员的 `convs` 中消失；对该群的 `send` / `sync` / `read` 返回 4043；管理接口查询返回 4043。
3. **群 ID 不能复用**：用已解散群的 ID 建群返回 4090，防止新群成员看到旧群历史。
4. 消息数据保留（按全局消息保留期，ARCH S13），只有后台 `msg.read` 能按会话查询（F-ADM-30），终端用户不可见。
5. 不提供"恢复群"（P2 再评估）。

**验收标准**
- AC-ADM-24-1：3 个成员在线，解散后 3 人都收到 `convRemoved`，`reason` 为 `dissolved`；刷新后会话列表中没有该群。
- AC-ADM-24-2【后端】：解散后成员 `send` 返回 4043，`sync` 返回 4043；`GET /admin/groups/{id}` 返回 404 / 4043。
- AC-ADM-24-3【后端】：用同一 groupId 再次建群返回 409 / 4090。
- AC-ADM-24-4【后端】：解散后，审核员在后台仍能按会话 `group:{id}` 查询到历史消息（需要 `msg.read`）。
- AC-ADM-24-5：解散时离线的成员，上线后 `convs` 中没有该群，SDK 本地也移除该会话。

### 4.4 消息

#### F-ADM-30 会话消息查询（P0）

**规则**
1. 入口：① 输入会话 ID（`c2c:{a}:{b}` 或 `group:{gid}`）；② 从用户详情 → 该用户的会话列表（P1，依赖 G-ADM-13）；③ 从群详情。
2. 按 seq 倒序分页（每页 50），可按时间范围、发送者筛选。
3. 元数据需要 `msg.meta`；正文需要 `msg.read` 并遵守 F-ADM-08。
4. 查询不受 `historyVisible` 和成员关系限制（后台看到的是会话全部消息），已删除的消息显示"已删除"标记、删除人和时间。
5. 一期不支持跨会话全文搜索（P2，见第 9 节）。

**验收标准**
- AC-ADM-30-1：会话有 120 条消息，第 1 页显示 seq 120～71，第 3 页显示 20～1，然后显示"没有更多了"。
- AC-ADM-30-2：按发送者 u2 筛选，只出现 u2 发的消息。
- AC-ADM-30-3【后端】：会话 ID 格式错误返回 4007；会话不存在返回空列表（不暴露是否存在单聊关系以外的信息）。
- AC-ADM-30-4【后端】：10 万条消息的会话，任意一页 P95 ≤ 500ms。

#### F-ADM-31 删除违规消息（P0，新能力）

**描述**：对应腾讯 IM 的"删除 / 撤回消息"。删除后所有端同步不再显示原文。

**规则**
1. 需要 `msg.delete` + 理由 + 重新验证；可在消息查询页单条或多选（单次 ≤ 50 条，同一会话）。
2. 服务端**软删除**：保留 seq、msgId、发送者、时间，清空正文，标记 `deleted=true`、`deletedBy`（后台账号）、`deletedAt`。**seq 不留空洞**，不影响"不丢不重"的补拉逻辑。
3. 在线的会话参与者（单聊双方、群全体成员，含发送者其他端）收到事件 `msgDeleted {convId, msgIds, seqs}`；离线的在下次 `sync` 时拿到带 `deleted=true` 的消息。
4. 客户端：把本地该消息替换为占位"该消息已被删除"，并**清除本地缓存中的原文**；如果是会话最后一条，`convs` 的 `lastMsg` 摘要显示"该消息已被删除"。
5. 原文是否隔离保存用于取证，见 D-ADM-05（推荐：加密隔离保存 30 天，只有 `msg.read` 可看，到期物理删除）。
6. 已删除的消息不能再删除（幂等，返回成功）；不提供恢复。
7. 管理接口同步开放给业务服务端（`POST /admin/messages/delete`，PLAN 2.3 已规划）。
8. 需要修改 PRD-core（升 v1.3）、协议 Schema、两套 SDK，见第 8 节。

**验收标准**
- AC-ADM-31-1：群 g1 中 u1 发了一条消息，3 个成员在线；审核员删除后，3 个成员（以及 u1 的另一端）都收到 `msgDeleted`，界面变为"该消息已被删除"。
- AC-ADM-31-2【后端】：删除后，离线成员上线 `sync` 拿到该 seq 的消息，`deleted=true`，没有 `body`；前后 seq 连续。
- AC-ADM-31-3【前端】：删除后在客户端 IndexedDB / 内存缓存中搜索原文特征串，结果为 0。
- AC-ADM-31-4：被删除的是最后一条消息时，会话列表摘要显示"该消息已被删除"。
- AC-ADM-31-5【后端】：一次删除 51 条返回 4131；跨会话的 msgId 返回 4000；对已删除的消息再次删除返回成功，不再次下发事件。
- AC-ADM-31-6【后端】：删除操作审计中有 msgId 列表和理由，没有原文。

### 4.5 禁言

#### F-ADM-40 用户级禁言（P0，新能力）

**规则**
1. 禁言后该用户在**所有会话**（单聊、群聊；二期聊天室）都不能发消息；可以正常登录、接收、拉历史、标记已读。
2. 时长：10 分钟、1 小时、1 天、7 天、30 天、永久，或自定义（1 分钟～30 天）；必须填理由。
3. 被禁言用户 `send` 返回 ack 错误 **4031 MUTED**，`error` 中带 `mutedUntil`（毫秒，永久为 `null`）和 `scope: "user"`。
4. 禁言 / 解除时，该用户在线连接收到事件 `muted {scope: "user", mutedUntil}` / `unmuted {scope: "user"}`，客户端据此禁用 / 恢复输入框。
5. 到期自动解除（发送时按当前时间判断）；重复禁言以最后一次为准。
6. 4031 不计入发送限流（C-29），重发不改变结果。
7. 管理接口同步开放（`POST /admin/mute`，PLAN 2.3）。

**验收标准**
- AC-ADM-40-1：u1 禁言 10 分钟后，发单聊和群聊都返回 4031，`mutedUntil` = 禁言时间 + 10 分钟（±5 秒），`scope` = `user`。
- AC-ADM-40-2：禁言期间 u1 能收到别人发来的消息，`sync`、`read` 正常。
- AC-ADM-40-3【后端】：11 分钟后（测试时钟）u1 发送成功。
- AC-ADM-40-4：手动解除后 u1 立即可以发送；u1 在线端收到 `unmuted`，输入框恢复。
- AC-ADM-40-5【前端】：收到 `muted` 后输入框禁用，显示"你已被禁言，解除时间：{时间}"；永久禁言显示"你已被禁言"。

#### F-ADM-41 群成员禁言（P0，新能力）

**规则**
1. 只在指定群内不能发言，其他会话不受影响。
2. 时长、理由同 F-ADM-40；`send` 返回 4031，`scope: "group"`、`groupId`。
3. 用户级禁言与群内禁言同时存在时，返回 `scope: "user"`（范围大的优先），`mutedUntil` 取对应记录。
4. 被移出群时清除该群的禁言记录；再次入群不继承。
5. 群在线成员中只有被禁言者本人收到 `muted` 事件（不公开通知全群，P1 再考虑群内系统提示）。

**验收标准**
- AC-ADM-41-1：u1 在 g1 禁言 1 小时后，在 g1 发言返回 4031（`scope=group`、`groupId=g1`）；在 g2 和单聊发言正常。
- AC-ADM-41-2：u1 同时被用户级禁言和 g1 禁言，在 g1 发言返回 `scope=user`。
- AC-ADM-41-3【后端】：把 u1 移出 g1 再加入，u1 在 g1 发言成功。
- AC-ADM-41-4：群详情的成员列表中，u1 显示"禁言中"和到期时间；解除后标记消失。

#### F-ADM-42 全群禁言（P1）

**规则**：开启后只有（P1 新增的）群管理员能发言，一期没有群管理员概念，所以全员禁言；成员发言返回 4031（`scope: "groupAll"`）；全群在线成员收到 `muted {scope: "groupAll", groupId}`。

**验收标准**
- AC-ADM-42-1：开启 g1 全群禁言后，任何成员在 g1 发言返回 4031（`scope=groupAll`）；关闭后恢复。

### 4.6 系统通知

#### F-ADM-50 系统通知（P0，依赖二期 `push` 协议）

**描述**：对应腾讯 IM 的系统消息 / 业务推送（现有 App 借道群消息实现，曾经监听错回调导致收不到）。后台发出，客户端 SDK 通过 `pushes` 流交给业务代码按 `type` 分发。

**规则**
1. 目标：① 按用户（手填或 CSV，单次 ≤ 1000 个 userId）；② 全员。按房间推送等聊天室上线后加（二期）。
2. 内容：`type`（从 BFF 配置的模板列表中选择，如 `notice`、`activity`，每个模板定义 `data` 的 JSON Schema）+ `data`（JSON，≤ 4KB，按模板 Schema 校验）。
3. 投递语义（D-ADM-07）：按用户推送**持久化**，离线用户上线后补收，保留 7 天；全员推送**只投递给当前在线用户**，不持久化。
4. 全员推送是高危操作：重新验证 + 输入"全员发送"确认；同一后台全员推送间隔 ≥ 5 分钟（P1：双人复核）。
5. 发送前必须预览（显示目标人数 / "全员"、type、格式化后的 data）。
6. 发送记录：时间、操作人、目标、type、data 摘要（长度 + 哈希）、im-server 返回的投递统计（P1）。

**验收标准**
- AC-ADM-50-1：向在线用户 u1、u2 发送 type=`notice` 的通知，两人 3 秒内收到 `push` 帧，`type` 和 `data` 与发送内容一致。
- AC-ADM-50-2：u3 离线时按用户推送，u3 在 7 天内上线后收到该通知；超过 7 天（测试时钟）上线收不到。
- AC-ADM-50-3：全员推送时，在线的 5 个用户都收到；离线用户上线后收不到。
- AC-ADM-50-4【后端】：`data` 不符合模板 Schema 或超过 4KB 返回 4000，不投递。
- AC-ADM-50-5【后端】：全员推送成功后 4 分钟内再次全员推送返回 429，提示"全员通知间隔不少于 5 分钟"。
- AC-ADM-50-6【后端】：userId 列表中有不存在的用户时返回 4042 并列出这些 userId，整批不发送；1001 个 userId 返回 4131。

### 4.7 内容审核与数据

#### F-ADM-60 敏感词与内容审核（P2）

**规则**：维护敏感词库（词、级别：拦截 / 替换为 `*`）；im-server 发送前检查（一期为内置词库，之后接 ARCH S14 的审核 Webhook）；拦截时 `send` 返回新错误码 4050 CONTENT_BLOCKED；词库变更经 `cache.Invalidator` 通知所有节点。

**验收标准**
- AC-ADM-60-1：添加拦截词"违规词"后 10 秒内，发送含该词的消息返回 4050，消息不落库。
- AC-ADM-60-2：添加替换词"坏词"后，发送"这是坏词"，接收方收到"这是**"。

#### F-ADM-70 数据概览（P1）

**规则**：首页卡片：当前在线连接数（按平台）、今日新增用户、今日消息数、群总数；数据来自 im-server 统计接口（G-ADM-17），每 60 秒刷新；**不读取运维用的内网 `/metrics`**（那是运维后台的范围）。

**验收标准**
- AC-ADM-70-1：3 个 web 连接、2 个 pc 连接在线时，概览显示在线 5（web 3、pc 2），60 秒内刷新。

## 6. 后台服务端方案与服务端缺口

### 6.1 方案对比

| | 方案 A：im-server 内新增 `/console/*` | 方案 B：独立后台服务（BFF），调用 im-server 管理接口（**推荐**） |
|---|---|---|
| 形态 | 人员账号、会话、RBAC、审计都写进 im-server，和 `/ws`、`/admin` 同一进程、同一端口（或单独端口） | 新进程 `admin-console`（Go，同仓库 `server/cmd/admin-console`），托管前端静态资源 + `/console/api/*`；对 im-server 只是一个"业务服务端"调用方 |
| 攻击面 | 每个对外的 IM 节点都带着人员登录、密码校验、会话等代码；任何一处漏洞直接在 IM 进程里 | IM 对外端口不变；BFF 可以只部署在内网 / VPN 后面（`ADM_ALLOWED_CIDRS`）；BFF 被攻破时，权限也只限于它那把密钥的范围 |
| 密钥 | 不需要密钥（进程内调用），但"人员会话 → 管理权限"的映射混在 IM 代码里 | BFF 持有**独立的、限定权限的**管理凭证（G-ADM-03），浏览器永远拿不到 |
| 分布式 | IM 节点扩容时后台跟着扩，人员会话要进 IM 的共享存储 | BFF 无状态，独立扩容（通常 1～2 个实例足够）；IM 集群化不受影响 |
| 数据 | 后台账号、审计表进 IM 主库，迁移 / 备份耦合 | 后台账号、会话、审计放 BFF 自己的库，审计可以单独设置只追加权限和保留期 |
| 代价 | 少一个进程，开发最快 | 多一个进程和一套部署；im-server 必须先补齐管理接口（第 6.2 节，**无论 A / B 都要补**）；需要提前做 S8 的一部分（独立密钥 + 签名） |
| 演进 | 以后拆出去要返工 | 运维后台（Q10）可以复用同一个 BFF 的账号、会话、审计模块 |

**推荐 B**：符合"安全第一"和"方便分布式"两条原则，额外成本主要是 S8 提前——而 S8 是集群化 / 正式运营前本来就要做的。运维后台可以与管理后台共用同一个 BFF（不同菜单和权限），见 D-ADM-01。

## 7. 非功能需求

| 类别 | 要求 |

## 9. 待拍板（D-ADM-xx）

| # | 问题 | 背景 | 选项与代价 | 推荐 |
|---|---|---|---|---|
| D-ADM-01 | 后台部署形态 | 见 6.1 | **A** im-server 内 `/console/*`：最快，但人员登录代码进入每个对外 IM 节点，以后拆出返工。**B** 独立 BFF：多一个进程；需要提前做 S8 的独立密钥 + 签名（约 2～3 天）。**B′** B 的基础上与运维后台共用一个 BFF | **B′**：独立 BFF，部署在内网 / VPN 后，管理后台和运维后台共用账号、会话、审计模块 |
| D-ADM-02 | 登录方式 | 公司是否有统一身份（企业微信 / 飞书 / 钉钉 / OIDC）未知 | **自建账号 + 强制 TOTP**：不依赖外部，要自己做密码、锁定、恢复码。**接公司 SSO（OIDC）**：离职自动失效、少维护密码，但依赖 IdP 可用性和对接排期。**两者都做**：工作量最大 | 一期**自建 + 强制 TOTP**，账号模型预留 `idp_subject` 字段；公司有 IdP 时 P1 改为 SSO 登录（仍在后台侧做 RBAC 和审计），保留 1 个本地超管作应急 |
| D-ADM-03 | 一期范围 | 新能力多，且大多要改协议和两套 SDK | **大**：第 3 节全部 P0。**小**：先做安全基座 + 用户（含封禁）+ 群（含解散）+ 审计，禁言 / 删消息 / 推送等二期协议定稿后再做 | 按第 3 节 P0，但**分两批**交付：第一批安全基座 + 用户 + 群 + 消息元数据查询（不改客户端协议）；第二批禁言、删消息、系统通知（与二期协议、SDK 一起） |
| D-ADM-04 | 查看消息正文的权限与合规 | 单聊属于用户隐私，《个人信息保护法》要求最小必要；但处理举报、配合监管又需要看 | **a 不允许查看正文**：最安全，但无法处理违规。**b 专门角色 + 理由 + 重新验证 + 审计 + 水印（本文方案）**：可用，依赖内部管理。**c 只能查看被举报消息及前后 N 条**：最合规，但需要先做"举报"功能（客户端 + 服务端） | 一期 **b**，且默认只给"内容审核"角色；单聊正文是否允许查看**请法务确认**；有举报功能后收紧为 **c** |
| D-ADM-05 | 删除消息后原文怎么处理 | 软删除后客户端看不到，但取证可能需要原文 | **立即物理删除**：最干净，无法取证。**加密隔离保存 30 天后删除**：可取证，需要 G-ADM-19 和密钥管理。**永久保留**：合规风险大 | **加密隔离保存 30 天**，只有 `msg.read` 可看（同样走 F-ADM-08 留痕），到期物理删除 |
| D-ADM-06 | 封禁由谁主导 | 业务方有自己的用户体系，也可能自己封号；IM 封禁会让业务方签发 token 失败 | **IM 封禁（本文）**：客服可以直接处理，业务方需要处理 4034。**只由业务方封禁**：IM 后台只能强制下线，客服要转给业务方。**两边都可以** | **两边都可以**：IM 提供封禁（后台 + 管理接口），业务方签发 token 遇到 4034 时提示用户；接入文档写明 |
| D-ADM-07 | 系统通知的投递语义 | 腾讯现状借道群消息（持久化）；协议 `push` 是二期，持久化方案未定 | **只投在线**：最简单，离线用户收不到。**按用户持久化 7 天 + 全员只投在线（本文）**：兼顾，需要存储按用户的通知队列。**全部持久化**：全员推送 × 用户数，存储压力大 | **按用户持久化 7 天、全员只投在线**；"站内信"列表（已读 / 未读）放 P1 |
| D-ADM-08 | 审计保留期与存储 | 法律下限 6 个月；审计数据量随操作增长 | **6 个月在线**：存储最少，刚好满足下限。**1 年在线 + 3 年归档**：留出余量，归档要加密。**永久** | **1 年在线 + 3 年加密归档**；审计独立库，P1 同步到外部只追加存储 |
