## 1. 背景与目标

### 1.1 背景

fx-sport（Flutter）、ab77（iOS）、android 三个 App 的聊天室和站内推送都依赖腾讯云 IM。问题：
- 费用、功能、数据都受第三方约束；
- 三端各自封装一遍腾讯 SDK（合计约 2400 行），逻辑重复、行为不一致；
- 推送"借道"群消息通道，曾经因为监听错回调导致收不到推送。

### 1.2 目标

自研 IM 公共库（服务端 + SDK），并基于它做一个独立的 IM 聊天软件。

**一期只做核心业务**：让两个人、一群人能可靠地聊天。具体是账号接入、连接、单聊、群聊、会话列表、未读、多端同步。

二期再做业务接入能力（直播聊天室、系统推送、禁言、删消息），见第 7 节。

### 1.3 成功标准

| 指标 | 目标 |
|---|---|
| 消息可靠性 | 正常网络和弱网 / 断网重连场景下，不丢消息、不出现重复消息 |
| 实时性 | 双方在线时，从发出到对方看到 ≤ 1 秒（局域网 P99） |
| 多端一致 | 同一账号在 H5、PC、手机同时在线时，各端看到的消息和未读数一致 |
| 演示 | 分享会上能现场演示两个浏览器互聊、断网重连后消息补齐 |

## 2. 用户与场景

| 角色 | 说明 |
|---|---|
| 终端用户 | 使用 IM App（H5 / PC / Android / iOS）聊天的人 |
| 业务服务端 | 接入方（如 fx-sport 后端）。负责自己的用户体系，向 IM 换取用户凭证、建群、管成员 |
| 运营 / 管理员 | 一期通过管理接口操作，不做管理后台页面 |

核心场景：
1. 小明打开 App，看到会话列表和每个会话的未读数。
2. 小明给小红发消息，小红在线时立刻收到；小红离线时，上线后能看到。
3. 小明在地铁里网络断了，恢复后自动重连，期间别人发来的消息自动补齐，自己没发出去的消息可以重发且不会重复。
4. 小明手机和电脑同时在线，在手机上发的消息，电脑上也能看到；在电脑上读过的会话，手机上的未读也会清掉。
5. 业务方给一场活动建群，把参与者拉进来，大家在群里聊天。

## 4. 功能需求

> 格式：描述 → 业务规则 → 异常场景 → 验收标准（AC）。AC 必须能被测试直接验证。

### F-AUTH-01 业务方签发用户凭证（P0）

**描述**：业务服务端用管理密钥调用 IM 接口，为自己的用户换取 IM 凭证（token），下发给客户端。对应腾讯 IM 的 `genUserSig`。

**业务规则**
1. IM 不维护密码，用户身份以业务方传入的 `userId` 为准。
2. `userId` 只允许字母、数字、`_`、`-`，长度 1～64。
3. 凭证默认有效期 7 天，业务方可指定，最长 30 天。
4. 管理接口必须携带正确的管理密钥，否则拒绝。

**异常场景**：密钥错误 / 缺失；`userId` 不合法；有效期为 0 或负数（按默认处理）。

**验收标准**
- AC-AUTH-01-1：携带正确密钥和合法 `userId` 时，返回 token 和过期时间（毫秒时间戳）。
- AC-AUTH-01-2：密钥缺失或错误时返回 401，不签发 token。
- AC-AUTH-01-3：`userId` 不合法时返回 400。
- AC-AUTH-01-4：指定有效期超过 30 天时，按 30 天签发。

### F-AUTH-02 客户端登录与连接（P0）

**描述**：客户端拿到 token 后建立长连接，连接成功即视为"已登录 IM"。

**业务规则**
1. 连接时携带 token 和平台标识（android / ios / web / pc）。
2. 同一账号允许多个平台、多个设备同时在线（见 F-SYNC-01）。
3. token 无效或过期时拒绝连接。

**异常场景**：token 无效、过期、缺失；网络不通。

**验收标准**
- AC-AUTH-02-1：token 有效时连接成功，可以收发消息。
- AC-AUTH-02-2：token 无效 / 过期 / 缺失时连接被拒绝（HTTP 401），客户端提示"登录已失效"并回到登录页。
- AC-AUTH-02-3：同一账号在两个设备上同时连接，两个连接都保持在线。

### F-AUTH-03 凭证过期与被踢下线（P0）

**描述**：已连接的客户端在 token 过期或被业务方封禁时，要被服务端断开并告知原因。

**业务规则**
1. token 到期时，服务端主动下发 `kicked`（原因 `tokenExpired`）并断开连接。
2. 业务方可调用管理接口让某用户的所有连接下线（原因 `banned`）。
3. 客户端收到 `kicked` 后**不得自动重连**，要提示用户并回到登录页。
4. 一期不做"单设备登录互踢"（原因 `replaced`），保留协议字段。

**异常场景**：被踢时客户端正有消息在发送中 → 这些消息标记为发送失败。

**验收标准**
- AC-AUTH-03-1：token 到期后 5 秒内，客户端收到 `kicked/tokenExpired` 并被断开。
- AC-AUTH-03-2：调用"强制下线"接口后，该用户所有在线连接收到 `kicked/banned` 并被断开。
- AC-AUTH-03-3：被踢后客户端不再自动重连，界面提示原因并回到登录页。

### F-AUTH-04 演示用登录服务（P0）

**描述**：真实环境由业务服务端签发 token；但独立 IM App 和分享会演示没有业务服务端，需要一个**模拟业务服务端**：输入用户名即可登录。

**业务规则**
1. 仅用于开发和演示，生产环境必须关闭。
2. 前端不得持有管理密钥；由模拟服务转调 IM 管理接口。
3. 用户名规则同 `userId`。

**验收标准**
- AC-AUTH-04-1：前端提交用户名，模拟服务返回 IM token，前端用它能连接成功。
- AC-AUTH-04-2：前端代码和网络请求中不出现管理密钥。
- AC-AUTH-04-3：模拟服务可通过配置关闭，关闭后接口返回 404。

### F-CONN-01 心跳保活与断线重连（P0）

**描述**：客户端定时发心跳；网络断开后自动重连，重连成功后补齐断线期间的消息。

**业务规则**
1. 客户端每 30 秒发一次心跳；服务端 90 秒收不到任何数据就断开该连接。
2. 断线后自动重连，等待间隔指数退避：1s、2s、4s … 最长 30s，并加随机抖动，避免大量客户端同时重连。
3. 网络从不可用恢复为可用时（浏览器 `online` 事件 / 系统网络回调），立即尝试重连，不等退避。
4. 重连成功后，对**所有本地已有的会话**按本地最大 seq 补拉（见 F-MSG-05）。
5. 因 `kicked` 断开的不重连（见 F-AUTH-03）。

**验收标准**
- AC-CONN-01-1：保持连接 5 分钟不操作，连接不断开。
- AC-CONN-01-2：客户端停止发心跳超过 90 秒，服务端断开连接。
- AC-CONN-01-3：断网 10 秒后恢复，客户端在 5 秒内自动重连成功。
- AC-CONN-01-4：断网期间别人发来 3 条消息，重连后这 3 条消息按顺序出现，没有重复。
- AC-CONN-01-5：服务端持续不可用时，重连间隔逐步增大，最长不超过 30 秒。

### F-CONN-02 连接状态提示（P0）

**描述**：用户能看到当前是否连上了服务器。

**业务规则**
1. 三种状态：已连接（不显示提示）、连接中（顶部显示"连接中…"）、未连接（顶部显示"网络不可用"）。
2. 状态变化 500 毫秒内反映到界面；短于 1 秒的闪断不显示提示，避免界面闪烁。

**验收标准**
- AC-CONN-02-1：断网后 3 秒内顶部出现"网络不可用"或"连接中…"。
- AC-CONN-02-2：恢复连接后提示自动消失。

### F-MSG-01 单聊发送文本消息（P0）

**描述**：用户在单聊会话里发送文本消息。

**业务规则**
1. 文本长度 1～5000 字符；首尾空白会被去掉，去掉后为空则不能发送。
2. 每条消息由客户端生成唯一的 `clientMsgId`，用于去重。
3. 服务端为消息分配会话内递增的 `seq` 和全局唯一的 `msgId`，以服务端时间为准。
4. 可以给自己发消息（"文件传输助手"场景）。
5. 一期不校验对方 `userId` 是否存在（IM 不维护用户表），由业务方保证。

**异常场景**：文本超长；内容为空；网络断开；服务端返回错误。

**验收标准**
- AC-MSG-01-1：输入"你好"点发送，消息立即出现在会话底部（发送中状态），收到服务端确认后变为已发送。
- AC-MSG-01-2：输入为空或全是空格时，发送按钮不可点。
- AC-MSG-01-3：超过 5000 字时提示"消息过长"，不发送。
- AC-MSG-01-4：同一会话里连续发送的消息，`seq` 严格递增。

### F-MSG-02 接收消息（P0）

**描述**：在线时实时收到别人发来的消息。

**业务规则**
1. 当前正在查看该会话：消息直接追加到底部，并自动标记已读（见 F-CONV-02）。
2. 没在看该会话：会话列表里该会话的最后一条消息和未读数更新，会话移到列表顶部。
3. 消息按 `seq` 排序展示，不按到达顺序。

**验收标准**
- AC-MSG-02-1：A 给 B 发消息，B 在线时 1 秒内看到。
- AC-MSG-02-2：B 正在看与 A 的会话时，新消息出现在底部，未读数不增加。
- AC-MSG-02-3：B 在会话列表页时，与 A 的会话移到顶部，显示最新内容，未读数 +1。

### F-MSG-03 发送状态与失败重发（P0）

**描述**：用户能看到每条自己发出的消息是否发送成功，失败的可以重发。

**业务规则**
1. 状态：发送中 → 已发送 / 发送失败。
2. 10 秒内未收到确认视为失败。
3. 断线时发出的消息先进入"发送中"，重连后自动重发一次；仍失败则标记失败。
4. 点"发送失败"图标可手动重发，**使用原 `clientMsgId`**，保证服务端不会产生重复消息。
5. 失败消息在本地保留，刷新页面后仍可见、可重发（P1：一期 H5 可以只保留在内存中）。

**验收标准**
- AC-MSG-03-1：断网后发送消息，显示"发送中"，超时后显示"发送失败"图标。
- AC-MSG-03-2：恢复网络后点击重发，消息变为已发送，对方只收到一条。
- AC-MSG-03-3：模拟"服务端已保存但确认丢失"后重发，对方只收到一条，`msgId` 与第一次相同。

### F-MSG-04 消息不丢、不重、有序（P0）

**描述**：可靠性底线，贯穿发送、接收、重连。

**业务规则**
1. **不重**：服务端按（发送者，`clientMsgId`）去重；客户端按 `msgId` 去重展示。
2. **不丢**：客户端记录每个会话收到的最大 `seq`。收到的消息 `seq` 不连续（出现缺口）时，立即补拉缺口。
3. **有序**：同一会话内按 `seq` 升序展示。多人同时发言时，实时消息可能乱序到达，客户端要按 `seq` 插入到正确位置。

**验收标准**
- AC-MSG-04-1：同一 `clientMsgId` 重复提交 N 次，服务端只保存 1 条，每次返回相同的 `msgId` 和 `seq`。
- AC-MSG-04-2：客户端收到 seq=1、seq=3（缺 2）时，会自动补拉到 seq=2，最终按 1、2、3 展示。
- AC-MSG-04-3：5 个人在同一个群里各并发发 20 条，所有成员最终都看到 100 条，`seq` 为 1～100，连续且不重复。

### F-MSG-05 历史消息与离线补拉（P0）

**描述**：打开会话时加载历史消息；离线期间的消息上线后补齐。

**业务规则**
1. 打开会话先显示本地缓存，再从服务端补拉更新的消息。
2. 向上滚动到顶部时加载更早的消息，每次 20 条，直到没有更多。
3. 服务端单次最多返回 200 条，并告知是否还有更多。
4. 只能拉取自己参与的会话（单聊的一方、群成员）。

> ⚠️ 待评审：M1 的 `sync` 只支持"拉取 seq 之后的消息"（向后），**不支持向前翻页加载更早的消息**，需要补一个"拉取 seq 之前的消息"能力。

**验收标准**
- AC-MSG-05-1：离线期间收到 5 条消息，上线打开会话能看到全部 5 条。
- AC-MSG-05-2：会话里有 100 条历史消息，打开后显示最新的 20 条，向上滚动可以依次加载更早的，直到第 1 条。
- AC-MSG-05-3：拉取自己不在其中的会话时被拒绝（错误码 4030）。

### F-GRP-01 建群与成员管理（P0，管理接口）

**描述**：一期群由业务服务端通过管理接口创建和管理，App 内不提供建群入口。

**业务规则**
1. 建群：群 ID 由业务方指定（规则同 `userId`），附带群名称和初始成员。
2. 加成员、移除成员；单群成员上限 2000。
3. 查询群信息（名称、成员列表）。
4. 群 ID 重复创建返回冲突错误。
5. 成员变动后，新成员只能看到加入**之后**的消息吗？——**待评审决定**（方案 A：能看全部历史，实现简单；方案 B：只看加入后的，符合微信习惯）。

**验收标准**
- AC-GRP-01-1：建群成功后，初始成员都能在群里发消息。
- AC-GRP-01-2：重复建同一个群 ID 返回 409。
- AC-GRP-01-3：移除成员后，该成员不能再发送、拉取该群消息（4030），也不再收到新消息。
- AC-GRP-01-4：成员数超过 2000 时建群 / 加成员失败（400）。
- AC-GRP-01-5：可查询群名称和成员列表。

### F-GRP-02 群消息收发（P0）

**描述**：群成员在群里发送和接收文本消息。

**业务规则**
1. 只有群成员能发送、接收、拉取群消息。
2. 群消息展示发送者（一期显示 `userId`，有 F-USER-01 后显示昵称）。
3. 其余规则同单聊（发送状态、去重、有序、补拉）。

**验收标准**
- AC-GRP-02-1：成员发群消息，其他在线成员 1 秒内收到，发送者本设备不重复收到。
- AC-GRP-02-2：非成员发送群消息返回 4030；群不存在返回 4040。
- AC-GRP-02-3：群消息里能看到是谁发的。

### F-CONV-01 会话列表（P0）

**描述**：App 首页展示用户的所有会话（单聊和群聊）。

**业务规则**
1. 每个会话显示：头像占位、名称（单聊为对方 `userId`，群聊为群名）、最后一条消息摘要、时间、未读数。
2. 按最后一条消息时间倒序排列。
3. 登录后从服务端拉取会话列表（换设备、清缓存后也能恢复）。
4. 用户参与过（发过或收到过消息）的单聊、所在的群，都出现在列表里；新建且没有消息的群也显示。
5. 一期不做置顶、删除会话、免打扰（P1）。

**验收标准**
- AC-CONV-01-1：A 和 B、C 各聊过，且在群 g1 里，A 登录后会话列表显示 3 个会话，按最后消息时间倒序。
- AC-CONV-01-2：收到新消息的会话移到列表顶部，摘要和时间更新。
- AC-CONV-01-3：在一台新设备登录，会话列表与原设备一致。

### F-CONV-02 未读数与标记已读（P0）

**描述**：每个会话显示未读消息数，打开会话后清零。

**业务规则**
1. 未读数 = 会话最大 `seq` − 用户在该会话的已读 `seq`；自己发的消息不计入未读。
2. 打开会话、或在会话中收到新消息时，上报已读位置（最新 `seq`）。
3. 已读位置只前进不后退。
4. 未读数大于 99 显示"99+"。
5. 首页（或 App 角标）显示总未读数（P1）。

**验收标准**
- AC-CONV-02-1：B 离线时 A 发来 3 条，B 登录后与 A 的会话未读数为 3。
- AC-CONV-02-2：B 打开该会话后未读数变为 0；重新登录后仍为 0（已读已同步到服务端）。
- AC-CONV-02-3：B 自己发出的消息不增加 B 的未读数。
- AC-CONV-02-4：未读 120 条时显示"99+"。

### F-SYNC-01 多端消息同步（P0）

**描述**：同一账号多端同时在线时，消息在各端一致。

**业务规则**
1. 别人发来的消息，所有在线端都收到。
2. 自己在某一端发出的消息，自己的其他在线端也收到；发送端本身只收到确认，不重复显示。
3. 不在线的端上线后按 F-MSG-05 补齐。

**验收标准**
- AC-SYNC-01-1：A 在手机和电脑同时在线，B 给 A 发消息，两端都收到。
- AC-SYNC-01-2：A 在手机发消息，电脑端也出现这条消息（显示为自己发的），手机端不重复显示。

### F-SYNC-02 已读状态多端同步（P1）

**描述**：在一端读过的会话，其他端未读数也清零。

**验收标准**
- AC-SYNC-02-1：A 在电脑上打开有 3 条未读的会话，手机端该会话未读数在 2 秒内变为 0。

### F-USER-01 用户昵称与头像（P1）

**描述**：会话列表、聊天页显示昵称和头像，而不是 `userId`。

**业务规则**：昵称、头像 URL 由业务方通过管理接口导入或更新；IM 只做存储和下发。

**验收标准**
- AC-USER-01-1：业务方设置昵称后，聊天页和会话列表显示昵称；未设置时显示 `userId`。

## 5. 页面与交互（前端）

一期先做 **H5**（手机浏览器布局），PC 用同一套代码的宽屏三栏布局（见 PLAN M3、M4）。

| 页面 | 内容 | 关联功能 |
|---|---|---|
| 登录页 | 输入用户名 → 登录（走演示登录服务） | F-AUTH-02、F-AUTH-04 |
| 会话列表（首页） | 顶部连接状态条；会话列表；未读角标 | F-CONV-01、F-CONV-02、F-CONN-02 |
| 聊天页 | 消息列表（区分自己和对方、显示发送者、时间）、发送状态、失败重发、输入框、上拉加载历史 | F-MSG-*、F-GRP-02 |
| 发起单聊 | 输入对方 `userId` 开始聊天（一期没有通讯录） | F-MSG-01 |
| 我的 | 当前账号、退出登录 | F-AUTH-02 |

交互细节：
- 消息时间：同一分钟内的连续消息不重复显示时间；跨天显示日期。
- 进入聊天页自动滚到底部；用户在看历史消息时，新消息不强制滚动，而是显示"↓ 有新消息"。

## 6. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 单机支持 1 万长连接；单聊端到端延迟 P99 ≤ 1 秒（局域网）；`sync` 单次 200 条响应 ≤ 200ms |
| 可靠性 | 服务端重启后消息不丢（已确认的消息都已落盘）；客户端重连后自动补齐 |
| 安全 | token 签名校验；管理接口密钥鉴权；生产必须配置独立密钥；前端不持有管理密钥；上线前开启 WebSocket Origin 白名单 |
| 兼容 | H5：最新两个大版本的 Chrome / Safari（含 iOS Safari）、微信内置浏览器 |
| 可观测 | 服务端记录连接建立 / 断开（含原因）、错误日志；`/healthz` 健康检查 |
| 可测试 | 每条 AC 至少对应一条测试用例；后端 e2e 测试覆盖所有 P0 的后端 AC |
