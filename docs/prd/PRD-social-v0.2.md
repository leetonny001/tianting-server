## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 好友模式（S-1） | 服务端开关 `mode = open | friends`，默认 `open`。开放模式：**任何人都能私聊**（S-1 原义），好友只用来整理通讯录。好友制：互为好友才能私聊。官方账号两种模式下都可以和任何人私聊（F-SOC-13） |
| 业务方粒度（S-4 ①） | **一个 im-server 部署 = 一个业务方** = 一套用户、一套配置。yd / yi / tb 如果共用一个部署，就**共用同一种好友模式和同一套限额**；要用不同模式就分开部署 |
| 防骚扰默认值（S-8 ②） | "陌生人在对方回复前最多发 N 条"（`strangerMsgLimit`）和"每小时最多给 N 个新对象发消息"（`newPeerHourlyLimit`）**默认 0 = 关闭**，业务方按需打开（推荐 3 / 30）。默认配置下 PRD-core 现有 e2e 和 TC-PERF 不受影响（13.1 节 V-04 逐条说明） |
| 防枚举 | 好友申请、拉黑、`users`、建群 / 邀请这几条路径，对"不存在""不可被搜索""拉黑了我"一律给出**相同应答**；唯一保留的存在性信号是私聊的 4042（D5，已冻结），由在**存在性判断之前**执行的"新对象被拒配额"（默认每人每天 100 次）封顶。可验证的指标见 1.3 节，逐路径的上限见 11.2 节 |
| 关系版本号 | 每用户一个 `ver`，**每个操作分配一个新值**，同一操作改动的该用户所有行写同一个 ver；`socialSync` 按 `(ver, 类型, 主键)` 游标分页，同一个 ver 可以跨页、不会丢；每轮同步固定一个 `untilVer`；清理墓碑和过期申请时推进 `purgedVer`，客户端的 ver 落后于它就全量重建（F-SOC-06） |
| 并发 | 改关系的事务先锁相关用户的 `user_social` 行（两个用户按 userId 字节序），群操作先锁 `chat_groups` 行，全局加锁顺序固定（8.3 节）。好友上限、互相申请自动通过、陌生人限额都在加锁的事务内原子完成。SQLite 单连接测不出的场景写成 **Postgres 并发测试，作为 B6 的前置验收条件** |
| 冻结需求的变更 | 全部列入 13.1 节（V-01～V-24）。**管理接口的任何群操作都不产生群提示消息**（AC-GRP-01-6 / 7 / 12 不变）；空的托管群仍然合法（AC-GRP-02-3 不变），只有自建群在最后一人退出时解散 |
| 范围（S-7 ②） | **M3**：好友、拉黑、通讯录、私聊权限、搜索、资料、官方账号、业务方好友接口（F-SOC-01～13）。**M4**：群角色、客户端建群与群管理、群公告、群提示消息（F-SOC-20～30）。两者都在分享会（M8）之前 |
| 管理接口（S-11 ②） | 社交管理接口**在 X-5 落地之后**才对真实业务方开放，并且必须写审计日志；X-5 之前只在测试模式下注册（供 e2e 使用），生产部署用启动配置设定好友模式 |
| 工作量 | M3 社交 **41 人日** + 前置依赖（X-5 约 3.5、H5 基础约 8）；M4 **21 人日**；原生 SDK 各 6（含在 M5 / M6 首版内）。社交合计 74 人日，比 v0.1 的 55 多 19，来自评审指出的漏项（第 15 节） |

## 1. 背景与目标

### 1.1 背景

一期只做了"能聊"：任何登录用户可以给任何存在的 userId 发私聊（`logic.go` 第 117～124 行只校验对方存在）；群只能由业务方通过 `/admin/*` 建和管理；没有好友、拉黑、通讯录、用户搜索。PRD-core 第 7 节把"App 内建群、通讯录、好友"放在三期，PRD-ui 的通讯录因此只能"从单聊会话派生"（U-2）。

2026-11-03 Frank 拍板 S-1～S-3（好友模式按业务方配置、两种关系来源都支持、分享会前做完），并在评审后按建议通过 E 节 S-4、S-7～S-11。

### 1.2 目标

1. 让独立 IM App 成为一个完整的社交聊天软件：加好友、拉黑、通讯录、自己建群和管理群。
2. 让接入方（fx-sport 等）按自己的产品形态选择"开放私聊"或"好友制"，能把自己系统里的关系（关注、好友）导入 IM，能用官方账号联系用户。
3. 不破坏一期已冻结的规则：消息不丢不重、多端一致、分布式就绪（ARCH）、安全优先。对冻结需求的每一处改动都列为 PRD-core v1.3 变更。

### 1.3 成功标准（每项都有可执行的度量方法）

| 指标 | 目标 | 度量方法 |
|---|---|---|
| 正确性 | 第 6、7 节全部 AC 通过 | TC-SOC-*；CI 中 `mode=open`、`mode=friends` 各跑一遍 |
| 不回归 | 默认配置下 `server/e2e` 现有用例**不改代码**全部通过；TC-PERF-00-01～07 的错误率仍为 0，P99 与 M3 前基线相比在 ±10% 以内（3 次中位数） | CI；压测报告对比 |
| 同步正确性 | 随机操作序列（两人、各两个连接，含并发操作、断线、事件丢弃、清理任务、`limit` 在 1～500 间随机）结束后，每个客户端的本地状态与服务端全量**完全一致** | 同步模型测试（16 节），每次 CI 至少 1000 个随机序列 |
| 多端一致 | 一端操作后，同一用户的其他在线端 2 秒内更新；断线期间的变化在重连后的同步轮结束时补齐 | AC-SOC-06-2、AC-SOC-04-2、AC-SOC-05-4 |
| 防枚举 | 一个账号**在不给对方发出真实消息的前提下**，每天最多确认 `newPeerRejectDailyLimit`（默认 100）+ `searchDailyLimit`（默认 100）个 userId 是否存在，其中搜索只对"可被搜索"的用户有效；对不可被搜索的用户，好友申请、拉黑、`users`、建群 / 邀请四条路径的应答与"不存在"逐字段相同，且拿不到昵称头像 | 11.2 节表格每行一条安全用例（AC-SOC-02-4、02-6、07-9、08-10、08-11、09-3、10-5、10-6、21-5） |
| 隐私 | 被单向删除、被拒绝、被拉黑、被静默的一方，操作后 2 秒内收不到任何帧、ver 不变；附言、备注、搜索关键字、群公告的特征串不出现在服务端日志 | AC-SOC-03-3、05-1、07-8；AC-SOC-02-11、09-8、27-5 |
| 性能 | 好友制下私聊发送 P99 增加 ≤ 2ms；全量同步（5000 好友 + 1000 黑名单 + 200 申请）单页 P99 ≤ 100ms、整轮 ≤ 1 秒 | 压测，同一场景 3 次取中位数（DECISIONS 第 3 节口径），AC-SOC-06-12 |
| 演示 | M3：搜索加好友 → 对方同意 → 开聊 → 拉黑后被拒收 → 通讯录显示好友和群；M4 起：建群、邀请、转让群主 | 彩排 |

## 2. 角色与场景

| 角色 | 说明 |
|---|---|
| 终端用户 | 加好友、拉黑、搜索、管理自己建的群（M4） |
| 群主 / 群管理员 | 自建群的管理者；托管群被业务方交接后的管理者（M4） |
| 官方账号 | 业务方标记的客服 / 运营账号，豁免好友制和防骚扰限额（F-SOC-13） |
| 业务服务端 | 选择好友模式；导入、增删好友关系；标记官方账号；建托管群、指定群主（M4）。所有调用都经 X-5 的分调用方密钥并留审计 |
| 管理后台运营 | 通过后台服务调用同一套管理接口（PRD-admin） |

核心场景：
1. （M3）小明在独立 App 里搜索小红的账号，发送好友申请"我是小明"；小红在"新的朋友"里看到红点，点同意；小明的手机和电脑同时出现小红，可以开始聊天。
2. （M3）fx-sport 选择好友制，把用户的互关关系批量导入 IM；没有互关的用户之间不能私聊，但都能联系官方客服账号。
3. （M3）小明被陌生人骚扰，拉黑对方；对方再发消息提示"被对方拒收"，加好友对方也收不到。
4. （M4）小明建一个 5 人的群，拉进 3 个好友，改群名、发群公告；有事要离开时把群主转让给小红。
5. （M4）业务方建了一个 2000 人的活动群（托管群），成员只能聊天和退群；业务方指定一个运营账号做群主后，该账号可以在 App 里踢人、发公告；运营账号退群后，群回到托管状态，不会落到普通成员手里。

### 3.2 M3 与 M4 的边界

- **M3 不包含任何客户端群操作**：协议里不注册 `group*` 命令（客户端调用返回 4001），不产生群提示消息，`convs` 不返回 `myRole`。M3 里与群有关的只有：通讯录的"我的群聊"（`myGroups`，F-SOC-11）和会话成员数（`memberCount`，待 U-4）。
- **M3 演示路径**（分享会最低要求 = M3，PLAN 第 8 节）：搜索 → 申请 → 同意 → 私聊 → 拉黑被拒 → 通讯录（好友 + 业务方建的群）→ 好友制切换演示（官方客服仍可联系）。
- M4 在 M3 的数据和协议之上增加 0005 迁移和群命令，不修改 M3 已发布的字段含义。

## 4. 术语

| 术语 | 定义 |
|---|---|
| 业务方 | 一个 im-server 部署对应的接入方（S-4 ①）。同一部署内 userId 全局唯一，配置全局生效 |
| 好友边 | 有向关系"A 把 B 加为好友"，存在 A 这一侧（`friends(owner=A, peer=B)`）。备注名存在边上 |
| 互为好友 | A→B、B→A 两条边都存在（且不是墓碑） |
| 陌生人 | 不互为好友的两个人 |
| 申请行 | 一条好友申请在申请人一侧存一行 `out`、在被申请人一侧存一行 `in`。**`in` 行是申请状态的唯一真相**（是否待处理、是否可以同意、是否自动通过都看它）；`out` 行只用于申请人自己的展示 |
| 操作 | 一次客户端命令或一次管理接口调用。一次操作可能改动多个用户的多行数据 |
| 关系版本号 `ver` | 每个用户一个整数，从 0 开始。一次操作只要改动了某用户的同步数据（好友边、申请行、黑名单行、隐私设置、`requestSeenVer`），就给**该用户**分配一个新 ver（原值 + 1），并写到该用户本次改动的**所有行**上。见 5.4 节、F-SOC-06 |
| 同步项 | `socialSync` 返回的一条数据：好友项（键 = 对方 userId）、申请项（键 = 对方 userId + 方向）、黑名单项（键 = 对方 userId） |
| 同步轮 | 从 `socialSync {sinceVer}` 开始、用游标翻页、直到 `hasMore=false` 的一组请求。每轮有固定的 `untilVer` |
| `purgedVer` | 每个用户一个：清理任务物理删除过的行中最大的 ver。客户端本地 ver 小于它时必须全量重建 |
| 墓碑 | 好友边、黑名单行删除时不物理删除，标记 `deleted` 并写新 ver；30 天后由清理任务删除 |
| 新对象 | 发私聊时，和我之间的单聊会话 `c2c:{小}:{大}` 还没有任何消息的人 |
| 静默失败 | 发给新对象的私聊被 4042、4035、4036 拒绝（消息不保存，对方无感知） |
| 官方账号 | 被业务方标记 `official=true` 的用户（F-SOC-13） |
| 自建群 / 托管群 | 客户端 `groupCreate` 建的群（ID 以 `ug-` 开头，有群主）/ 业务方 `POST /admin/groups` 建的群（默认没有群主）（M4） |
| 群提示消息（tip） | 服务端在群里生成的灰色提示，占用 seq 的消息，`type = "tip"`（M4） |
| 可见范围 | 一个用户能读取哪些人的资料（F-SOC-10） |

## 5. 通用约定

### 5.1 业务方可配置参数（F-SOC-01）

全部参数存在数据库 `app_settings`（key = `social`），管理接口可改（X-5 之后），没配置时用默认值。

| 参数 | 含义 | 默认 | 范围 | 里程碑 |
|---|---|---|---|---|
| `mode` | 好友模式 | `open` | `open` / `friends` | M3 |
| `strangerMsgLimit` | 开放模式下，陌生人在对方回复前最多发几条 | **0（关闭）**；推荐 3 | 0～100，0 = 不限制 | M3 |
| `newPeerHourlyLimit` | 每人每小时最多给几个新对象发私聊（两种模式都生效） | **0（关闭）**；推荐 30 | 0～1000，0 = 不限制 | M3 |
| `newPeerRejectDailyLimit` | 每人每天给新对象发私聊"静默失败"的次数上限；用完后给任何新对象发私聊都返回 4292（防枚举，F-SOC-08 规则 5） | 100 | 10～1000，**不能关闭** | M3 |
| `maxFriends` | 每人好友上限（自己这一侧的边数） | 2000 | 100～5000 | M3 |
| `maxBlocks` | 黑名单上限 | 1000 | 100～5000 | M3 |
| `requestExpireDays` | 好友申请有效期 | 7 | 1～30 | M3 |
| `applyDailyLimit` | 每人每天最多发几次好友申请（重复申请、发给不存在的人都算） | 30 | 1～500 | M3 |
| `applyPerTargetDailyLimit` | 每天对同一个人最多申请几次 | 3 | 1～10 | M3 |

| `searchableDefault` | 用户没设置过时是否可被搜索 | `true` | 布尔 | M3 |

### 5.2 限流与配额（复用 `ratelimit.Limiter`）

| 键 | 速率 | 超出 | 里程碑 |
|---|---|---|---|
| `friendApply:{uid}` | 每秒 1 个，突发 5 | 4290 | M3 |
| `friendApplyDay:{uid}`、`friendApplyDay:{uid}:{peer}` | `applyDailyLimit` / `applyPerTargetDailyLimit` 每天 | 4292 | M3 |
| `search:{uid}` | 每分钟 10 个，突发 10 | 4290 | M3 |
| `searchDay:{uid}` | `searchDailyLimit` 每天 | 4292 | M3 |
| `users:{uid}` | 每分钟 30 个，突发 10 | 4290 | M3 |
| `social:{uid}`（处理申请、删除、备注、拉黑、取消拉黑、隐私设置、标记已读） | 每秒 5 个，突发 20 | 4290 | M3 |
| `blockDay:{uid}`（拉黑、取消拉黑） | `blockDailyLimit` 每天 | 4292 | M3 |
| `socialFull:{uid}`（全量同步轮，在第一页计数，含服务端判定的全量） | 每分钟 10 轮，突发 5 | 4290 | M3 |
| `groupRead:{uid}`（`myGroups`；M4 起加 `groupInfo`、`groupMembers`） | 每秒 10 个，突发 30 | 4290 | M3 |
| `newPeerHour:{uid}` | `newPeerHourlyLimit` 每小时（为 0 时不检查） | 4292 | M3 |
| `newPeerReject:{uid}` | `newPeerRejectDailyLimit` 每天（只在静默失败时扣） | 4292 | M3 |
| `groupOp:{uid}`（邀请、移出、转让、设管理员、改资料、退群、解散） | 每秒 5 个，突发 20 | 4290 | M4 |
| `groupCreateDay:{uid}` | `groupCreateDailyLimit` 每天 | 4292 | M4 |

规则：
1. **一项限流 / 配额拒绝了请求，就不扣这一项的令牌**（C-29 原文）；判定顺序里排在它前面、已经通过的限流照常扣（例如 `send` 通过了发送限流、再被 `newPeerReject` 返回 4292，发送令牌已经扣了）。**通过了全部限流和配额检查、之后因业务原因失败的**（4042、4035、4036、4137、4132 等）照常扣。例外：`newPeerReject` 是预扣、成功退还（F-SOC-08 规则 5）。
2. "每天"按 `NewPer(24h/N, N)` 的令牌桶近似，"每小时"按 `NewPer(1h/N, N)`，不按自然日清零（避免零点集中）。
3. **参数修改立即生效**：`ratelimit` 增加 `Reconfigure(rate, burst)`，配置修改后对已有的桶立即生效——已有桶的剩余令牌截断到新容量、不清零（已用量保留）；调大时剩余令牌不自动补满，按新速率补充。
4. 一期为内存实现：进程重启后计数清零；多节点时每个节点各算一份（ARCH G2）。M3 是单节点，影响是"每次发版后配额重置"，作为已接受风险写入 11.3 节；集群化（B6）时换 Redis 令牌桶，每日配额带 TTL 持久化。
5. 所有配额都按用户计；官方账号（F-SOC-13）只豁免 `newPeerHour`，其余照常。

### 5.3 多错误时的优先级

所有新命令统一：帧 / 参数格式（4002、4004、4000）→ 限流 4290 / 配额 4292 → 资源存在性（4043、4045）→ 关系与权限（4033、4030、4035、4036、4046）→ 数量上限（413x）。

**用户是否存在不作为社交命令的独立判定步骤**（防枚举）：好友申请、拉黑、取消拉黑对不存在的用户照常成功；删除好友幂等成功；备注返回 4040（与"不是好友"相同）；建群 / 邀请返回 4035（与"不是好友"相同）。只有 `send` 保留 4042（D5，已冻结），其判定顺序见 F-SOC-08 规则 7。各命令的完整顺序写在各自的规则里，以规则为准。

### 5.4 版本号与事件：操作 × 谁的 ver 变化

总规则：
1. 一次操作给每个**有数据变化**的用户各分配**一个**新 ver（原值 + 1），该用户本次改动的所有行写同一个 ver。没有变化（幂等的重复操作、值没变的修改）不分配 ver。
2. **只有 ver 变化了的用户才收到 `socialChanged {ver}`**；发起操作的那个连接不收（从 ack 拿结果，F-SOC-06 规则 7）。
3. 被单向删除、被拒绝、被拉黑、被静默（拉黑期间的申请、发给不存在用户的申请）的一方，ver 不变，**收不到任何帧**。

下表是测试依据（R-SOC-01、R-SOC-06）。"A"为发起人，"B"为对方。

| # | 操作 | A 的 ver | A 本次改动的行（同一个 ver） | B 的 ver | B 本次改动的行（同一个 ver） | 收到 `socialChanged` |
|---|---|---|---|---|---|---|

| 2 | `friendApply`：B 不存在，或 B 拉黑了 A | +1 | A 的 out 行 | 不变 | — | A 的其他连接 |

## 6. 功能需求：好友、拉黑、通讯录、私聊（M3）

> 写法同 PRD-core 第 4 节：规则 → 验收标准。【后端】【前端】表示主要验证层，未标注的为端到端。
> AC 中的 alice、bob、carol、dave、eve、frank 都是已导入的用户，昵称与 userId 相同；`nobody` 是不存在的 userId。"好友制下"指 `mode=friends`，"开放模式下"指 `mode=open`；没有特别说明时其余配置为默认值。
> 标"B6 前置"的 AC 在 SQLite 上同样运行，但只有在 Postgres 上才有判别力（8.7 节），B6 上线前必须在 Postgres 上通过。

### F-SOC-01 社交模式与业务方配置（P0，M3）

**规则**
1. 配置粒度：**一个 im-server 部署一套配置**（S-4 ①）。yd / yi / tb 共用一个部署时共用同一套配置；需要不同的好友模式就分开部署。
2. 读写：管理接口 `GET / PATCH /admin/settings/social`，PATCH 只改传了的字段。上线条件见 F-SOC-12 规则 8（X-5 ②）。新部署的初始值也可以由启动配置 `IM_SOCIAL_DEFAULTS`（JSON，字段同 5.1 节）给出：**只在数据库里还没有 `social` 配置行时写入一次**，之后一律以数据库为准。
3. 生效：服务端缓存配置，修改后通过 `cache.Invalidator`（主题 `socialSettings`）通知所有节点，TTL 60 秒兜底。
4. 在线客户端：修改成功后给全部在线连接下发 `socialSettingsChanged {mode, strangerMsgLimit}`（尽力投递）；每一页 `socialSync` 应答头里也带这两项，所以每次重连都能拿到最新值。客户端只用它们做界面提示，**判定一律以服务端为准**。
5. 模式切换不改任何已有数据：`open → friends` 后，非好友之间的历史会话仍在会话列表里、可以拉历史，但不能再发（4035）；`friends → open` 后立即恢复。待处理的好友申请在两种模式下都有效，不受切换影响。
6. 陌生人条数按**累计**计算：每个单聊会话里每人已发条数（`sent_count`）一直维护，与开关无关。`strangerMsgLimit` 从 0 改为 3 时，已经发了 3 条以上、对方没回复过的会话立即受限。
7. 调低上限（`maxFriends`、`maxBlocks`）时，已有的关系全部保留，只拦截之后的新增，直到数量降到上限以下。（M4：`clientGroupMaxMembers` 只影响之后新建的群，已有群的上限在建群时固定。）
8. 非法配置（超出 5.1 节范围、未知字段、`mode` 不是两个值之一）返回 HTTP 400 / 4000，整次修改不生效。
9. 每次成功的 PATCH 写一条审计记录（F-SOC-12 规则 9）。

**验收标准**
- AC-SOC-01-1【后端】：新部署（没有 `IM_SOCIAL_DEFAULTS`）`GET /admin/settings/social` 返回 5.1 节的全部默认值，其中 `mode=open`、`strangerMsgLimit=0`、`newPeerHourlyLimit=0`、`newPeerRejectDailyLimit=100`。
- AC-SOC-01-2【后端】：`PATCH {"mode":"friends"}` 成功后 1 秒内，alice 给非好友 bob 发私聊返回 4035（不需要重启）。
- AC-SOC-01-3【后端】：`PATCH {"mode":"friends","maxFriends":99}` 返回 400 / 4000，再次 GET 时 `mode` 仍为 `open`；`PATCH {"strangerMsgLimit":-1}`、`PATCH {"foo":1}` 都返回 400 / 4000。
- AC-SOC-01-4【后端】：alice 和 bob 在开放模式下聊过 5 条，切到好友制后：alice 的 `convs` 仍有该会话，`sync` 能拉到 5 条，`send` 返回 4035；切回开放模式后 `send` 成功。
- AC-SOC-01-5【后端】：双节点测试环境（5.6 节）中，在节点 1 修改 `mode`，连在节点 2 的用户 1 秒内按新模式判定；节点 2 设置 `IM_TEST_INVALIDATION=off` 时，节点 2 的测试时钟推进 59 秒仍按旧模式判定，推进 61 秒后按新模式判定。
- AC-SOC-01-6：alice 的 web、pc 两个连接在线，业务方把 `strangerMsgLimit` 从 0 改为 3，两个连接 1 秒内都收到 `socialSettingsChanged {mode:"open", strangerMsgLimit:3}`，SDK 的 `socialSettings` 回调给出新值。
- AC-SOC-01-7【后端】：`strangerMsgLimit=0` 时 alice 给陌生人 bob 发了 5 条（bob 没回复）；改为 3 后，alice 再发一条返回 4137（累计口径）。
- AC-SOC-01-8【后端】：alice 有 150 个好友时把 `maxFriends` 改为 100：alice 的 150 个好友都保留、都能正常私聊；alice 同意一条新申请返回 4132；删除 51 个好友（剩 99）后可以再同意 1 个。
- AC-SOC-01-9【后端】：用 `IM_SOCIAL_DEFAULTS={"mode":"friends"}` 启动的新部署，GET 返回 `mode=friends`；之后 PATCH 改为 `open` 并用同样的启动配置重启，GET 仍为 `open`。

### F-SOC-02 发送好友申请（P0，M3）

**规则**
1. 命令 `friendApply {to, message?, source?, sourceRef?, remark?}`：
   - `message`：附言 0～50 码点（去首尾空白后）；`remark`：同意后我给对方的预设备注名 0～32 码点。
   - `source`：`search`、`group`、`card`（名片 / 资料卡）、`conv`（单聊会话）、`other`，默认 `other`。`source=group` 时必须带 `sourceRef=groupId`。被申请人一侧（in 行）记录**校验后的**来源：服务端校验双方都在这个群里，不满足时记为 `other`（不报错）；申请人一侧（out 行）**原样记录请求值**（不把校验结果透露给申请人）。
2. **判定顺序**（按顺序匹配，第一条命中即返回）：

   | # | 条件 | 结果 |
   |---|---|---|
   | 1 | 格式：`to` 不合法 4004；`to` 是自己、附言 / 备注超长、未知字段 4000 | 错误 |
   | 2 | 限流 `friendApply` 4290；配额 `friendApplyDay`、`friendApplyDay:{peer}` 4292 | 错误，不扣令牌 |
   | 3 | 我把对方拉黑了 | 4000（客户端应先取消拉黑；H5 对已拉黑的人不显示"添加到通讯录"） |
   | 4 | 已互为好友 | `accepted`，不改数据（`changed=false`） |
   | 5 | 我的好友已满 | 4132 |
   | 6 | **对方不存在，或对方把我拉黑了** | `pending`：只新建 / 合并**我的 out 行**，对方什么都不写、收不到任何帧；应答与第 9 行**逐字段同构** |
   | 7 | 对方仍有我的边（我之前单向删了对方） | 恢复我的边，`accepted`；对方无感知（同微信） |
   | 8 | 我这一侧有一条来自对方的、**未过期**的 in 行（`pending` 或 `rejected`） | **自动成为好友**：对方好友已满 4133（不改数据）；否则建立双向边，双方之间所有申请行置 `accepted`，`accepted` |
   | 9 | 其他 | 新建或合并申请：我的 out 行 + 对方的 in 行，`pending` |

   第 4、5 行在第 6 行之前：两者只依赖我自己的数据，不会因为对方是否存在而不同。第 8 行要求对方给我发过申请，因此 4133 不会泄露任何新信息。
3. **重复申请合并**：同一申请人对同一人只有一对申请行。再次申请时：附言、来源、预设备注更新为最新一次，`expireAt` 重新计算，`applyCount` +1，in 行写新 ver（对方的"新的朋友"里移到最前、重新计入红点，F-SOC-04）。被拒绝或过期后再次申请，同样复用这一对，状态回到 `pending`。第 6 行的情况只合并我的 out 行。
4. 有效期：`expireAt = 最后一次申请时间 + requestExpireDays`。过期在读取时按服务端时间判定（状态显示为 `expired`），不需要定时任务，也不改变 ver。
5. ver 与事件按 5.4 节第 1～5 行。
6. ack：`{status, ver, changed, items}`，`status` 为 `pending` / `accepted`，`items` 是我本次改动的全部行（F-SOC-06 规则 7）。out 行在被同意之前**不带对方资料**（F-SOC-06 规则 9），因此第 6 行与第 9 行的应答在字段和取值上无法区分（ver、时间戳除外）。
7. 日志不记录附言和备注原文，只记录长度；`protocol.Errorf` 的 `msg` 里不拼入任何用户输入。

### F-SOC-03 处理好友申请（P0，M3）

### F-SOC-06 关系同步：好友列表、多端同步、离线补拉（P0，M3）

**规则**
1. **版本号**：每个用户一个 `ver`，存在 `user_social`，从 0 开始。一次操作（5.4 节）只要改动了该用户的同步数据，就在同一个事务里、持有该用户的锁时（8.3 节）执行一次 `UPDATE user_social SET ver = ver + 1 … RETURNING ver`，并把这个值写到该用户**本次改动的所有行**上。因此：每个操作对每个用户最多分配一个 ver；同一操作的行共享一个 ver；不同操作的行 ver 不同；ver 严格递增、没有空洞（每个 ver 都对应一次操作，但可能没有行，如 5.4 节第 15、16 行）。
2. **同步项与排序**：好友项（键 = 对方 userId）、申请项（键 = 对方 userId + 方向）、黑名单项（键 = 对方 userId）。统一按**排序键 `(ver, 类型, 对方 userId, 方向)`** 排序，类型顺序为 好友 < 申请 < 黑名单。好友边、黑名单删除时写墓碑（`deleted=true`，新 ver）；申请行没有墓碑，只改状态，30 天后被清理。
3. **同步轮**：第一页 `socialSync {sinceVer, limit?}`，之后 `socialSync {cursor, limit?}`，直到 `hasMore=false`。
   - 第一页在一个读事务里读出当前 ver（记为 V）和 `purgedVer`（记为 P）。`0 < sinceVer ≤ V` 且 `sinceVer ≥ P` 时为**增量轮**；`sinceVer = 0`、`sinceVer < P`、`sinceVer > V` 时为**全量轮**（`full=true`）。
   - 本轮的 `untilVer = V`，写在游标里，整轮不变。
   - 增量轮返回 `sinceVer < ver ≤ untilVer` 的全部同步项（含墓碑）；全量轮返回 `ver ≤ untilVer`、不是墓碑、申请 `updatedAt` 在 30 天内的全部同步项。两者都按排序键升序，每页最多 `limit` 项。
   - 游标是不透明字符串，编码 `{轮类型, sinceVer, untilVer, 本页最后一项的排序键}`；下一页从排序键**严格大于**它的项开始。因此同一个 ver 的多行可以跨页，但不会被跳过或重复。
   - 本轮进行期间发生的变化会得到大于 `untilVer` 的 ver，不进入本轮，由下一轮增量（从 `untilVer` 开始）拿到。这就是 `untilVer` 必须固定的原因。
   - 增量轮的后续页如果发现当前 `purgedVer > sinceVer`（清理任务在本轮中途执行过），返回 `restart=true`、不带数据；客户端放弃本轮，用**同一个 `sinceVer`** 重新开始，服务端按第一页规则判定为全量。
   - 游标格式非法、属于其他用户，返回 4000；`sinceVer` 和 `cursor` 同时传或都不传，返回 4000。游标本身不过期。
4. **每页应答**：`{full, untilVer, latestVer, hasMore, cursor, restart?, friends, requests, blocks, requestSeenVer, settings: {searchable}, mode, strangerMsgLimit, official}`。`latestVer` 是读这一页时的当前 ver；`official` 是我自己是否为官方账号。
5. **清理任务**（每小时一次，只在一个节点上跑；测试接口可立即触发）：按用户、在持有该用户锁的事务里，物理删除 `updatedAt` 早于 30 天的墓碑和申请行，并把该用户的 `purgedVer` 设为 `max(purgedVer, 被删行的最大 ver)`。清理不分配 ver、不发事件。
   - 正确性：本地 ver ≥ `purgedVer` 的客户端已经收到过这些行的最终状态（墓碑已应用；申请按规则 10.2 节在本地同样按 30 天丢弃），不需要处理；本地 ver < `purgedVer` 的客户端可能错过了被删的墓碑，下一轮被判定为全量重建。
6. **实时提醒**：事件 `socialChanged {ver}` 只发给 ver 变化了的用户，并排除发起操作的连接（5.4 节）。投递尽力而为；SDK 收到后若 `ver > 本地 ver`，200ms 去抖后开始一轮同步。正确性不依赖事件（ARCH 2.2 约束 4）。
7. **修改类命令的 ack**：`{ver, changed, items: {friends, requests, blocks}}`。`changed=true` 时 `ver` 是本次为我分配的新 ver，`items` 是我本次改动的**全部**行（都带这个 ver）；`changed=false` 时 `ver` 是当前 ver、`items` 为空。SDK：`changed=true` 且 `ver = 本地 ver + 1` 时应用 `items` 并把本地 ver 设为 `ver`；`changed=true` 且 `ver > 本地 ver + 1`（中间有别的变化）时先应用 `items`（按键保留 ver 较大的一项），再从本地 ver 开始一轮同步；`changed=false` 时不处理。
8. **客户端应用规则**：增量轮的数据可以逐页应用（同一个键只保留 ver 最大的一项，墓碑表示删除，重复应用无副作用）；全量轮收齐所有页后**整体替换**本地数据。轮结束时把本地 ver 设为 `untilVer`；若最后一页的 `latestVer > untilVer`，或期间收到了 `ver > untilVer` 的 `socialChanged`，立即从 `untilVer` 开始下一轮。
9. **资料**：每一项带 `profile {nickname, avatar, official}`（应答时的最新值），规则如下，昵称头像变化**不改变** ver：
   - 好友项、in 申请项：带资料。
   - out 申请项：**只有状态为 `accepted` 时带资料**，其余为 null（防止通过申请读取不可被搜索的用户的资料，R-SOC-02）。
   - 黑名单项：对方在我的可见范围内（F-SOC-10 规则 2，拉黑本身不算）时带资料，否则为 null。
10. SDK 每次连接成功（含重连）：先 `convs`，再从本地 ver 开始一轮同步。sdk-ts 只在内存（D4），**H5 每次刷新页面都是全量轮**；原生 SDK 持久化时 ver 与数据必须在同一个本地事务里写入（10.2 节）。

### F-SOC-07 拉黑与黑名单（P0，M3）

**规则**
1. `block {userId}` / `unblock {userId}`；黑名单在 `socialSync` 的 `blocks` 里，多端同步。
2. 拉黑**不改变好友关系**（同微信）：好友列表里对方仍在，界面标记"已拉黑"。
3. A 拉黑 B 之后：
   | B 的操作 | 结果 |
   |---|---|
   | 给 A 发私聊 | 4036（"消息已发出，但被对方拒收了"），消息不保存、A 收不到 |
   | 给 A 发好友申请 | 假装成功（F-SOC-02 规则 2 第 6 行） |
   | 邀请 A 进群、建群时拉 A（M4） | 与"A 不是 B 的好友"相同，返回 4035（R-SOC-10，不单独暴露拉黑） |
   | 搜索 A、查 A 的资料 | 照常（不暴露拉黑） |
   | 在共同的群里发言 | 照常，A 照常收到（**群里拉黑不生效**） |

   A 自己给 B 发私聊不受影响（开放模式下照常；好友制下仍要求互为好友）。
4. 拉黑时，A 一侧来自 B 的 `pending` in 行自动变为 `rejected`（同一个 ver）；B 的 out 行不变，B 无感知。取消拉黑不恢复任何东西。
5. **不暴露对方是否存在**：拉黑 / 取消拉黑不存在的用户照常成功（写入黑名单行，计入 `maxBlocks` 和 `blockDailyLimit`），应答与拉黑存在的用户同构；黑名单项的资料按 F-SOC-06 规则 9，不在可见范围内的一律为 null。
6. 不能拉黑自己（4000）；黑名单满 4134；重复拉黑、取消一个不在黑名单的人都是幂等成功（`changed=false`）；拉黑 + 取消拉黑每天合计 `blockDailyLimit` 次（4292）。
7. 生效时点：拉黑的 ack 返回之后**才开始**的发送一定被拒（8.3 节 L7）。

**验收标准**
- AC-SOC-07-1：alice 拉黑 bob 后，bob 给 alice 发私聊返回 4036，alice 的所有连接都没有收到消息，alice `sync` 该会话也没有这条；bob 的 SDK 把消息标记失败，提示"消息已发出，但被对方拒收了"。

### F-SOC-08 私聊权限（P0，M3）

**规则**
1. 每次 `send`（单聊）时实时判定，不缓存判定结果（第 12 节）。给自己发消息永远允许，不计入任何新对象配额。
2. **好友制**：双方必须互为好友，否则 4035。任一方是官方账号时豁免（F-SOC-13）。
3. **拉黑（两种模式都生效）**：对方把我拉黑，4036。官方账号同样受此约束。
4. **开放模式的陌生人限额**（`strangerMsgLimit > 0` 时才生效，默认 0 = 关闭）：不互为好友、任一方都不是官方账号、对方**从未在这个会话里发过消息**（对方的 `sent_count = 0`）、我在这个会话里已发 `sent_count ≥ strangerMsgLimit` 时，返回 4137；对方回复过一条之后永久解除（即使之后又变回陌生人）。该判断在 `SaveMessage` 的事务内、持有会话 seq 锁之后执行（8.3 节 L6），并发发送不会超出；被拒绝时不占用 seq。被 4036、4137 拒绝的消息不计入 `sent_count`。
5. **新对象配额**（只对新对象生效，即和我之间的单聊会话还没有任何消息的人；两项都在**存在性判断之前**检查）：
   - a. **`newPeerReject`（防枚举，默认每天 100 次，不能关闭）**：令牌用完时，给任何新对象发私聊都返回 4292（无论对方是否存在）。**先扣后退**：给新对象发私聊时先原子地扣 1 个令牌（扣不到就返回 4292），消息成功保存后退还；被 4042、4035、4036 拒绝（静默失败）时不退。这样同一用户 10 个连接并行探测时，在途请求也各自占用一个令牌，不会出现"都通过检查、事后只扣到一个"（复审 N-01）。正常用户几乎不会触发；探测者每天最多做 100 次"对方无感知"的探测。需要 `ratelimit.Limiter` 增加"预扣 + 退还"接口（TokenBucket 实现 `Take` / `Refund`，分布式实现同样原子）。
   - b. **`newPeerHour`（防骚扰，`newPeerHourlyLimit > 0` 时才生效，默认关闭）**：令牌用完时返回 4292；通过检查的每次发送都扣 1 个（无论结果）。官方账号作为发送方时豁免。
6. 历史会话：权限只影响**发送**；`sync`、`read`、`convs` 的规则不变（PRD-core F-MSG-05 规则 4）。删除好友、被拉黑、模式切换之后，会话仍在列表里。
7. **判定顺序**（变更 PRD-core F-MSG-01，13.1 节 V-03）：
   1. 格式（4002～4008；M4 起 `clientMsgId` 以 `tip-` 开头返回 4000）
   2. 去重命中 → 直接返回第一次的 ack（已经保存的消息重发一律成功，不受之后关系变化影响）
   3. 发送限流 4290（扣令牌，C-29）
   4. 对方是新对象时：预扣 `newPeerReject` 1 个令牌，扣不到 → 4292（消息保存成功后退还，见规则 5a）
   5. 对方是新对象、`newPeerHourlyLimit > 0`、我不是官方账号时：`newPeerHour` 令牌已用完 → 4292，否则扣 1
   6. 对方不存在 → 4042（D5）
   7. 好友制下不互为好友（且双方都不是官方账号）→ 4035
   8. 对方拉黑了我 → 4036
   9. （`SaveMessage` 事务内）陌生人限额 → 4137
   10. 保存并投递

   第 6～8 步拒绝且对方是新对象时扣 1 个 `newPeerReject` 令牌。被 4042、4035、4036、4137 拒绝的消息都扣过第 3 步的发送令牌（C-29 现有行为：通过限流之后才失败）。
8. 对方不存在沿用 4042（D5）。用户注销一期不存在（F-USER-01 规则 4）；被封禁的用户照常可以接收消息（X-8）。
9. 客户端文案**按"命令 + 错误码"映射**（9.4 节）。`send` 收到 4035：消息标记失败，聊天页插入"对方开启了好友验证，你还不是他的好友"和"发送好友申请"入口；4036："消息已发出，但被对方拒收了"；4137："对方回复之前，最多只能发送 N 条消息"（N 取最近一次同步 / 事件中的 `strangerMsgLimit`）；4292："今天发起新聊天的次数已用完，请稍后再试"。都不自动重发。

### F-SOC-09 用户搜索与"可被搜索"开关（P0，M3）

**规则**
1. `userSearch {keyword}`：去首尾空白后必须是合法 userId（4004），**只做精确匹配**，不做前缀、模糊匹配。
2. 返回 `{user: {userId, nickname, avatar, official, relation} | null}`。`relation` 与 SDK 的 `relationOf` 共用一个枚举，按优先级取第一个满足的：`self`、`blocked`（我拉黑了对方）、`friend`（我这一侧有边）、`pendingIn`、`pendingOut`、`none`。不暴露"对方是否拉黑了我""对方是否加了我"。
3. 返回 `null` 的情况：用户不存在；对方关闭了"可被搜索"；对方被封禁（规则 7）。几种情况的应答**完全相同**，并且走**同样的查询路径**（每次都查用户、隐私设置和关系，再统一判断，避免响应时间可区分）。搜索自己总能返回。
4. `setPrivacy {searchable}`：个人开关，默认跟随 `searchableDefault`；多端同步（5.4 节第 15 行）。关闭后只是不能被搜到；其他路径本来就不暴露存在性（11.2 节）。好友、同群成员、单聊对象仍可以通过资料卡看到他（F-SOC-10）。

### F-SOC-12 业务方管理好友关系（P0，M3，依赖 X-5）

**规则**
1. 导入：`POST /admin/friends/import {pairs: [{a, b, remarkA?, remarkB?}]}`，单次 ≤ 500 对；每一对建立**双向**好友边，来源 `admin`。
2. 幂等：已经是好友的对不变；传了备注且**值与现有不同**时更新备注（算变化，分配 ver），值相同不算变化；同一请求里重复的对按最后一条为准；`a == b` 返回 4000。
3. 整批原子：任意一对不合法、任一用户不存在、任一用户导入后超过 `maxFriends`（`msg` 中写出 userId），整批不生效。错误优先级：4004 → 4000 → 4131 → 4042 → 4132。（管理接口是可信调用方，可以返回 4042。）
4. 删除：`DELETE /admin/friends {pairs: [{a, b}]}`，单次 ≤ 500 对，删除**双向**的边（墓碑）；不是好友的忽略。
5. 查询：`GET /admin/users/{userId}/friends?cursor=&limit=`（limit 1～500，默认 100），按对方 userId 升序，游标翻页；每项 `{userId, source, createdAt}`，**不返回备注**（备注只有本人可见）。

7. 导入不受拉黑影响（业务方的决定优先），但不解除拉黑。
8. **上线条件**（S-11 ②；X-5 ②）：本 PRD 的全部社交管理接口（F-SOC-01 配置、本功能点、F-SOC-13 官方账号标记、M4 的群主交接）只注册在 X-5 的独立内网管理端口上，按调用方密钥的 scope 判定（`social.settings`、`social.friends`）。**X-5 落地之前，这些接口只在 `IM_TEST_MODE=1` 时注册**（供 e2e 使用），生产部署用 `IM_SOCIAL_DEFAULTS` 设定好友模式，不能导入好友、不能标记官方账号。

### F-SOC-21 客户端建群（P0，M4）

**规则**
1. `groupCreate {clientReqId, name?, members}`：`clientReqId` 8～64 位（同 clientMsgId 的规则）。**只记录成功的建群**：同一用户用同一个 `clientReqId` 重复提交，返回第一次成功的结果（不重复建群）；失败不记录，重试时重新判定。去重记录保留 7 天（`created_at` 索引）。
2. `members` 不含自己（含自己时忽略），去重后**至少 2 人**，总人数（含自己）≤ `clientGroupMaxMembers`（超出 4130）。
3. 每个被邀请人必须**存在、和我互为好友、没有拉黑我**，否则返回 4035（三种情况同码，不暴露拉黑和存在性，R-SOC-10）；被邀请人加入的群数达到 `maxJoinedGroups` 返回 4135。**任一人不满足时整个建群失败**，错误里带 `userId`（9.2 节）。我自己的群数已满返回 4135；`clientGroupEnabled=false` 返回 4030。
4. `maxJoinedGroups` 是**软上限**：按该用户当前加入的全部群（含业务方拉入的）计数，只在客户端建群 / 邀请时用 `count(*)` 检查（依赖 `group_members(user_id)` 索引），并发时可能少量超出，接受。
5. groupId 由服务端生成：`ug-` + UUIDv7 去掉连字符（35 个字符）。**`ug-` 前缀保留给自建群**：业务方 `POST /admin/groups` 使用这个前缀返回 4004（变更 ADMIN.md）。0005 迁移前检查已有群 ID，发现 `ug-` 开头的就中止迁移并列出（8.5 节）。
6. `name` 可选：不传时用前 3 个成员（含自己，按 `members` 顺序）的**昵称（没有昵称用 userId，绝不用备注）**，以"、"连接，超过 50 码点截断；建群时生成，之后不自动变化。
7. 建群者为群主；`historyVisible=false`（客户端一期不能修改）；`max_members` 固定为建群时的 `clientGroupMaxMembers`。
8. 成功：ack 返回 `{groupId, conv}`（`conv` 与 `convs` 中的一项相同）；被邀请人和建群者的其他在线连接收到 `convAdded`；群里生成一条 `created` 提示消息，与建群在同一个事务里（seq=1）。
9. 每天最多建 `groupCreateDailyLimit` 个群（4292）。

### F-SOC-23 退群（P0，M4）

**规则**
1. `groupLeave {groupId}`：任何成员都可以退出，包括托管群。
2. 退群后同"被移除"：不能再发、拉、读（4033），`convs` 和 `myGroups` 中不再出现；本人其他在线连接收到 `convRemoved {reason: "left"}`；成员缓存失效。
3. **不生成群提示消息**（同微信：退群不通知全体成员）；在线成员收到 `groupChanged`（合并发送）。
4. **群主退群**：
   - 自建群：自动转让给最早成为管理员的管理员（按 `role_at`，相同时按 userId）；没有管理员时给最早入群的成员（按入群时间，相同时按 userId）；生成 `ownerChanged` 提示消息（`from=""`，`targets=[新群主]`）。
   - 托管群（业务方指定的群主）：**回到"无群主"的托管状态**（R-SOC-19），不转让给任何成员；生成 `ownerChanged` 提示消息（`from=""`，`targets=[]`，客户端显示"群主已退出群聊"），由业务方重新指定。
5. **最后一个人退群**：
   - 自建群：群自动解散（按 F-SOC-26 处理，同一个事务）。X-6 ②、S-10 已拍板：解散群提前，`DissolveGroup` 在 M3 随管理接口交付，M4 的自建群直接复用。
   - 托管群：**保留为空群**（PRD-core AC-GRP-02-3 不变，业务方可以之后再加人）。
6. 不是成员时返回 4033（不是幂等成功：避免客户端误以为退了一个从来不在的群）。

### F-SOC-26 解散群（P0；存储方法、管理接口、`convRemoved.reason` 为 M3，客户端 `groupDissolve` 为 M4）

### F-SOC-29 群提示消息（tip）（P0，M4）

**规则**
1. 新消息类型 `type = "tip"`：服务端生成，占用 seq，和普通消息一起 `sync`、补拉、去重。`clientMsgId` 由服务端生成，格式 `tip-{UUIDv7}`；**客户端的 `clientMsgId` 不能以 `tip-` 开头**（4000，13.1 节 V-05），避免与服务端生成的去重键冲突。客户端不能发送 `type=tip`（4000）。
2. `body = {tip: {kind, actor, targets, count?, text}}`；`kind`：`created`、`joined`、`ownerChanged`、`adminSet`、`adminUnset`、`renamed`、`noticeUpdated`。`from` 为操作人 userId；系统操作（自动转让、托管群回到无群主、业务方指定 / 收回群主）`from = ""`。Schema 中 `Message.from` 和 `LastMsg.from` 只在 `type=tip` 时允许为空（9.2 节）。
3. **生成提示消息的操作**：客户端建群、客户端邀请、转让群主（含自动转让、托管群回到无群主、业务方指定 / 收回群主）、设置 / 取消管理员、客户端改群名、客户端改公告。**不生成**：退群、移出、解散、管理接口的建群 / 加减成员 / 改名 / 改 `historyVisible`。
4. **与对应的修改在同一个事务里落库**（同一次 seq 分配）：Store 的群管理方法带提示消息参数，任何一步失败整体回滚，不会出现"成员加了、提示消息没有"。
5. 已读位置：`from` 为操作人的提示消息，与"发言即已读"一致，推进操作人自己的 `readSeq`，并按现有规则给操作人的其他连接发 `readUpdated`（`sqlite.go` 第 160～166 行的同一路径）；`from = ""` 的提示消息不推进任何人的已读位置。
6. 计入未读（C-02 的公式不变：提示消息占用 seq）；出现在 `lastMsg`，摘要由服务端按 5.5 节生成（只用昵称，如"bob 邀请 dave 加入了群聊"）。不计入未读放 P1。
7. 客户端邀请一次最多 50 人，`targets` 最多 20 个 userId，超过时另带 `count`（总人数）。
8. 不认识的 `kind` 显示为"[群通知]"；不认识的 `type` 沿用 PRD-ui 的"[暂不支持的消息类型]"。
9. 客户端用 `actor`、`targets` 和本地资料渲染个性化文案（"你邀请了……"，可以使用本机的备注）；服务端摘要只用于 `lastMsg` 和不认识的情况。

**验收标准**

### 8.3 并发与加锁（Postgres 上的规则；SQLite 单连接下自然满足）

**全局加锁顺序**（任何事务都只能按这个顺序加锁，从而不会死锁）：
1. `chat_groups` 行，按 groupId 字节序升序（`SELECT … FOR UPDATE`）；
2. `user_social` 行，按 userId 字节序升序（行不存在时先 `INSERT … ON CONFLICT DO NOTHING`，再 `SELECT … FOR UPDATE`）；
3. `conv_seq` 行（现有的 seq 分配，`SaveMessage` 内）；
4. 其余行（`friends`、`friend_requests`、`blocks`、`user_conv`、`group_members`、`messages`）只在持有上面对应的"所有者锁"时修改，本身不作为加锁顺序的一部分。

| # | 规则 | 保证的性质 |
|---|---|---|
| L1 | 修改用户 U 的任何同步数据（好友边、申请行、黑名单、`user_social` 计数）之前，必须先持有 U 的 `user_social` 行锁；ver 分配（`UPDATE user_social SET ver = ver + 1 … RETURNING ver`）在持有锁时进行，每个操作对每个用户只执行一次 | ver 严格递增、每操作一个；同一用户的关系修改串行化 |
| L2 | 涉及两个用户的操作（`friendApply`、`friendRespond`）**在做任何判定之前**按 userId 字节序锁住双方的 `user_social` 行；F-SOC-02 规则 2 的判定表在持锁之后读取。对方不存在时只锁自己，不为不存在的用户创建 `user_social` 行 | **互相申请自动通过的原子性**：A→B 与 B→A 并发时在同一对锁上串行，后到的一方一定看到先到一方写的 in 行，走第 8 行"自动成为好友" |
| L3 | 好友上限：`friend_count` 与好友边在同一事务里维护；4132 / 4133 读取的是已加锁的双方计数。管理接口批量导入 / 删除：先收集全部涉及的用户、去重、按字节序**一次性**加锁（最多 1000 行），再逐对处理 | **好友上限原子**：并发同意、并发导入都不会突破上限 |
| L4 | 只涉及自己的操作（删除、备注、拉黑、取消拉黑、隐私、标记已读）只锁自己。拉黑把对方发来的 in 行置为 `rejected`，该行属于自己，不需要对方的锁 | 不产生跨用户锁，减少争用 |
| L5 | 群操作（M4 的全部 `group*`、管理接口的加减成员 / 改设置 / 解散）先锁 `chat_groups` 行，再做权限、人数、群主、`dissolved_at` 判断和修改；带提示消息的操作随后在同一事务里分配 seq（顺序 1 → 3）。群操作不锁用户行：好友关系、拉黑是只读判断；`maxJoinedGroups` 是软上限（F-SOC-21 规则 4） | `member_count` 准确；退群与转让、最后两人同时退群、邀请与解散都串行化 |
| L6 | **陌生人限额**在 `SaveMessage` 事务内、持有会话 `conv_seq` 行锁之后判断：读取双方在该会话的 `sent_count`，满足 F-SOC-08 规则 4 的拒绝条件就回滚（不占用 seq），否则分配 seq、写消息、`sent_count + 1` | **陌生人计数原子**：同一会话的发送本来就在 `conv_seq` 锁上串行，两个连接并发发送不会超出 N |
| L7 | 发送路径的关系判断（好友边、拉黑、官方账号、模式）是普通读、不加锁，在 `SaveMessage` 之前执行 | 保证"拉黑 / 删除好友 / 模式切换提交之后**才开始**的发送一定按新关系判定"；与之重叠的一次发送可能按旧关系通过，接受（与 PRD-core 的投递语义一致） |
| L8 | 隔离级别：Postgres 用 `READ COMMITTED` + 上述显式行锁；SQLite 现在是单连接（`sqlite.go` 第 50 行 `SetMaxOpenConns(1)`），全部事务天然串行 | 两种实现行为一致 |
| L9 | Postgres 设 `lock_timeout = 2s`，超时返回 5030（可重试）。按全局顺序加锁不应出现死锁；一旦检测到死锁按缺陷处理（记日志和指标 `store_deadlock_total`） | 可观测 |

### 8.4 分片方案（ARCH 3.6 第 4 步，不在 M3 / M4 / B6 范围，记入 ARCH 差距）

v0.1 写的"按用户各自写入 + 幂等重试、不需要跨分片事务"与好友上限、互相申请自动通过的原子性矛盾（R-SOC-04 ③），改为：
1. **一对用户一条权威记录**：`friend_pairs(lo, hi)`（lo < hi 按字节序）存在 `shard(lo)` 上，保存这一对之间两个方向的申请状态和两条边的权威状态。申请、同意、自动通过、删除都先在这条记录上原子决定——**互相申请自动通过只涉及一个分片**。
2. **关系行双写**：每个用户自己分片上的 `friends`、`friend_requests`、`blocks` 行是权威记录的副本，由同一操作通过 outbox 写到两个用户各自的分片，按"操作 ID"幂等；每个用户的 ver 在其所在分片应用副本时分配（仍是"每操作一个"）。副本写入失败由 outbox 重放，最终一致；`socialSync` 读副本。
3. **好友上限**：在每个用户的分片上做条件预留（`friend_count + reserved < max` 时预留 1），预留成功后再提交权威记录、最后确认；任一步失败补偿释放预留。上限严格不超；代价是短时间内可能因为未确认的预留误报 4132。
4. 陌生人限额按会话分片（同 `conv_seq`），不受影响；群仍按 groupId 分片，"我的群"需要按用户冗余一份二级索引。
5. 单库阶段（M3 / M4 的 SQLite、B6 的 Postgres）不需要以上机制，按 8.3 节的事务和锁实现即可；契约测试的断言（上限不超、自动通过、ver 连续）对分片实现同样适用。

### 8.5 发布、回滚与计数器修复

1. **停机升级**：0004 / 0005 不支持新旧二进制混跑。发布步骤：停止所有节点 → 按 ARCH 3.4 备份数据库 → `migrate up` → 启动新版本。M3 是单节点，停机时间为分钟级。
2. **回滚 = 恢复升级前的备份**。不提供 `migrate down`（删列 / 删表同样会丢数据，而且旧二进制起不来的问题只能靠恢复备份解决）。数据损失范围：升级之后的全部写入（消息、关系、群）。因此 M3 / M4 发布后先在演示环境运行 24 小时再接入真实业务方。
3. **计数器修复**：新增 `im-server repair counters`，按基础表重新计算 `user_social.friend_count / block_count`、`chat_groups.member_count`、`user_conv.sent_count`，幂等，可以在线执行（逐行持锁修复）。恢复备份后、契约检查发现漂移时运行。测试模式下启动时抽样校验计数器，发现不一致记 ERROR 日志。
4. **0005 迁移前检查**：已有群 ID 以 `ug-` 开头时迁移中止，列出这些群 ID，由运维处理后再升级。

### 11.2 存在性探测预算（安全用例的依据）

"确认存在"指：调用方能从应答（或其中的资料）区分"该 userId 存在"和"不存在"。

| 路径 | 能否确认存在 | 对方是否有感知 | 每个账号每天的上限 | 依据 / 用例 |
|---|---|---|---|---|
| `send` 给新对象，被拒（4042 / 4035 / 4036） | 能 | 无 | `newPeerRejectDailyLimit`（默认 100），在存在性判断之前执行，用完后对任何新对象都返回 4292 | F-SOC-08 规则 5；AC-SOC-08-10、08-11 |
| `send` 给新对象，成功（开放模式） | 能 | **有**：对方收到真实消息，可以拉黑 | 不限（开放模式"任何人都能私聊"的本义）；业务方可打开 `newPeerHourlyLimit` | 11.3 节已接受风险 |
| `userSearch` | 只对可被搜索的用户能 | 无 | `searchDailyLimit`（默认 100）；不可被搜索的与不存在的应答相同 | F-SOC-09；AC-SOC-09-3、09-9 |
| `friendApply` | 不能（不存在 / 拉黑了我 / 正常都返回同构的 `pending`，out 行不带资料） | 不存在、拉黑时无；正常时对方收到申请 | 0 | AC-SOC-02-4、02-6 |
| `block` / `unblock` | 不能（都成功，黑名单项资料按可见范围） | 无 | 0 | AC-SOC-07-9 |
| `users` | 不能（不可见与不存在都不返回） | 无 | 0 | AC-SOC-10-1、10-5、10-6 |
| `friendRemark` / `friendDelete` / `friendRespond` | 不能（4040 / 幂等成功 / 4045 统一） | 无 | 0 | AC-SOC-05-3、05-5、03-6 |
| `groupCreate` / `groupInvite`（M4） | 不能（不存在 / 不是好友 / 拉黑了我都是 4035） | 无 | 0 | AC-SOC-21-5、22-2 |
| 管理接口 | 能（可信调用方） | — | 不限，经 X-5 鉴权并审计 | F-SOC-12 |

结论：一个账号在对方无感知的前提下，每天最多确认 100（私聊被拒）+ 100（搜索，仅限可被搜索的用户）个 userId 的存在性；对不可被搜索的用户，只有私聊被拒这一条路径，每天最多 100 个，且拿不到资料（1.3 节指标）。

### 11.3 已接受的风险

| 风险 | 说明 | 何时处理 |
|---|---|---|
| 配额在内存里 | 进程重启后清零，每次发版配额重置；多节点时乘以节点数 | B6 集群化时迁到 Redis（ARCH G2） |
| 开放模式下发真实消息即可确认存在、并因建立会话获得对方资料 | 对方收到消息、可以拉黑；受发送限流约束；需要防骚扰的业务方打开 `newPeerHourlyLimit` 或改用好友制（R-SOC-26） | 业务方配置 |
| 发送路径的关系判断不加锁 | 与拉黑 / 删除并发的一次发送可能按旧关系通过 | 不处理（8.3 节 L7） |
| `maxJoinedGroups` 软上限 | 并发建群 / 邀请时可能少量超出 | 不处理 |
| 分片后好友上限可能误报 | 未确认的预留导致短时间内误报 4132 | 分片时（8.4 节） |
