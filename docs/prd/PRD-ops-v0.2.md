## 0. 本版要点（相对 v0.1）

1. **后端改为 `console-server`**（X-1）：不再有独立的 `ops-server`。运维后台与管理后台共用一个后台服务进程，按"账号空间"和域名分开。
2. **账号、会话、重新验证、审计全部以公共基座为准**（X-2、X-4）。本 PRD 只写运维专属的角色、权限，以及运维侧对基座的需求清单（第 4 节 B-OPS-01～15），便于之后与 PRD-admin v0.2 逐条核对。
3. **节点运维接口的凭证**改为：每个节点一把独立的 Ed25519 私钥（节点只存公钥）+ 请求签名（与 X-5 管理接口同一实现，PRD-admin F-KEY-03）+ TLS + 节点侧来源网段白名单；控制台只向静态配置并通过 TLS 身份校验的节点发请求（F-OPS-16）。
4. **握手阶段被拒也计入断开指标和断开记录**（4401、4009、4010～4012、1011）；签名有效的（4011、4012、1011）按 userId 写入断开记录（F-OPS-09）。
5. **pprof 移出指标端口**，Grafana 由 console-server 做认证代理，Prometheus / Alertmanager 对 VPN 用户不可达（F-OPS-17）。
6. **备份**：只读展示记录 + 发布流程在 `migrate up` 前自动备份（O-2 ① + ③）；删除"请求立即备份"，恢复永远不进后台（F-OPS-12、F-OPS-13）。
7. **告警升为第一批**，告警口径改为与内存分析一致的"存活内存"，并加最小量保护和发布抑制（F-OPS-07）。
8. **AC 全部补齐"环境 / 输入 / 操作 / 预期"**，性能类 AC 改为交替对照 + 中位数 + 绝对余量（AC-OPS-90-1）。
9. 每个功能点标注**第一批 / 第二批**；工作量按 28～40 人日分项重估（第 10 节）。

## 1. 背景与目标

### 1.1 背景

服务端已经具备基础可观测能力（B5）：`/healthz`、`/readyz`；内网地址 `IM_METRICS_ADDR` 上的 Prometheus 指标和 pprof；连接关闭日志（`conn closed`）；备份 / 恢复 / 迁移命令行。但这些能力只能靠 curl、`go tool pprof`、翻日志来用：
- 没有统一的地方看"服务现在好不好"；
- 用户反馈"老掉线"时只能登服务器 grep 日志，而且**握手阶段被拒（token 过期、被强制下线后反复重连）目前既不写断开日志、也不计入断开指标**，是最常见却最查不到的一类；
- 备份是否按时成功没人知道；
- 生产配置是否安全只能读环境变量；
- 将来集群化（ARCH 第 2 节）后，上面每件事都要在 N 个节点上各做一遍。

### 1.2 目标与原则

给运维 / 开发一个**只在内网 / VPN 可用**的运维后台：掌握服务运行状态、排查连接问题、检查配置与备份、查看两个后台的操作审计。

1. **安全第一**：运维后台能看到内部指标和用户在线信息，比业务后台更敏感。本期**完全只读**：不提供任何改变 IM 运行状态的操作，也不提供备份触发（v0.1 的"请求备份"已删除）。唯一的写操作是第二批的"告警静默"（只影响通知，不影响 IM）。
2. **不影响 IM 主流程**：所有查询走内网、走 Prometheus 或节点只读接口，有并发和超时上限；节点接口不与消息写入共用数据库连接。
3. **为集群预留**：所有页面以"节点"为维度；单节点是 N=1 的特例。依赖 B6（Redis / NATS / Postgres 集群）的能力单独标注，不作为第一批验收条件。
4. **一套登录**：运维后台、Grafana 共用 console-server 的会话和 TOTP，不存在"只靠密码就能进"的第二个入口。

### 1.3 成功标准

| 指标 | 目标 | 度量方法 |
|---|---|---|
| 发现问题 | 节点不可达、无就绪节点、5xxx 错误率升高、备份超过 2 小时未成功，**3 分钟内**通知到告警接收人 | AC-OPS-07-2、07-3（第一批即可度量：告警已升为第一批） |
| 排查效率 | 给定 userId，1 分钟内查到其当前连接和最近断开原因（**包括握手阶段被拒**），不需要登服务器 | AC-OPS-08-1、09-1、09-3 |
| 安全 | 外网不可达；VPN 用户也不能绕开 console-server 直接访问节点接口、Prometheus、Alertmanager、pprof；所有用户级查询可审计且与节点访问日志对得上；任何页面、接口、日志都不出现密钥 | F-OPS-03、14、16、17 的 AC + 上线前渗透测试（AC-OPS-90-6） |
| 无副作用 | 1 万连接 + 500 条/秒下持续使用运维后台：IM 端到端 P99 的中位数 ≤ 对照组中位数 + 20ms 且 ≤ 1 秒，意外断开 0 | AC-OPS-90-1 |

## 2. 角色与场景

运维账号属于公共基座中**独立的 `ops` 账号空间**（X-2）：与管理后台账号互不相通，管理后台的任何角色（包括 `super_admin`）都不能查看、创建、重置、停用运维账号。

| 角色 | 说明 |
|---|---|
| 运维超管 `ops_superadmin` | 运维账号的创建、重置（密码与二次验证一并重置）、解锁、停用 / 启用、改角色。**本身没有任何运维数据权限**（看不到总览、连接、审计） |
| 运维值班 `ops_viewer` | 总览、节点、指标图表（Grafana）、告警、配置检查、数据库与备份；**看不到任何用户级信息** |
| 运维排障 `ops_engineer` | `ops_viewer` 的全部权限 + 按 userId 查当前连接和断开记录（必须填工单号和理由）；第二批：告警静默 |
| 运维审计员 `ops_auditor` | 只能查看审计日志（运维空间 + 管理空间两个来源） |

角色按公共基座**可以叠加**（同一空间内），但 `ops_superadmin`、`ops_auditor` 是**互斥角色**，不能与任何其他运维角色叠加（基座 F-CON-06 规则 4）："排障"和"审计"必须是两个人，运维超管没有任何运维数据权限。`ops_engineer` 已包含 `ops_viewer` 的权限，所以小团队一个人做值班和排障只需要一个账号。运维空间**没有应急授权**（基座 F-CON-06 规则 6 只在管理空间提供）。

核心场景：
1. 值班同学早上打开总览，确认所有节点就绪、在线连接数正常、错误率接近 0、昨晚备份全部成功、没有正在触发的告警。
2. 半夜收到"5xxx 错误率高"告警，手机连 VPN 打开总览，看到是 `send` 出错，点进 Grafana 看命令耗时，确认是数据库变慢。
3. 客服转来"用户 u123 一直掉线"（工单 `CS-1024`），排障同学输入 userId、工单号和理由，看到该用户最近 20 次断开都是**握手阶段的 4012**（账号已被强制下线，客户端还在用旧 token 反复重连），判断是客户端没有处理 `kicked`。
4. 发布前，开发在配置检查页确认生产 Origin 白名单正确、测试开关全部关闭、各节点配置一致；发布脚本在 `migrate up` 前自动备份，备份页上能看到这条"发布前"记录。
5. 审计员按月抽查：谁查过哪些用户的连接、理由是什么、节点侧访问日志能否一一对上；谁在管理后台删过消息。

### 3.1 组件与名词

| 名词 | 说明 |
|---|---|
| `console-server` | 后台服务（X-1）：独立仓库、独立进程，同时服务管理后台和运维后台；只部署在内网 / VPN 后面；数据库为 Postgres（X-3）。运维后台的入口为 `ops.<内网域名>`，管理后台为 `admin.<内网域名>`，两者 Cookie、菜单、角色互不相通 |
| 公共基座 | PRD-admin v0.2 中"console-server 公共基座"一节定义的账号空间、登录、TOTP、角色模型、会话、重新验证、审计、测试模式、错误码。**本 PRD 中凡涉及这些内容，一律以公共基座为准** |
| 节点 | 一个 im-server 进程，以 `IM_NODE_ID` 标识（生产环境必须配置，见 S-OPS-19） |
| 节点运维接口 | im-server 在 `IM_OPS_ADDR` 上提供的只读接口（第 7.2 节），只接受 console-server 的签名请求 |
| 节点凭证表 | console-server 的静态配置：每个节点的 `node_id`、地址、TLS 服务名、密钥 ID 与 Ed25519 私钥的文件引用（第 7.3 节）。私钥只在密钥文件中，不进数据库、不进日志 |
| Prometheus / Grafana / Alertmanager | 指标存储、图表、告警；配置全部在 `tianting-server/deploy/observability/` |
| 备份存储 | 对象存储（单机模式用本地 MinIO），`backups/` 前缀放加密后的备份文件，`manifests/` 前缀放清单 |

### 3.2 通用约定

| 项 | 约定 |
|---|---|
| 时间 | 页面按浏览器本地时区显示到秒；接口一律毫秒时间戳。**"今日"统一按 Asia/Shanghai 自然日计算**，卡片上注明 |
| 数据新鲜度 | 每个数据卡片显示"数据时间"；数据源不可用时显示"数据不可用"和原因，**不得显示为 0 或"无"** |
| 自动刷新 | 总览、节点列表每 15 秒自动刷新，可暂停；其他页面手动刷新。自动刷新请求带 `X-Console-Background: 1`，**不续期空闲计时**（B-OPS-05）；页面不可见（`visibilitychange` 为 hidden）时暂停自动刷新，恢复可见时立即刷新一次 |
| 密钥 | 任何页面、接口响应、console-server 与 im-server 日志都不得出现密钥、token、密码、TOTP 种子、恢复码及其哈希；只显示"已配置 / 长度达标 / 数量" |
| 个人信息 | 用户级数据（连接、断开记录）只对 `ops_engineer` 可见；终端用户 IP 只显示脱敏形式（IPv4 保留前 2 段，如 `10.8.*.*`；IPv6 保留前 3 组（48 位），其余为 `*`），与 PRD-admin F-ADM-14 相同，脱敏在 im-server 内完成，节点只保存脱敏后的值；不展示任何消息正文和会话订阅 |
| 部分结果 | 多节点聚合时某节点超时或出错：返回其余节点的结果，响应带 `partial: true` 和 `missingNodes`，页面顶部标出"节点 X 未响应，结果可能不完整"，**不得据此得出"不存在 / 不在线"的结论** |
| 文本长度 | 去首尾空白后按 Unicode 码点计数（与 PRD-core、PRD-admin 一致） |
| 错误 | 错误码以公共基座和 `errors.json` 为准（按 ERRORS.md 号段规则分配）；运维侧**不新增**独立错误码：参数错误 4000 / 4004，频率 4290；每日配额 4292（不可自动重试），权限 4030，其他后台通用码见公共基座。前端按错误码显示文案 |
| 适配 | 桌面浏览器为主；总览、节点、告警列表在 375px 宽度可用（值班手机）。兼容 Chrome、Edge、Safari、Firefox 最新两个大版本 |

## 4. 对公共基座的需求（运维侧必须满足的条目）

> **账号、会话、重新验证、审计以 PRD-admin v0.2「console-server 公共基座」为准。** 本节只列运维侧必须满足的条目。一致性复审（RECHECK-v0.2 第 2 节）已逐条核对：与基座冲突的条目已改为基座写法（C-01～C-10），基座缺的通用能力已补进基座（C-06、C-11）；**以修改基座为准，不在本 PRD 另起规则**。

| 编号 | 运维侧需求 | 运维侧验证 AC | 与 PRD-admin v0.1 的差异（核对点） |
|---|---|---|---|
| B-OPS-01 | **独立账号空间**：基座支持多个账号空间，运维账号属于 `ops` 空间；一个账号只属于一个空间；管理空间的任何角色（含 `super_admin`）对 `ops` 空间账号没有任何读写接口权限，反之亦然；在一个空间登录得到的会话不能访问另一个空间的接口 | AC-OPS-01-13、01-14 | v0.1 是单一账号库，`super_admin` 可以重置任意账号（R-OPS-02） |

## 5. 功能需求

> 每个功能点：描述 → 规则 → 验收标准（AC）。【后端】指 console-server 或 im-server，【前端】指 `tianting-ops`；未标注的为端到端。AC 一律写明环境、输入、操作、预期。
> AC 编号与 v0.1 同号的，验证的是同一件事（或其修正版）；v0.1 中被删除的 AC 不复用编号，见第 14 节。

### F-OPS-01 账号、登录与会话（第一批）

**描述**：规格以公共基座为准（B-OPS-01～07、12、13）。本节的 AC 在运维空间内验证这些需求。

**规则**
1. 运维后台入口 `ops.<内网域名>`，只接受 `ops` 空间账号登录。
2. 首个 `ops_superadmin` 由命令行在 console-server 主机上创建（`console-server account bootstrap --space ops --username <u>`，基座 F-CON-02 规则 2），之后由 `ops_superadmin` 在页面上创建其他运维账号。网页上没有注册入口。
3. 运维侧遵守基座的全部登录、会话、CSRF、重新验证规则；与 v0.1 相比的运维专属要求只有一条：自动刷新和 Grafana 的数据查询不续期空闲计时（B-OPS-05，已补进基座 F-CON-05 规则 3）。

**验收标准**
- AC-OPS-01-1【后端】：[E1] 输入：console-server 的路由清单（启动时导出）；操作：筛选所有能创建账号的接口；预期：只有 `ops_superadmin` 的账号创建接口和管理空间的对应接口，不存在任何未登录可调用的注册接口；`ops` 空间没有账号时，访问登录页显示"请先在服务器上用命令行创建运维超管"。
- AC-OPS-01-2【后端】：[E1] 输入：不存在的账号、错误密码、错误动态码、错误恢复码、已停用账号、待激活账号六种情况（同基座 AC-CON-03-2）；操作：每种各登录 20 次；预期：六种情况响应完全相同（HTTP 401、错误码 4015、同一文案、同一响应头集合），响应时间中位数两两相差 ≤ 30ms。
- AC-OPS-01-3【后端】：[E1] 输入：账号 `eng1`；操作：从同一 IP 连续 5 次错误密码，第 6 次用正确密码 + 正确 TOTP；测试时钟前进 15 分钟后再登录；另取账号 `eng2` 锁定后由 `ops_superadmin` 手动解锁再登录；对不存在的账号名 `ghost` 从同一 IP 连续失败 5 次后再登录第 6 次；预期：`eng1` 第 6 次返回 429 / 4291；时钟前进后登录成功；`eng2` 解锁后立即登录成功，审计中有一条 `account.unlock` 记录；`ghost` 第 6 次同样返回 429 / 4291，响应与 `eng1` 第 6 次完全相同。
- AC-OPS-01-4【后端】：[E1] 输入：同一来源 IP；操作：1 分钟内发起 21 次登录请求；预期：第 21 次返回 HTTP 429 / 4290。
- AC-OPS-01-5：[E1] 输入：`ops_superadmin` 新建账号 `view1`（得到一次性激活码）；操作：`view1` 用激活码 + 新密码激活后、绑定 TOTP 之前请求 `GET /console/api/ops/v1/overview`；预期：返回 401 / 4016，不返回数据；页面跳到"绑定二次验证"页。
- AC-OPS-01-6【后端】：[E1] 操作：登录运维后台；预期：`Set-Cookie` 名为 `__Host-ops_sid`，含 `HttpOnly`、`Secure`、`SameSite=Strict`、`Path=/`，无 `Domain`；登录前后会话 ID 不同；数据库中密码字段以 `$argon2id$` 开头。
- AC-OPS-01-7【后端】：[E1] 操作：登录后最后一次请求过去 29 分钟（测试时钟）请求一次、再过 31 分钟请求一次；另一会话持续每 10 分钟请求一次直到第 12 小时 1 分；预期：29 分钟时成功、31 分钟时返回 401；第 12 小时 1 分时返回 401。
- AC-OPS-01-8【后端】：[E1] 操作：同一账号在浏览器 A、B 各登录一次，A 修改密码；预期：B 的下一次请求返回 401，A 的当前会话保持有效。
- AC-OPS-01-9【后端】：[E1] 输入：`POST /console/api/ops/v1/troubleshoot/query`；操作：分别不带 `X-CSRF-Token`、带错误令牌、`Origin` 为 `https://evil.example`；预期：三次都返回 403 / 4037，没有调用任何节点接口，审计表无新增（CSRF 失败属于基座 F-CON-06 规则 3 的未认证拒绝，只计 `console_rejected_total{reason}`）。
- AC-OPS-01-10【后端】：[E1] 操作：唯一的 `ops_superadmin` 修改自己的角色；预期：返回 409 / 4093，角色不变，审计记录 `result=failure`、`code=4093`。
- AC-OPS-01-11【后端】：[E1] 操作：唯一的 `ops_superadmin` 停用自己；新建第二个 `ops_superadmin` 后，第一个停用第二个、再尝试停用自己；预期：第一次返回 409 / 4093；停用第二个成功；之后停用自己仍返回 409 / 4093（不能停用最后一个启用的运维超管）。
- AC-OPS-01-12【后端】：[E1] 操作：`ops_superadmin` 在会话中从未重新验证时创建账号；预期：返回 403 / 4038（基座定义的"需要重新验证"），**HTTP 状态不是 401**，账号未创建；输入正确 TOTP 后 4 分钟内再创建一个账号不需要再次输入，6 分钟后（测试时钟）需要再次输入。
- AC-OPS-01-13【后端】：[E1] 输入：管理空间的 `super_admin` 会话、运维账号 `eng1` 的账号 ID；操作：调用重置、解锁、停用、修改角色、查询账号详情 5 个接口；预期：全部返回 404 / 4040，`eng1` 状态不变，每次都产生一条 `space=admin`、`result=denied`、`code=4040` 的审计记录。
- AC-OPS-01-14：[E1] 操作：用管理空间账号的用户名、密码、TOTP 登录 `ops.<内网域名>`；用运维账号登录 `admin.<内网域名>`；把管理后台的 `__Host-adm_sid` Cookie 手工带到运维后台接口上；预期：两次登录都返回 AC-OPS-01-2 的通用失败；带管理 Cookie 的运维接口请求返回 401。
- AC-OPS-01-15：[E1] 操作：登录后打开总览，保持自动刷新，不做任何人工操作；测试时钟推进 30 分钟后等待下一次自动刷新；另一会话在第 29 分钟手动点击"刷新"；预期：第一个会话的下一次请求返回 401，页面跳到登录页并提示"登录已过期"；第二个会话在第 29 分钟的手动刷新续期，之后 30 分钟内的请求仍成功。
- AC-OPS-01-16【前端】：[E1] 操作：打开总览后把标签页切到后台（`visibilitychange` 为 hidden）60 秒，再切回；预期：hidden 期间没有发出 overview 请求；切回后 1 秒内发出一次刷新请求；所有自动刷新请求带 `X-Console-Background: 1`，手动刷新请求不带。
- AC-OPS-01-17【后端】：[E1] 操作：用某个 TOTP 码登录成功后，在同一 30 秒步长内用同一码再次登录；预期：401 / 4015。
- AC-OPS-01-18【后端】：[E1] 操作：在 console-server 主机上用命令行创建首个 `ops_superadmin`；预期：审计中有一条 `space=ops`、`action=account.bootstrap`、操作人 `cli:<操作系统用户>@<主机名>` 的记录，且进入哈希链（校验命令通过）。

### F-OPS-02 运维角色与权限（第一批；双人批准为第二批）

**规则**
1. 权限矩阵（✅ 可用，— 不可用）：

| 权限点 | 功能 | ops_viewer | ops_engineer | ops_auditor | ops_superadmin |
|---|---|---|---|---|---|
| `ops.overview.read` | 总览、节点列表、告警列表、进入 Grafana | ✅ | ✅ | — | — |
| `ops.config.read` | 配置检查、数据库与迁移、备份记录 | ✅ | ✅ | — | — |
| `ops.troubleshoot` | 连接排查（当前连接、断开记录） | — | ✅ | — | — |
| `ops.silence.write` | 告警静默（第二批） | — | ✅ | — | — |
| `ops.audit.read` | 审计日志查看（运维 + 管理两个来源） | — | — | ✅ | — |
| `ops.account.manage` | 运维账号与角色管理 | — | — | — | ✅ |
| 只需登录 | 个人设置（改密码、退出、查看自己的会话） | ✅ | ✅ | ✅ | ✅ |

   角色可叠加时权限取并集（基座 F-CON-06 规则 1）；`ops_superadmin`、`ops_auditor` 为互斥角色，不能与任何其他运维角色叠加，所以实际可出现的组合只有：单独 `ops_viewer`、单独 `ops_engineer`、`ops_viewer` + `ops_engineer`（等同 `ops_engineer`）、单独 `ops_auditor`、单独 `ops_superadmin`。运维空间**没有应急授权**：`ops_superadmin` 不能给自己加任何角色，要获得排障权限只能由另一名运维超管授予 `ops_engineer`（第二批起需第二人批准，规则 6）。

2. 新建账号至少选择一个角色；权限只在服务端判断，接口清单（第 6 节）中每个接口声明所需权限点，未声明的路由启动失败（基座 F-CON-06 规则 2）。前端隐藏菜单只是体验优化。
3. 管理空间的任何账号或角色都不能获得运维权限（B-OPS-01）。
4. 登录后的越权请求返回 403 / 4030 并写审计（`result=denied`）；网段外和未登录请求不写审计（B-OPS-11）。
5. 运维空间的敏感角色（基座 F-CON-06 规则 5）为 `ops_superadmin`、`ops_engineer`、`ops_auditor`：授予或变更为上述角色时，向全部 `ops_auditor` 发站内通知（操作人、对象账号、新角色、时间）。
6. 第二批：授予 `ops_engineer` 需要第二个 `ops_superadmin` 批准后生效。

**验收标准**
- AC-OPS-02-1【后端】：[E1] 输入：第 6 节接口清单（机器可读版本，作为参数化测试的数据源）；操作：用 4 个角色各一个账号 + 一个无会话请求，逐个调用清单中的全部接口；预期：结果与规则 1 矩阵逐格一致（有权限 ≠ 403；无权限 = 403 / 4030；无会话 = 401）。
- AC-OPS-02-2【前端】：[E1] 操作：`ops_viewer` 登录；预期：菜单中没有"连接排查""审计日志""账号管理"；手动输入这些页面地址显示"无权限"页。

### F-OPS-07 告警（第一批）

**规则**
1. 告警规则在 `tianting-server/deploy/observability/prometheus/alerts.yml`，每条都有 `promtool test rules` 用例，覆盖触发、不触发和边界。初始规则（`job="im"`）：

| 告警 | 条件（PromQL 口径） | 持续 | 级别 |
|---|---|---|---|
| 节点不可达 | `up{job="im"} == 0` | 1 分钟 | 严重 |
| 无就绪节点 | `(sum(im_ready{job="im"}) or vector(0)) == 0`（节点全挂、指标全部消失时也成立） | 1 分钟 | 严重 |
| 5xxx 错误率高 | 5 分钟内 5xxx 占比 > 1% **且** 5xxx 条数 ≥ 10 | 5 分钟 | 严重 |
| 命令耗时高 | 5 分钟内 send 中超过 500ms 的比例 > 1%（`1 - bucket{le="0.5"} / count`，直接读桶边界，不插值）**且** send 速率 > 1 条/秒 | 5 分钟 | 警告 |
| 在线连接骤降 | 总连接数比 5 分钟前下降 > 30% 且下降前 > 100；**任一节点 `im_draining == 1` 或最近 10 分钟有节点重启（`changes(process_start_time_seconds[10m]) > 0`）时不触发** | 2 分钟 | 警告 |
| 慢连接增多 | `increase(im_slow_consumers_total[1m]) > 10` | 5 分钟 | 警告 |
| 握手异常 | 凭证无效（`result="token_invalid"`）握手 > 50 次 / 分钟 | 5 分钟 | 警告（可能是攻击或客户端 bug） |
| 内存逼近上限 | 已设置 GOMEMLIMIT 时，**存活内存估算 > GOMEMLIMIT × 0.66**（余量不足 1.5 倍，与内存分析的部署建议一致） | 10 分钟 | 警告 |
| 疑似 GC 风暴 | GC CPU 占比 > 25% | 5 分钟 | 严重 |
| 备份过期 | `time() - max by (source) (im_backup_last_success_timestamp_seconds) > 7200`，或该指标不存在（`absent`） | 1 分钟 | 严重 |
| 版本不一致 | `count(count by (version) (im_build_info)) > 1` | 30 分钟 | 警告 |

2. 通知内容：告警名、级别、`node_id`、当前值、阈值、开始时间、运维后台对应页面链接（内网地址）。模板**不输出 `instance` 标签**（节点 IP:端口），**不包含任何终端用户的 userId、IP、token**。恢复时发送"已恢复"。
3. 通知渠道：第一批为办公 IM 机器人 + 邮件（Alertmanager receiver，配置在仓库中）；**告警链路不经过天听自身**。接收人名单和严重告警是否加电话 / 短信见第 11 节 F-1。
4. 同一告警 `repeat_interval = 1h`；`im_draining == 1` 时抑制该节点的"节点不可达"以外的警告级告警（inhibit）。
5. 静默：第一批只能在 Alertmanager 主机上用 `amtool` 创建，`comment` 必须写工单号；第二批改为经 console-server 创建并写审计（F-OPS-18）。
6. 告警链路（Prometheus → Alertmanager → 通知渠道）不依赖 console-server 和 IM 本身。

**验收标准**
- AC-OPS-07-1【后端】：[promtool] 输入：每条告警的构造时间序列；操作：`promtool test rules`；预期：全部通过，至少覆盖：5xxx 9 条（占比 2%）不触发、10 条触发；节点全挂（`im_ready` 消失）触发"无就绪节点"；连接骤降发生在节点重启后 10 分钟内不触发、无重启时触发；send 速率 0.5 条/秒时不触发耗时告警；存活内存 = 上限 × 0.65 不触发、× 0.67 持续 10 分钟触发；GOMEMLIMIT 未设置时不触发内存告警；备份指标不存在时触发"备份过期"。

### F-OPS-08 连接排查：当前连接（第一批；异常查询通知为第二批）

**规则**
1. 仅 `ops_engineer`。接口 `POST /console/api/ops/v1/troubleshoot/query`，请求体 `{userId, ticket, reason}`（**不放在 URL 里**，避免进入浏览器历史和访问日志）：
   - `userId`：格式同 PRD-core 3.1 节，不合法返回 4004；
   - `ticket`（工单号）：必填，格式由基座 `CON_TICKET_PATTERN` 决定（默认 `^[A-Za-z0-9_-]{3,32}$`，PRD-admin 2.3 节）；
   - `reason`（理由）：必填，去首尾空白后 4～200 个码点，不能由同一个字符重复组成（基座 PRD-admin 2.3 节）。
   不合法时返回 4000，**不调用任何节点接口**。
2. 每条连接显示：连接 ID（含节点前缀）、平台、所在节点、建立时间、在线时长、客户端 IP（脱敏）、下行队列状态（正常 / 积压中）。**不显示 token、消息内容、订阅了哪些会话**。
3. 查询方式：第一批向全部静态节点并发查询（并发上限 8，单节点超时 1.5 秒）。B6 之后先查 Presence 得到用户所在节点，只请求这些节点；Presence 不可用时退化为全部节点并提示"在线路由不可用，已查询全部节点"。
4. 结果判定：
   - 全部节点都响应且都没有连接：显示"当前不在线"，并引导查看断开记录；**不区分"用户不存在"和"不在线"**。
   - 只要有节点未响应：**不得显示"当前不在线"**，显示"在已响应的 N 个节点上未找到连接；节点 X 未响应，结果可能不完整"。
5. 频率与配额：每个账号每分钟最多 30 次查询；每个账号每个自然日（Asia/Shanghai）最多查询 **50 个不同的 userId**，超出返回 429 / 4292（不可自动重试，基座 2.3 节"每日上限"）并提示"今日排查用户数已达上限，请联系运维超管"；重复查询已查过的 userId 不额外计数。
6. 每次查询写一条审计（与 F-OPS-09 共用，见 F-OPS-14）：操作人、userId、工单号、理由、结果条数、`partial`、请求 ID。
7. console-server、节点、代理的访问日志中不出现 userId、工单号和理由原文（只在审计表里）。
8. 只读：不提供强制下线按钮；需要踢人时使用管理后台。
9. 第二批：同一账号 1 小时内查询 ≥ 20 个不同 userId 时，向全部 `ops_auditor` 发站内通知。

| 密钥 | `IM_JWT_KEYS` 的 kid 列表、`IM_JWT_ACTIVE_KID`、管理密钥、运维接口密钥 kid 列表 | **只显示 kid、数量和"已配置 / 长度达标"**，不显示值和哈希 |
| 网络 | `IM_ADDR`、`IM_METRICS_ADDR`、`IM_OPS_ADDR`（及是否启用 TLS）、`IM_OPS_ALLOWED_CIDRS`、`IM_PPROF_ADDR`、`IM_ALLOWED_ORIGINS`、`IM_TRUSTED_PROXIES` | 原值 |
| 限流与上限 | `IM_HANDSHAKE_RATE`、`IM_HANDSHAKE_BURST`、无效 token 封禁阈值、`IM_MAX_CONNS_PER_USER`、单用户发送限流（C-29）、`IM_IDLE_TIMEOUT`、`IM_DRAIN_DELAY` | 原值 |
| 数据库 | 类型、位置 | SQLite 显示文件路径；Postgres（B6）显示主机和库名，**去掉用户名和密码** |
| 开关 | `IM_TEST_MODE`、`IM_DEMO_LOGIN`、`IM_AUTO_MIGRATE` | 原值 |

2. 风险提示（只提示，不修改；判断写成纯函数并单测）：
   - `IM_ALLOWED_ORIGINS` 含 `*` → 高风险；
   - production 下 `IM_TRUSTED_PROXIES` 为空 → "如果部署在负载均衡之后，客户端 IP 和限流会失效"；
   - `GOMEMLIMIT` 未设置 → 提示参考内存分析；
   - `GOMEMLIMIT` < 规划连接数 × 32 KB × 1.5 → 高风险（GC 风暴）。规划连接数取 `IM_PLANNED_CONNS`；未配置时取 Prometheus 近 7 天该节点峰值连接数，并注明来源；
   - `IM_NODE_ID` 未配置（非 production）→ 提示"集群部署和生产环境必须配置"；
   - `IM_PPROF_ADDR` 不是回环地址（非 production）→ 高风险；
   - 非 production 开启测试模式 → 提示。
3. 集群模式（E2a 起）增加"节点间差异"视图：同一配置项在各节点取值不同时高亮（版本、节点 ID、地址类除外）。
4. 页面只读，不提供修改配置的入口。

### F-OPS-11 数据库与迁移状态（第一批；库大小与行数估算为第二批）

**规则**
1. 显示：数据库类型、位置（脱敏规则同 F-OPS-10）、连通性、当前迁移版本、已执行的迁移列表（版本、执行时间、校验和是否一致）、**未执行的迁移**。内容与 `im-server migrate status` 一致：两者调用**同一个函数**（S-OPS-22）。
2. 有未执行的迁移时标黄："有 N 个迁移未执行，生产环境由发布流程执行 `im-server migrate up`（执行前自动备份，见 F-OPS-13）"；校验和不一致标红。
3. 节点的 `/internal/v1/db` 使用**单独的只读连接**（SQLite `mode=ro`；Postgres 用只读账号），不与消息写入共用连接。
4. 第二批（仅 Postgres，依赖 B6）：数据库大小、消息表行数估算（读 `pg_class.reltuples`，不做 `count(*)`）。SQLite 不提供行数估算。
5. 只读，不提供执行迁移的按钮。

**验收标准**
- AC-OPS-11-1：[E1] 操作：迁移全部执行后，对比页面与 `im-server migrate status` 的输出；预期：版本、执行时间、校验和状态逐项一致。
- AC-OPS-11-2：[E1] 输入：包含新迁移 `0002` 的二进制、`IM_AUTO_MIGRATE=0`；操作：启动后打开页面；预期：显示"有 1 个迁移未执行"并列出 `0002`。
- AC-OPS-11-3：[E1] 操作：用 `IM_TEST_MODE` 的故障注入让 `store.Ping` 返回错误；预期：连通性显示"不可用"，与 `/readyz` 返回 503 一致；节点列表中该节点显示"未就绪"（不是"下线中"）。
- AC-OPS-11-4【后端】：[单测] 操作：通过 `/internal/v1/db` 使用的连接执行一条 INSERT；同时在主连接写入一条消息；预期：前者返回只读错误（SQLITE_READONLY）；后者成功。
- AC-OPS-11-5【后端】：[E1] 操作：在测试库中把已执行迁移 `0001` 的记录校验和改为错误值后打开页面；预期：`0001` 标红"校验和不一致"，与 `migrate status` 输出一致。
- AC-OPS-11-6【后端】：[E2b·依赖 B6]（第二批）操作：打开数据库页并检查 Postgres 执行过的语句；预期：显示数据库大小和消息表行数估算；执行的语句中没有 `count(*)`。

### F-OPS-12 备份记录（第一批，只读）

**规则**
1. **备份由主机上的定时任务和发布流程执行，运维后台只读展示**；im-server 和 console-server 都不提供任何备份或恢复的 HTTP 接口（ARCH 第 7 节；O-2）。恢复永远不进后台，只能在主机上停服后用 `im-server restore`。
2. 定时备份任务（`tianting-server/deploy/backup/`，每小时一次，保留 48 份）：`im-server backup`（在线快照 + 校验）→ 用 age 加密（ARCH S10）→ 上传到备份存储 `backups/` → 写清单到 `manifests/` → 更新 node_exporter textfile 指标。单机模式同样上传到对象存储（本地 MinIO），console-server 不需要与数据库同机。
3. 清单字段：`source`（`im` / `console`，console-server 自己的 Postgres 备份也写同格式清单）、`trigger`（`schedule` / `pre-migrate`）、开始 / 结束时间、文件名、大小、SHA-256、是否通过校验、是否已加密、是否已上传、迁移版本、执行主机、发布版本（`pre-migrate` 时）、结果、失败原因摘要（不含路径和凭证）。
4. 指标：备份任务成功后在同一步写 textfile：`im_backup_last_success_timestamp_seconds{source, trigger}`、`im_backup_last_attempt_timestamp_seconds{source}`、`im_backup_last_size_bytes{source}`。"备份过期"告警直接由 Prometheus 判断，**不经过 console-server**。
5. console-server 的存储凭证**只能列出和读取 `manifests/` 前缀**；不能读 `backups/`，不能写或删任何对象。
6. 显示：最近 48 次记录（按 `source` 分组）、最近一次成功的时间与距今时长；距今 > 2 小时标红（与告警一致）。**判断健康只看"最近一次成功"**：备份任务可能连失败记录都写不出来，这种情况表现为"最近一次成功"变旧，同样标红和告警。
7. 页面只显示文件名，不显示完整路径、桶名之外的存储地址和凭证；不提供下载和恢复入口。
8. 集群模式（B6，Postgres + pgBackRest）：备份任务把 `pgbackrest info` 导出为同格式清单，页面不变。

**验收标准**
- AC-OPS-12-1：[E1] 操作：手动执行一次定时备份任务，之后刷新备份页；预期：出现一条 `source=im`、`trigger=定时` 的记录，大小和 SHA-256 与对象存储中的文件一致，"已校验""已加密""已上传"均为是。
- AC-OPS-12-2：[E1] 输入：备份任务的 age 公钥配置为空（加密步骤失败）；操作：执行任务；预期：页面出现一条"失败"记录，失败原因摘要为"加密失败"，不含路径和凭证；`im_backup_last_success_timestamp_seconds` 不变。
- AC-OPS-12-3：[E1] 操作：测试时钟推进到最近一次成功备份后 2 小时 1 分钟；预期：备份页"最近一次成功"标红，总览的备份卡片同样标红。
- AC-OPS-12-4：[E1] 操作：删除最近 3 次的清单文件、不写任何失败记录（模拟磁盘满），刷新页面；预期："最近一次成功"显示为更早的那次，并按距今时长正确标红。
- AC-OPS-12-5【后端】：[E1] 输入：console-server 使用的存储凭证；操作：列出 / 读取 `manifests/`；读取 `backups/` 中任一对象；向任一前缀写入；删除任一对象；预期：第一项成功，其余三项都返回 AccessDenied。
- AC-OPS-12-6【后端】：[E1] 操作：检查备份相关接口的完整响应；预期：只含文件名，不含服务器路径、存储访问密钥。
- AC-OPS-12-7：[E1] 操作：执行一次成功备份后读取 Prometheus；预期：`im_backup_last_success_timestamp_seconds{source="im"}` 与清单中的结束时间相差 ≤ 1 秒。
- AC-OPS-12-8：[E1] 操作：执行一次 console-server Postgres 的备份任务；预期：备份页 `source=console` 分组下出现一条记录，字段齐全。

### F-OPS-13 发布前自动备份（第一批，替换 v0.1 的"请求立即备份"）

**描述**：真实需求是"发布、迁移前一定有一份最新备份"，放在发布流程里，不在后台开写入通道（O-2 ③）。

**规则**
1. 发布脚本（`tianting-server/deploy/release.sh`，或 CI 中同样的步骤）在执行 `im-server migrate up` 之前，先用 `im-server migrate status` 判断是否有未执行的迁移：有则执行与定时备份**完全相同**的备份任务（`trigger=pre-migrate`，清单带发布版本）；没有则跳过并在发布日志中写"无待执行迁移，跳过发布前备份"。
2. 备份任务任何一步失败（快照、校验、加密、上传、清单）：**终止发布**，不执行 `migrate up`，不切换二进制，脚本以非 0 退出。
3. 备份页把这类记录标为"发布前"，显示发布版本。
4. console-server 不提供任何触发备份的接口；恢复永远不进后台。

**验收标准**
- AC-OPS-13-1【后端】：[E1] 输入：当前库迁移版本 0001，新二进制包含 `0002`；操作：执行发布脚本；预期：先产生一条 `trigger=pre-migrate`、迁移版本 0001 的成功清单，其结束时间早于 `migrate up` 的执行时间；发布后 `migrate status` 显示 0002 已执行。
- AC-OPS-13-2【后端】：[E1] 输入：同上，但让上传步骤失败（对象存储凭证错误）；操作：执行发布脚本；预期：脚本非 0 退出；`migrate status` 仍显示 0002 未执行；运行中的仍是旧版本二进制。
- AC-OPS-13-3【后端】：[单测] 输入：console-server 与 im-server（`IM_ADDR`、`IM_METRICS_ADDR`、`IM_OPS_ADDR`、`IM_PPROF_ADDR` 全部端口）的路由表；预期：不存在任何与备份、恢复相关的 HTTP 路径。
- AC-OPS-13-4：[E1] 操作：AC-OPS-13-1 之后打开备份页；预期：该记录标为"发布前"，显示发布版本号。
- AC-OPS-13-5【后端】：[E1] 输入：没有待执行迁移；操作：执行发布脚本；预期：不产生新的备份清单，发布日志含"无待执行迁移，跳过发布前备份"，发布成功。

**规则**
1. 存储、字段、哈希链、写失败处理、保留期、数据库权限、校验命令**以公共基座为准**（B-OPS-09）。运维侧所有事件 `space=ops`。
2. 运维侧必须记录的事件（`action` 枚举，由基座枚举扩展）：

| action | 事件 | 目标 | 额外字段 |
|---|---|---|---|
| 基座定义的登录 / 登出 / 失败 / 锁定 / 解锁 / TOTP 绑定与重置 / 账号创建 / 停用 / 启用 / 角色变更 / 审计查询 / 权限拒绝 | — | — | 以基座为准 |
| `ops.troubleshoot.query` | 连接排查（当前连接 + 断开记录，一次一条） | `user:<userId>` | 工单号、理由、结果条数、`partial`、查询的节点列表 |
| `ops.config.view` | 查看配置检查 | `node:*` 或 `node:<id>` | — |

| `ops.silence.create` / `ops.silence.expire` | 告警静默（第二批） | `alert:<匹配条件>` | 工单号、理由、时长 |
| `ops.audit.export` | 审计导出（P1） | — | 筛选条件、条数 |

3. 不记录审计：总览、节点、图表、数据库、备份页的浏览（不含个人信息、量大）；网段外和未登录请求（B-OPS-11）。
4. **写失败则操作失败**（X-4）：上表中的事件写审计失败时，该操作返回失败、不执行（排查不调用节点接口，配置检查不返回数据）；不记录审计的页面不受影响。
5. **节点侧对账**：im-server 对运维接口的每次请求写访问日志（S-OPS-10）：时间、调用方密钥 ID、操作人账号 ID（签名范围内的请求头）、请求 ID、接口、结果条数、耗时、调用方 IP；**不写 userId**。审计员可以用请求 ID 把审计记录与节点访问日志一一对上；对账脚本放在 `tianting-server/deploy/ops/`。
6. 不记录：密码、TOTP、恢复码、会话 ID、CSRF 令牌、任何密钥、消息正文。

**验收标准**
- AC-OPS-14-1【后端】：[E1] 操作：对规则 2 中第一批的每一类事件各触发一次（参数化测试）；预期：审计表中各产生一条 `space=ops` 的记录，基座要求的字段和本表"额外字段"齐全。
- AC-OPS-14-2【后端】：[E1] 输入：特征串密码、特征串 TOTP；操作：用它们登录（失败），再用特征串新密码修改密码；预期：审计表全部字段、console-server 日志中都不出现这些特征串。
- AC-OPS-14-3【后端】：[E1] 操作：用 console-server 的审计数据库账号执行 `UPDATE` 和 `DELETE` 审计表；预期：均返回 Postgres 权限错误。
- AC-OPS-14-4【后端】：[E1] 操作：用基座测试模式注入审计写入失败，分别执行连接排查、查看配置检查、打开总览；预期：排查返回失败且 im-server 访问日志中没有对应请求；配置检查返回失败且不含配置数据；总览正常。
- AC-OPS-14-5【后端】：[E1] 操作：用数据库超级用户修改一条运维审计记录的 `reason` 字段，再运行校验命令；预期：校验命令以非 0 退出，并报告从该条开始哈希链断裂。
- AC-OPS-14-6【后端】：[E2a] 操作：执行 20 次排查（覆盖单节点和双节点用户）后运行对账脚本；预期：每条 `ops.troubleshoot.query` 审计的请求 ID 都能在所查询节点的访问日志中找到，结果条数一致；节点访问日志中每条用户级接口请求都有对应审计，差异 0 条。
- AC-OPS-14-7【后端】：[E1] 操作：从网段外发 1000 次请求、未登录发 1000 次 API 请求；预期：审计表条数不变；console-server 的拒绝计数指标增加 2000。

### F-OPS-15 审计日志查看（第一批；导出为 P1）

**规则**

### F-OPS-16 节点运维接口与凭证（第一批）

**描述**：im-server 在内网地址上为 console-server 提供只读接口（第 7.2 节）。取代 v0.1 中"全部节点共用一把静态 token、明文传输"的方案。

**规则**
1. **每节点独立凭证**：console-server 为每个节点持有一把独立的 Ed25519 私钥（节点凭证表中为私钥文件引用）；节点配置自己那把的公钥 `IM_OPS_PUBKEYS=kid:base64`（最多 2 把同时有效，用于轮换）。一个节点的公钥只能验证发给它的请求；节点被攻破也拿不到可以签名的材料。
2. **请求签名**：与 X-5 管理接口使用同一实现（PRD-admin F-KEY-03）：请求头 `X-IM-Caller: console-ops`、`X-IM-Timestamp`、`X-IM-Nonce`、`X-IM-Signature`、`X-IM-Operator: ops:{accountId}`、`X-Request-Id`、`X-IM-Target-Node`；待签名串为 F-KEY-03 规则 2 的 8 行（第 8 行 `X-IM-Target-Node` 必填，且必须等于本节点 `IM_NODE_ID`）。时间戳超出 300 秒、nonce 10 分钟内重复（节点本地内存去重即可）、目标节点不符、签名不符：**401 / 4017**，不返回任何数据。
3. **TLS**：`IM_OPS_ADDR` 绑定非回环地址时必须启用 TLS（`IM_OPS_TLS_CERT` / `IM_OPS_TLS_KEY`，内部 CA 签发，证书服务名为节点凭证表中的 TLS 服务名，如 `n1.ops.internal`）；生产环境违反时拒绝启动。只绑回环地址（同机部署、开发环境）时允许不启用 TLS，但签名照常校验。console-server 只信任内部 CA，并校验服务名与凭证表一致，校验失败时不发送请求。
4. **节点侧来源网段**：`IM_OPS_ALLOWED_CIDRS`，只放行 console-server 所在网段；不在网段内的请求在校验签名之前返回 403 / 4030。生产环境 `IM_OPS_ADDR` 为非回环地址时必须配置。
5. **地址只来自静态配置**：console-server 只向节点凭证表中的地址发请求，不信任注册表中节点自报的地址（F-OPS-05）。
6. **权限隔离**：运维凭证（调用方 `console-ops` 的私钥）只能调用运维接口；X-5 的管理接口调用方不能调用运维接口，`console-ops` 也不能调用 `/admin/*`（不在 `IM_ADMIN_CALLERS` 中）。对外端口 `IM_ADDR` 上不存在运维接口路径（404）。
7. **保护 IM 主流程**：每节点运维接口同时最多 4 个请求，超出返回 429 / 4290；节点侧处理超时 2 秒，console-server 侧单节点超时 1.5 秒；console-server 每个实例对单节点最多 2 个并发；不持有 hub 全局锁做遍历；内存数据用 `runtime/metrics` 读取（不调用 `runtime.ReadMemStats`，避免 STW）。
8. **访问日志**：见 F-OPS-14 规则 5。签名校验失败的日志写明原因（缺少签名 / 时间戳过期 / nonce 重复 / 目标节点不符 / 签名错误），不写密钥和签名值。
9. im-server 不认识后台的账号和角色；权限和"填原因 + 审计"都在 console-server 完成。节点只信任签名范围内的操作人和请求 ID 用于对账。

**验收标准**
- AC-OPS-16-1【后端】：[E1] 输入：对 `POST /internal/v1/connections:query` 构造 5 种请求：不签名、签名错误、时间戳早 6 分钟、重放一个已用过的 nonce、目标节点 ID 写成 n2；预期：都返回 401 / 4017、响应体不含数据；访问日志分别记录对应的失败原因。
- AC-OPS-16-2【后端】：[E2a] 操作：用 n1 的私钥和"目标节点 n1"签名的请求发给 n2；再用 n1 的私钥、"目标节点 n2"签名发给 n2；预期：都返回 401 / 4017。
- AC-OPS-16-3【后端】：[E1] 操作：签名后把请求体中的 userId 从 u1 改为 u2 再发送；预期：返回 401 / 4017。
- AC-OPS-16-4【后端】：[单测] 输入：production 配置组合：① `IM_OPS_ADDR=10.0.0.5:9091` 未配置 TLS；② 同①配置了 TLS 但未配置 `IM_OPS_ALLOWED_CIDRS`；③ `IM_OPS_ADDR=127.0.0.1:9091` 未配置 TLS；④ `IM_OPS_PUBKEYS` 某项不是合法的 Ed25519 公钥；⑤ 生产环境未配置 `IM_NODE_ID`；预期：①②④⑤拒绝启动并列出问题；③正常启动。
- AC-OPS-16-5【后端】：[E2a] 输入：节点凭证表中 n2 的地址被改为一台测试机，该机使用内部 CA 签发、服务名为 `n9.ops.internal` 的证书；操作：触发对 n2 的探测和一次排查，并在测试机抓包；预期：TLS 校验失败，n2 显示"未通过身份校验"；测试机只看到 TLS 握手，没有收到任何 HTTP 请求（即没有收到签名）。
- AC-OPS-16-6【后端】：[E1] 输入：节点 `IM_OPS_PUBKEYS=k1:…,k2:…`；操作：console-server 从 k1 私钥切换到 k2 私钥签名，期间每秒发 1 次探测；之后节点去掉 k1 公钥重启，再用 k1 私钥签名请求；预期：切换期间探测全部成功；去掉 k1 后 k1 签名的请求返回 401 / 4017。
- AC-OPS-16-7【后端】：[E1] 操作：在 `IM_ADDR` 上请求 `/internal/v1/node`；用 `console-ops` 私钥按 X-5 的格式调用一个管理接口；用管理接口调用方的密钥调用 `/internal/v1/node`；预期：依次返回 404、401 / 4017、401 / 4017。
- AC-OPS-16-8【后端】：[E1] 输入：测试模式让 `/internal/v1/config` 处理时人为延迟 1 秒；操作：同时发 5 个合法请求；预期：第 5 个立即返回 429 / 4290；其余 4 个成功。
- AC-OPS-16-9【后端】：[E1] 输入：`IM_OPS_ALLOWED_CIDRS=10.8.2.0/24`；操作：从 `10.8.3.5` 发送合法签名的请求；预期：返回 403 / 4030，访问日志记录"来源网段不允许"，没有进入签名校验。
- AC-OPS-16-10【后端】：[单测] 操作：在基准测试中调用 `/internal/v1/node` 1000 次，读取 runtime/metrics 的 `/sched/pauses/total/other:seconds` 计数变化；预期：增量为 0（接口不触发 STW）。

### F-OPS-17 观测组件访问控制（第一批）

**规则**
1. **Grafana 由 console-server 做认证代理**，只有一套登录和 TOTP：
   - Grafana 使用单独的主机名 `grafana.ops.<内网域名>`（与运维后台不同源，Grafana 页面里的脚本无法调用运维后台接口），只监听 console-server 能访问的地址；
   - 用户在运维后台点"指标"时，console-server 校验会话和角色（`ops_viewer`、`ops_engineer`），签发**一次性票据**（30 秒有效、只能用一次）并跳转；Grafana 主机上的 console-server 代理用票据换取主机专属 Cookie，该 Cookie 绑定原运维会话：原会话失效（退出、过期、改密、改角色）时立即失效；
   - 代理向 Grafana 传 `auth.proxy` 用户头；Grafana 只信任 console-server 的来源地址（`whitelist`），关闭登录表单和匿名访问，所有代理用户映射为 **Viewer**，任何人都不能通过代理获得 Editor / Admin；面板只读（F-OPS-06）；
   - 签发票据时写审计 `ops.grafana.enter`；
   - 会话续期规则见 B-OPS-05。
2. **Prometheus、Alertmanager** 只监听回环地址或只对 console-server、Grafana 所在地址开放（防火墙规则在 `deploy/observability/`）；VPN 用户不能直接访问它们的 UI 和 API。console-server 读取 Alertmanager API（只读）。第二批的静默创建只能经 console-server（F-OPS-18）。
3. **pprof 移出指标端口**（S-OPS-20）：`IM_METRICS_ADDR` 上只保留 `/metrics`，并只对 Prometheus 所在地址开放；pprof 改为 `IM_PPROF_ADDR`，开发环境默认 `127.0.0.1:6060`，生产环境默认关闭，设置时必须是回环地址（否则拒绝启动）。需要排查时在节点主机上通过 SSH 隧道访问，不经过 VPN 直接暴露。
4. `im-loadtest` 改为从 `IM_PPROF_ADDR` 采集堆快照（S-OPS-25）。

**验收标准**
- AC-OPS-17-1：[E1] 操作：从 VPN 网段的测试机直接访问 Grafana 的监听地址；再经运维后台"指标"入口进入 Grafana 后，调用保存面板接口和数据源管理接口；预期：直接访问连接被拒绝或返回 403；经入口进入成功、身份为 Viewer；保存面板和数据源管理都返回 403。
- AC-OPS-17-2：[E1] 操作：截获一次性票据，第一次使用后再用一次；另取一张票据等 31 秒再用；预期：第二次使用和过期票据都失败，跳回运维后台登录页。
- AC-OPS-17-3：[E1] 操作：在运维后台点"退出"后，刷新已打开的 Grafana 页面；预期：Grafana 请求返回 401 并跳回运维后台登录页。
- AC-OPS-17-4：[E1] 操作：`ops_auditor` 和 `ops_superadmin` 访问"指标"入口；预期：返回 403，不签发票据。
- AC-OPS-17-5：[E1] 操作：从 VPN 测试机带 `X-WEBAUTH-USER: admin` 请求头直接访问 Grafana 地址；预期：被拒绝（来源不在 Grafana 的 `whitelist` 中）。
- AC-OPS-17-6：[E1] 操作：从 VPN 测试机访问 Prometheus（9090）和 Alertmanager（9093）的 UI 与 API（含 `POST /api/v2/silences`）；在 console-server 主机上访问同样地址；预期：VPN 测试机连接被拒绝或超时；console-server 主机可以读取。
- AC-OPS-17-7【后端】：[E1] 操作：请求 `IM_METRICS_ADDR` 上的 `/debug/pprof/`；在节点本机请求 `IM_PPROF_ADDR`（`127.0.0.1:6060`）上的 `/debug/pprof/heap`；以 production、`IM_PPROF_ADDR=0.0.0.0:6060` 启动；预期：依次为 404、200、拒绝启动。
- AC-OPS-17-8：[E1] 操作：进入 Grafana 打开一个面板并开启 30 秒自动刷新，不在运维后台做任何操作，测试时钟推进 31 分钟；另一会话在第 20 分钟在 Grafana 中点击打开另一个面板（页面导航）；预期：第一个会话的下一次 Grafana 数据请求返回 401；第二个会话的导航续期，之后 30 分钟内仍可用。
- AC-OPS-17-9：[E1] 操作：从非 Prometheus 所在的内网主机请求 `IM_METRICS_ADDR/metrics`；预期：连接被拒绝（防火墙规则生效）；Prometheus 抓取正常（`up == 1`）。

### F-OPS-18 告警静默（第二批）

## 7. 数据来源与节点运维接口

### 7.1 数据来源

| 数据 | 来源 | 现状与缺口（tianting-server 改造编号见第 15 节） |
|---|---|---|
| 连接数（总览、节点）、就绪 / 下线中、版本、内存、goroutine | console-server 每 5 秒探测 `GET /internal/v1/node` | 接口**缺**（S-OPS-13） |
| 指标图表与告警 | Prometheus 抓取各节点 `IM_METRICS_ADDR/metrics`（15 秒），file_sd 打 `node_id` 标签 | 指标已有；`im_build_info`、`im_ready`、`im_draining`、`phase` 标签、`origin_rejected`、GOMEMLIMIT / 存活内存 / GC CPU 指标**缺**（S-OPS-01～05） |
| 当前连接 | `POST /internal/v1/connections:query`（hub 按 userId 索引，不遍历）；B6 后先查 Presence | 接口**缺**；连接对象不保存建立时间和 IP（`opened` 只是局部变量）**缺**（S-OPS-14） |
| 断开记录 | 节点内存环形缓冲（按用户 50 条、全节点 2 万条）；长期记录在日志 | 缓冲**缺**；握手阶段不写断开指标和断开日志**缺**（S-OPS-01、07、15） |
| 未归属的握手拒绝汇总 | Prometheus `im_disconnects_total{phase="handshake",code=~"4401\|4010\|4009"}` | 随 S-OPS-01 |
| 配置摘要与生产检查 | `GET /internal/v1/config`（由 `internal/config` 生成结构化摘要，检查项来自 `productionProblems`） | **缺**；`productionProblems` 在 `IM_JWT_KEYS` 下漏查与管理密钥相同**（漏洞）**（S-OPS-16、18） |
| 迁移状态 | `GET /internal/v1/db`（只读连接，与 `migrate status` 同一函数） | **缺**；`migrate status` 不输出执行时间和校验和（S-OPS-17、22） |
| 备份记录 | 备份存储 `manifests/` 前缀（console-server 只读凭证） | **缺**：清单输出、加密、上传、定时脚本、textfile 指标都没有（S-OPS-23、28、29） |
| 告警 | Alertmanager API（console-server 内网只读） | 需部署 |
| 审计 | 公共基座（Postgres） | 随基座 |

### 7.2 节点运维接口（im-server，`IM_OPS_ADDR`）

全部只读；用户级接口用 POST 是为了把 userId 放进请求体（不进路径和访问日志），不产生任何副作用。

| 接口 | 返回 | 实现要求 |
|---|---|---|
| `GET /internal/v1/node` | 节点 ID、版本、启动时间、`ready`、`draining`、按平台的连接数、存活内存估算、堆、栈、GOMEMLIMIT、goroutine 数、断开缓冲最早时间 | 计数器读取 O(1)；内存用 `runtime/metrics` |
| `POST /internal/v1/connections:query` `{userId}` | 该用户在本节点的连接列表（F-OPS-08 规则 2 的字段） | 按 userId 索引；与管理后台在线设备接口（PRD-admin G-ADM-06）**共用同一个查询函数**，避免集群化时改两遍 |
| `POST /internal/v1/disconnects:query` `{userId, limit≤50}` | 本节点缓冲中该用户的断开记录 + 缓冲最早时间 | 读时复制 |
| `GET /internal/v1/config` | 结构化配置摘要 + 生产检查项（ID、结论、实际检查内容） | 单测保证不含密钥 |
| `GET /internal/v1/db` | 数据库类型、脱敏位置、连通性、迁移状态（版本、执行时间、校验和） | 独立只读连接 |

### 7.4 集群化后的聚合

| 数据 | 聚合方式 |
|---|---|
| 指标 | Prometheus 抓取全部节点，`sum by` 聚合，`node_id` 筛选 |
| 节点列表 | 节点凭证表 + 主动探测；B6 后注册表只用于发现"未登记"节点 |
| 当前连接 | 第一批扇出到全部静态节点；B6 后 Presence → 只请求相关节点，不可用时扇出 |
| 断开记录 | 扇出到全部节点 → 按时间合并；节点数 > 20 时改为接日志平台（届时另行评估） |
| 配置 | 扇出到全部节点 → 差异视图 |
| 数据库 / 备份 / 审计 | 与节点无关，读共享存储 |

所有扇出：每个 console-server 实例并发上限 8、单节点超时 1.5 秒、对单节点最多 2 个并发；部分失败返回部分结果。
