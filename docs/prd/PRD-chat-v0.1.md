### 1.2 目标

1. 用户不依赖任何业务方，能自己注册、登录、找回账号、改资料。
2. 聊天内容覆盖日常：图片、文件、撤回、引用、@。
3. App 不在前台时能收到通知。
4. 用户能管理自己的会话：置顶、免打扰、删除。
5. 有最基本的内容治理：敏感词拦截、用户举报、后台处理。
6. 不破坏已冻结的规则：不丢不重、多端一致、安全优先（ARCH 第 4 节）。

### 1.3 成功标准

### 4.2 新的 HTTP 接口约定

1. 第一批新增客户端 HTTP 接口，路径前缀 `/v1/`，在对外端口（`IM_ADDR`）上提供；管理接口仍只在管理端口。
2. 请求和响应 JSON；错误 `{code, msg, reason?, details?}`，HTTP 状态取 `errors.json`。错误码新增 `scope: "client"`。
3. 需要登录的接口用 `Authorization: Bearer <token>`，不用 Cookie，token 不进 URL（ARCH S1）。校验和 WS 的 `auth` 相同（4010、4011、4012）。
4. 请求体上限 64 KB。文件内容不经过 im-server。
5. 现有服务端不设 `ReadTimeout`（ARCH 第 7 节，避免断开 WebSocket），`/v1/*` 要在路由层自己设超时。
6. H5 同源访问，沿用 PRD-ui F-UI-03 规则 7。
7. 生产环境只接受 HTTPS（ARCH S2）。

### 4.3 单聊、群聊发送的判定顺序（在 PRD-core F-MSG-01 规则 6 上扩展）

1. 格式（`image` / `file` / `quote` / `mentions` 的结构，4000）。
2. 去重命中 → 返回第一次的 ack（已保存的消息重发一律成功）。
3. 禁言 4031（不扣令牌）。
4. 发送限流 4290。
5. 单聊：新对象配额、对方存在、好友制、拉黑（F-MSG-01 规则 6 第 5～9 步）；群聊：群存在、成员（4043、4033）。
6. **附件校验**（4048、4096）。
7. **引用校验**（4040 `reason`）。
8. **@ 所有人的权限和次数**（4030 `reason`、4293）；过滤 `mentions.userIds`。
9. **敏感词**（4510）。
10. （事务内）陌生人限额 4137，保存并投递。

规则 5～9 失败都已扣发送令牌（C-29 的"被哪一项拒绝就不扣哪一项"不变）；不保存消息。

## 5. C1 账号注册和登录

### F-ACC-01 注册（P0）

**规则**
1. `POST /v1/account/register {username, password, nickname?, inviteCode?, platform, deviceName?}`。按 `IM_REGISTER_MODE`：`closed` 一律 403 / 4030（`reason: registerClosed`）；`invite` 必须带有效邀请码，否则 403 / 4030（`reason: inviteInvalid`，缺失、错误、过期、用完的应答相同）；`open` 不需要邀请码。
2. **`IM_ENV=production` 且 `IM_REGISTER_MODE=open` 时，必须同时 `IM_MOD_ENABLED=1`，否则拒绝启动。**
3. 用户名：去首尾空白并转小写后 4～32 位，`[a-z0-9_-]`，字母开头（是现有 `userId` 规则的子集）。不合法 400 / 4004。
4. **`userId` 就是规范化后的用户名**，不可修改（CH-02）。按不区分大小写检查 `users` 表（含演示和导入用户）的唯一性，已存在 409 / 4095。保留名（`admin`、`root`、`system`、`official`、`tianting`、`support`、`kefu` 等，配置文件维护）也返回 4095。已注销的用户名不能复用。
5. 密码 8～128 个码点；不能等于用户名；不能全是同一个字符；不能在内置弱口令表里（400 / 4000，`reason: passwordWeak`）。用 Argon2id 存储，和 console-server 同一算法（`internal/secret`），参数未校准。
6. 昵称 1～32 个码点，不传时等于用户名；C6 上线后要过敏感词（F-MOD-02 规则 2）。
7. **防枚举**：4095 必然暴露用户名是否存在。`invite` 模式先校验邀请码再查用户名，没有有效邀请码的人得不到这个信号。`open` 模式按 IP 限制注册请求（每 IP 每小时 20 次，未校准，429 / 4290）。这条路径要写进 PRD-social 11.2 节的探测预算，1.3 节的指标改为"按账号"且注明注册路径单独按 IP 计（第 16 节）。
8. 成功：同一事务写用户和账号、扣减邀请码；响应 `{userId, accessToken, accessExpiresAt, refreshToken, refreshExpiresAt, recoveryCode}`。`recoveryCode` 只返回这一次（F-ACC-05）。
9. 请求参数之外不收集手机号、邮箱、实名信息（CH-23 的默认假设）。

**异常**
- 同一用户名并发注册：只有一个成功，其他 4095。
- 事务失败：邀请码不扣减，用户不产生。
- Argon2 计算占 CPU：`/v1/account/*` 有并发闸门，满了 503 / 5030（未校准：同时 8 个）。

**验收标准**
- AC-ACC-01-1【后端】：输入 `IM_REGISTER_MODE=invite`、有效邀请码、用户名 `Alice_1`、合法密码；操作 注册；预期 成功，`userId=alice_1`，返回 token 和恢复码；token 能通过 WS `auth`；错误码 —。

### F-ACC-02 登录（P0）

**规则**
1. `POST /v1/account/login {username, password, platform, deviceName?}`，用户名按 F-ACC-01 规则 3 规范化。响应同注册（没有 `recoveryCode`）。
2. 用户不存在、没有账号记录（演示和导入用户）、密码错误、已注销：**响应相同**，401 / 4018；不存在时也做一次哈希计算，让响应时间不可区分。
3. 失败限制：按"用户名 + IP"累计，15 分钟内 5 次，之后 429 / 4294（`details.retryAfterSeconds`），不自动重试。另外每 IP 每分钟 20 次（4290），防止撞库。不按用户名单独全局锁，否则任何人都能把别人锁死。
4. 校验密码通过后才判断封禁：封禁中 403 / 4034（`details.bannedUntil`），文案沿用 F-UI-43。
5. 登录成功创建一条设备会话（F-ACC-03）。不踢其他设备（CH-04）。

**异常**：数据库不可用 503 / 5030。密码哈希参数升级后，旧哈希登录成功时重算（不改变应答）。

**验收标准**
- AC-ACC-02-1【后端】：输入 正确的用户名和密码（大小写不同的用户名）；操作 登录；预期 成功，token 能连接；错误码 —。
- AC-ACC-02-2【后端】：输入 不存在的用户名；演示用户（无账号记录）；已注销用户；密码错误；操作 分别登录；预期 都是 401，响应体完全相同；错误码 4018。
- AC-ACC-02-3【后端】：输入 不存在的用户名和存在的用户名（密码错误），各 100 次；操作 比较响应时间中位数；预期 差值不超过 20%（未校准）；错误码 4018。
- AC-ACC-02-4【后端】[IM 钟]：输入 同一用户名 + IP 连续 5 次密码错误；操作 第 6 次用正确密码；15 分钟后再试；预期 第 6 次 429，`details.retryAfterSeconds` 存在；15 分钟后成功；错误码 4294。
- AC-ACC-02-5【后端】：输入 u1 被 IP-A 锁定；操作 从 IP-B 用正确密码登录 u1；预期 成功；错误码 —。
- AC-ACC-02-6【后端】：输入 封禁中的用户；操作 用错误密码、正确密码分别登录；预期 依次 401 / 4018、403 / 4034 带 `bannedUntil`；错误码 4018、4034。
- AC-ACC-02-7【后端】：输入 u1 已在 Android 登录；操作 再从 iOS 登录；预期 两边都在线（AC-AUTH-02-5 不变）；错误码 —。
- AC-ACC-02-8【前端】：输入 服务端返回 4018；操作 登录；预期 提示"用户名或密码错误"，密码框清空，用户名保留；错误码 4018。
- AC-ACC-02-9【前端】：输入 服务端返回 4294，`retryAfterSeconds=600`；操作 登录；预期 提示"尝试次数过多，请 10 分钟后再试"，不自动重试；错误码 4294。

### F-ACC-03 会话续期与设备会话（P0）

**规则**
1. 每次账号登录产生一条**设备会话** `sid`：`{sid, userId, platform, deviceName, createdAt, lastSeenAt, refreshHash, revokedAt}`。access token 增加 `sid` 声明；`POST /admin/users/token` 和 `/demo/login` 签发的 token 没有 `sid`，行为和现在完全一样。
2. `auth` 时除现有的令牌版本号外，有 `sid` 的 token 还要检查会话没有被吊销，已吊销：`kicked/sessionRevoked`，关闭码 4012。
3. refresh token 是不透明随机串，服务端只存哈希。`POST /v1/account/token/refresh {refreshToken}` 返回新的一对，旧的立即作废（轮换）；**用已作废的 refresh token 请求**：吊销这条设备会话，401 / 4019。滑动续期，最长不超过 `IM_REFRESH_TTL`（从最近一次刷新起算）。
4. 轮换的网络重试：旧 refresh token 作废后 30 秒内（未校准）用同一个旧值重试，返回同样的新 token，不算重放（否则弱网时用户被无故踢出）。
5. SDK 行为：access token 剩余不足 24 小时、或启动时已过期 → 先刷新再连接；连接中到期前主动刷新，用 1000 断开后立即重连（持续不足 1 秒不显示连接提示，F-CONN-02 不变）。**刷新失败才回登录页**。
6. `kicked/tokenExpired`（4011）：账号模式下 SDK 先尝试刷新一次，成功就重连，不弹窗；失败按 AC-AUTH-02-4 处理。演示模式没有 refresh token，行为不变。
7. 存储：Android 用现有 Keystore 加密文件、iOS 用现有 Keychain，都增加 refresh token；H5 沿用 D4，只放 `sessionStorage`，**关闭标签页后重新登录**（不做"记住我"）。
8. 第一批不提供设备列表页面（后续批"多端同时在线"）。

**异常**：refresh 时用户已封禁 403 / 4034；已强制下线（令牌版本号变了）401 / 4019。

**验收标准**
- AC-ACC-03-1【后端】：输入 有效 refresh token；操作 刷新；预期 返回新 access、新 refresh；新 access 能连接；错误码 —。
- AC-ACC-03-2【后端】[IM 钟]：输入 refresh token R1 已刷新过；操作 31 秒后再用 R1 刷新，然后用 R1 换来的 R2 刷新；预期 R1 请求 401；这条设备会话被吊销，R2 也 401，它的 access token `auth` 收到 `kicked/sessionRevoked`；错误码 4019。
- AC-ACC-03-3【后端】[IM 钟]：输入 R1 已刷新；操作 10 秒内用 R1 重试；预期 返回和第一次相同的新 token，会话不被吊销；错误码 —。
- AC-ACC-03-4【后端】[IM 钟]：输入 refresh token 91 天没有使用；操作 刷新；预期 401；错误码 4019。
- AC-ACC-03-5【后端】：输入 `POST /admin/users/token` 签发的 token；操作 连接、发消息；查声明；预期 没有 `sid`，和现在行为一致；错误码 —。
- AC-ACC-03-6【后端】：输入 用户被强制下线；操作 用之前的 refresh token 刷新；预期 401；错误码 4019。
- AC-ACC-03-7【前端】（Android、iOS）[IM 钟]：输入 access token 已过期、refresh 有效，App 冷启动；操作 观察；预期 不出现登录页和弹窗，直接进入会话列表并连接成功；错误码 —。
- AC-ACC-03-8【前端】（Android、iOS）：输入 refresh token 已被吊销；操作 冷启动；预期 回登录页，提示"登录已失效，请重新登录"；错误码 4019。
- AC-ACC-03-9【前端】（H5）：输入 账号登录的标签页；操作 刷新页面；关闭后新开标签页；检查 `localStorage`；预期 刷新后仍登录；新标签页回登录页；`localStorage` 里没有 token；错误码 —。
- AC-ACC-03-10【前端】：输入 连接中的账号会话，access token 将在 1 小时内到期；操作 观察到期前后 2 分钟；预期 自动换新 token 并重连，不弹窗，到期后消息照常收发；错误码 —。

### F-ACC-04 退出、改密与下线（P0）

**规则**
1. 退出登录（F-AUTH-05、F-UI-16 不变）增加：先调用 `POST /v1/account/logout`（Bearer，幂等），吊销当前 `sid` 和它的推送令牌，再用 1000 断开。网络不通时仍然本地退出，服务端的 `sid` 等到期或下次吊销。
2. 改密 `POST /v1/account/password {oldPassword, newPassword}`：旧密码错误 401 / 4018（计入 F-ACC-02 规则 3 的失败次数）；新密码规则同注册。
3. 改密成功：**当前设备保持登录**（响应返回新 token），其他设备会话全部吊销，在线连接收到 `kicked/passwordChanged`（4012），它们的推送令牌全部删除。需要 `delivery.Router` 支持按 `sid` 排除（第 11.4 节）。
4. 现有强制下线（F-AUTH-03 规则 2）和封禁（F-ADM-13）同时吊销该用户全部设备会话和推送令牌。
5. 不认识 `passwordChanged`、`sessionRevoked` 的老 SDK 按关闭码 4012 处理（"账号已被下线"）。

**异常**：令牌删除或吊销写库失败：改密整体回滚，返回 5000，旧密码仍有效。D1 改密时 D2 正在刷新：刷新在吊销之后的返回 4019。

**验收标准**
- AC-ACC-04-1【后端】：输入 u1 在设备 D1、D2 登录；操作 D1 退出；预期 D1 的 refresh 不可用（4019），D1 的 access 再 `auth` 收到 `kicked/sessionRevoked`；D2 不受影响；错误码 4019。
- AC-ACC-04-2【后端】：输入 u1 在 D1、D2 在线；操作 D1 改密；预期 D1 连接不断，响应的新 token 可用；D2 收到 `kicked/passwordChanged` 并以 4012 关闭；D2 的 refresh 401；错误码 4019。
- AC-ACC-04-3【后端】：输入 旧密码错误；操作 改密；预期 401，密码不变，其他设备不受影响；错误码 4018。
- AC-ACC-04-4【后端】：输入 u1 有两条设备会话；操作 管理接口强制下线；预期 两条都吊销，推送令牌表里没有 u1 的记录；错误码 —。
- AC-ACC-04-5【前端】：输入 D2 收到 `kicked/passwordChanged`；操作 观察；预期 不重连，弹窗"密码已修改，请重新登录"，确定后回登录页并清空本地数据；错误码 —。
- AC-ACC-04-6【前端】：输入 网络断开时点退出；操作 确认退出；预期 本地仍退出并回登录页，token 被清除；错误码 —。

### F-ACC-05 找回密码（P0）

**规则**
1. 注册时生成 1 个恢复码（16 位，易读字符），服务端只存哈希，只显示一次。
2. `POST /v1/account/recover {username, recoveryCode, newPassword, platform}`：用户名不存在、恢复码错误、已用过：**相同响应** 401 / 4018，和登录共用失败限制。
3. 成功：改密码；吊销全部设备会话；恢复码作废并生成新的，随响应返回一次；响应同时带新 token。
4. 恢复码丢失：走客服。`support` 核实身份后在后台生成**一次性重置码**（F-ACC-09 规则 4，有效 30 分钟），用户在同一接口用重置码代替恢复码。**核实身份的方法第一批没有技术手段**，要人工判断，这是用户名方案的主要缺点（CH-01）。
5. 登录后可以"重新生成恢复码"（要输入当前密码），旧码立即失效。

**异常**：新密码不合规：400 / 4000，恢复码不作废。恢复码正确但账号封禁：403 / 4034，不改密码。

**验收标准**
- AC-ACC-05-1【后端】：输入 正确的恢复码和新密码；操作 找回；预期 新密码可登录，旧密码 401；全部旧设备会话吊销；响应带新恢复码；旧恢复码再用 401；错误码 4018。
- AC-ACC-05-2【后端】：输入 不存在的用户名；错误的恢复码；已用过的恢复码；操作 分别找回；预期 都是 401，响应体相同；错误码 4018。
- AC-ACC-05-3【后端】[IM 钟]：输入 同一用户名 + IP 连续 5 次恢复码错误；操作 第 6 次用正确恢复码；预期 429；错误码 4294。
- AC-ACC-05-4【后端】：输入 登录后重新生成恢复码，当前密码错误 / 正确；操作 分别请求，再用旧码找回；预期 错误时 401，码不变；正确时旧码失效；错误码 4018。
- AC-ACC-05-5【前端】：输入 找回成功；操作 观察；预期 显示新恢复码，确认保存后进入会话列表；错误码 —。

### F-ACC-07 与演示登录、管理接口并存（P0）

**规则**
1. **三种入口并存，共用同一张 `users` 表和同一种 token**：账号登录（`/v1/account/*`）、演示登录（`/demo/login`，`IM_DEMO_LOGIN=1`，生产拒绝启动，ARCH S4 不变）、管理接口（`POST /admin/users/token`，scope `token.issue`，只在管理端口）。
2. 演示和导入的用户没有账号记录，不能密码登录（4018），要用密码登录必须由后台生成重置码（F-ACC-09 规则 4）后设置。

## 6. C2 图片和文件消息

### F-FILE-01 上传流程（P0）

**规则**
1. `POST /v1/files/uploads {kind: image|file|avatar, name, size, mime, sha256, thumb?: {size, mime, sha256}}` → `{fileId, put: {url, headers, expiresAt}, thumbPut?}`。预签名 PUT 有效 15 分钟（未校准），把大小和 SHA-256 写进签名，内容不符时对象存储拒绝。
2. 客户端直接 PUT 到对象存储，**文件内容不经过 im-server**。第一批不做分片和断点续传，失败从头重传。
3. `POST /v1/files/{fileId}/complete`：服务端 HEAD 核对大小；读取前 4 KB 嗅探真实类型，与声明的 `mime` 矛盾或属于禁止类型：删除对象，415 / 4150。成功后状态 `ready`，响应 `{fileId, size, mime}`。
4. 对象键由服务端生成（随机），不包含文件名和用户 ID。文件名只存数据库。
5. 配额：按声明大小扣当天额度，超出 429 / 4292（SDK 不重试）。申请失败不扣，放弃的上传不退（防止滥用）。
6. 文件名：1～255 字节，去掉路径分隔符和控制字符，显示时按纯文本（ARCH S12）。
7. 对象存储不可用：503 / 5032，可重试。

**异常**：断网后重传用新的 `fileId`；未 `complete` 或未绑定消息的上传由定时任务清理（F-FILE-06）。

**验收标准**
- AC-FILE-01-1【后端】：输入 1 MiB 的 png，声明正确；操作 申请、PUT、complete；预期 状态 `ready`，对象键不含文件名和 userId；错误码 —。
- AC-FILE-01-2【后端】：输入 申请时声明 1 MiB，实际 PUT 2 MiB；声明的 sha256 与内容不符；操作 PUT；预期 对象存储拒绝，complete 返回 404；错误码 4048。
- AC-FILE-01-3【后端】：输入 声明 `image/png`，内容是 HTML；操作 complete；预期 415，对象被删除；错误码 4150。
- AC-FILE-01-4【后端】：输入 当天已用 2 GiB；操作 申请 1 字节；预期 429，SDK 不重试；次日可用；错误码 4292。
- AC-FILE-01-5【后端】：输入 对象存储不可用（测试替身返回 503）；操作 申请上传；预期 503；im-server 其他功能正常（WS 收发不受影响）；错误码 5032。
- AC-FILE-01-6【后端】：输入 未登录；用别人的 `fileId` complete；操作 分别请求；预期 依次 401（4010）、404；错误码 4010、4048。
- AC-FILE-01-7【后端】：输入 文件名 `../../etc/passwd`、含 `\n` 和控制字符；操作 申请；查数据库；预期 存储的是去掉分隔符和控制字符后的名字；错误码 —。
- AC-FILE-01-8【后端】：输入 100 MiB 的文件上传；操作 观察 im-server 存活内存；预期 增长 ≤ 10 MiB（未校准），证明内容不经过服务端；错误码 —。

### F-FILE-02 图片消息（P0）

**规则**
1. `send {type: "image", body: {image: {fileId, thumbFileId, width, height}}}`。服务端用自己的记录覆盖 `size`、`mime`，下发时带上；客户端声明的 `width`、`height` 只做范围校验（1～10000）。
2. 允许：jpeg、png、webp、gif。HEIC 由 iOS 客户端转 JPEG。SVG、BMP、TIFF 不允许。
3. **缩略图由发送端客户端生成**（长边 ≤ 480，≤ 512 KiB），和原图一起上传（CH-08）；服务端不解码图片。
4. **发送前重新编码，去掉 EXIF 和 GPS**（CH-09）：H5 用 canvas，Android、iOS 用系统图片接口；长边超过 4096 时缩放。动图 GIF 不重新编码（否则丢动画），EXIF 问题不存在于 GIF。
5. `lastMsg`：`type=image`、`text=""`；客户端显示"[图片]"。
6. 聊天页：按 `width`/`height` 预留占位，先显示缩略图；点击全屏查看原图，支持缩放和保存。加载失败显示占位和"点击重试"；过期显示"图片已过期"。
7. 发送状态机沿用 F-MSG-03，增加"上传中"（带进度，可取消）；上传失败标记失败，手动重发时重新上传。`clientMsgId` 不变。
8. 老版本客户端显示"[暂不支持的消息]"（已核实）。

**异常**：缩略图上传失败：整条消息按上传失败处理，不发 `send`。原图过期但缩略图还在：两者同时过期，不单独保留。解码失败：显示占位，可以当文件下载。

**验收标准**
- AC-FILE-02-1：输入 u1 给 u2 发 2 MiB 的 jpeg；操作 发送；预期 u2 收到 `type=image`，先显示缩略图，点开看到原图；两边 `size`、`mime` 一致；错误码 —。

- AC-FILE-02-3【后端】：输入 `fileId` 是别人的；是 `kind=file`；未 complete；已绑定到另一条消息；操作 分别发图片；预期 依次 404 / 4048、400 / 4000（`reason=fileKindMismatch`）、4096、4096；消息未保存；错误码 4048、4000、4096。
- AC-FILE-02-4【前端】：输入 带 GPS 和相机型号 EXIF 的 jpeg；操作 发送后从对象存储下载原图和缩略图；预期 用 EXIF 解析工具读不到任何 EXIF 字段；错误码 —。

### F-FILE-03 文件消息（P0）

**规则**
1. `send {type: "file", body: {file: {fileId}}}`；服务端下发 `{fileId, name, size, mime}`。
2. 文件内容不重新编码，**EXIF 等元数据原样保留**；用"文件"方式发图片时，发送前提示"文件会保留原始信息（可能包含位置）"。
3. 聊天页：显示类型图标（按扩展名）、文件名（中间省略）、大小。点击下载，显示进度；下载完成后用系统方式打开或保存。
4. 下载的响应带 `Content-Disposition: attachment`，H5 不在页面内打开，避免在对象存储域名下执行内容。对象存储用独立域名，和 App 不同源。
5. `lastMsg`：`type=file`、`text=""`；客户端显示"[文件] "加文件名。文件名来自消息，由客户端渲染；摘要不走服务端。
6. 禁止类型见 F-FILE-05。

**异常**：下载时地址过期：SDK 重新申请一次；再失败提示"下载失败"。文件名全部被清洗为空：用 `file` 显示。

### F-FILE-04 访问控制（P0）

**规则**
1. `POST /v1/files/{fileId}/url {variant: "original"|"thumb"}` → `{url, expiresAt}`。预签名 GET，TTL 300 秒。
2. 只有同时满足才发地址：请求者**当前**能访问这条消息——单聊参与者；或当前群成员且消息 seq ≥ 他的 `minSeq`（包括 F-CVS-03 的清空位置）；消息没有被撤回、删除；文件没有过期。发送者在绑定消息前可以访问自己的上传。
3. 其他情况一律 **404 / 4048**，响应相同，不暴露文件是否存在。
4. **已知限制（写进接入说明）**：地址发出后到过期前，持有地址的人仍能下载；撤回、退群不能收回已发出的地址和已下载到本地的文件。不用鉴权代理的原因见 CH-06。
5. 客户端不把预签名地址持久化，不写日志；按需申请，过期重新申请。
6. 每人每分钟 120 次申请（未校准，4290）；批量申请缩略图由 SDK 合并节流。

**异常**：对象存储不可用时地址仍然可以生成（只是签名），下载由客户端按失败处理。消息状态和文件状态不一致时一律按不可访问（4048）。

**验收标准**
- AC-FILE-04-1【后端】：输入 单聊 u1、u2 的图片；操作 u3 申请地址；预期 404，响应与"不存在的 fileId"完全相同；错误码 4048。
- AC-FILE-04-2【后端】：输入 群 g1 的文件；操作 成员申请成功；把他移出群后再申请；预期 移出后 404；错误码 4048。
- AC-FILE-04-3【后端】：输入 `historyVisible=false`，D 入群前的图片；操作 D 申请地址；预期 404；改为 `true` 后成功；错误码 4048。
- AC-FILE-04-4【后端】[IM 钟]：输入 已发放的地址；操作 真实时间 301 秒后 GET（对象存储用真实时钟）；预期 对象存储拒绝；错误码 —。
- AC-FILE-04-5【后端】：输入 图片消息被撤回 / 被后台删除；操作 参与者申请地址；预期 都是 404；错误码 4048。
- AC-FILE-04-6【后端】：输入 不带 Authorization 直接访问对象键（无签名）；操作 GET；列举桶；预期 都被对象存储拒绝；错误码 —。
- AC-FILE-04-7【后端】：输入 申请地址和下载；操作 扫描 im-server 日志；预期 搜不到预签名查询串和文件名特征串；错误码 —。

### F-FILE-05 类型与安全（P0）

**规则**
1. 文件禁止的扩展名和真实类型（配置文件维护）：可执行和脚本类，如 `exe`、`msi`、`bat`、`cmd`、`com`、`scr`、`ps1`、`vbs`、`js`、`jar`、`apk`、`ipa`、`dmg`、`pkg`、`deb`、`rpm`、`sh`。415 / 4150。**这不能替代病毒扫描**（CH-09）。
2. 第一批不做病毒扫描。文件表预留 `scanState`（默认 `skipped`）。内部 / 小范围可以接受，**面向公众开放前要重新决定**（CH-23）。
3. 下载前提示："文件来自其他用户，请确认来源可信"（只在下载非图片时，每个会话首次）。
4. 客户端渲染文件名按纯文本；图片只用系统解码器。

**异常**：扩展名和真实类型矛盾：按更严格的处理，拒绝。无法识别的真实类型：按 `application/octet-stream` 放行（文件消息）或拒绝（图片消息）。

**验收标准**
- AC-FILE-05-1【后端】：输入 `a.exe`；`a.EXE`；`a.pdf.exe`；扩展名 `.pdf` 但内容是 PE 可执行文件；操作 分别申请并 complete；预期 前三个申请时 415；第四个 complete 时 415 且对象被删；错误码 4150。
- AC-FILE-05-2【后端】：输入 F-FILE-05 的配置新增 `xyz`；操作 重启后上传 `a.xyz`；预期 415；错误码 4150。
- AC-FILE-05-3【前端】：输入 群里的 zip 文件；操作 首次点下载；预期 出现来源提示；确认后下载；同一会话第二次不再提示；错误码 —。

### F-FILE-06 生命周期（P0）

**规则**
1. 一个文件只能绑定一条消息（不去重、不秒传，避免成为存在性探测手段）。后续批转发时再定义引用方式。
2. 状态：`pending` → `ready` → `attached` → `revoked` → 物理删除；或 `attached` → `expired` → 物理删除；或 `pending` / `ready` 超过 24 小时未绑定 → 物理删除。
3. **保留期**：绑定后 180 天（`IM_FILE_RETENTION_DAYS`）到期，对象删除，消息保留，显示"已过期"（CH-10）。
4. **撤回、后台删除**：立即停止发放地址（`revoked`）；对象保留到隔离期结束（默认 30 天，同 F-ADM-32 和 CH-17）后物理删除。
5. 举报证据引用的文件：保留到证据到期（F-MOD-03 规则 6），过程中不发放给普通用户。
6. 解散群、退群、删除会话：**不**删除文件（其他人可能还能访问）；保留期到了再删。
7. 定时任务 `file_purge` 每小时运行，一批 1000 个（未校准），和现有 `quarantine_purge` 同样的方式。对象存储删除失败下次重试，不影响消息。
8. 备份：数据库备份（ARCH 3.4）不含文件内容；文件的持久性靠对象存储自身（多副本、版本）。恢复数据库到较早时间点后，文件表和对象可能不一致：缺对象的显示"已过期"，多余对象按孤儿清理。

**异常**：清理任务中途退出：下次继续。消息被撤回时文件已过期：只改状态，不报错。

**验收标准**
- AC-FILE-06-1【后端】[IM 钟]：输入 `ready` 但未绑定的上传；操作 推进 25 小时并运行 `file_purge`；预期 对象和记录都被删除；错误码 —。
- AC-FILE-06-2【后端】[IM 钟]：输入 已绑定的图片；操作 推进 181 天并运行清理；预期 对象不存在；`sync` 消息还在，带 `expired=true`；申请地址 404；错误码 4048。
- AC-FILE-06-3【后端】[IM 钟]：输入 被撤回的图片；操作 第 29 天检查、推进到第 31 天运行清理；预期 第 29 天对象还在且用户申请 404；第 31 天对象被删除；错误码 4048。
- AC-FILE-06-4【后端】：输入 同一 `fileId`；操作 再发一条消息；预期 4096；用原 `clientMsgId` 重发得到原 ack；错误码 4096。
- AC-FILE-06-5【后端】：输入 对象存储删除接口返回错误；操作 运行清理；预期 记录保留，指标 `im_job_runs_total{job="file_purge",result="error"}` 增加，下次重试成功；错误码 —。
- AC-FILE-06-6【前端】：输入 `expired=true` 的图片和文件消息；操作 查看；预期 分别显示"图片已过期""文件已过期"，不发申请地址的请求；错误码 —。

## 7. C3 离线推送

### F-APN-01 设备令牌（P0）

**规则**
1. WS 命令 `pushRegister {provider: "apns"|"fcm", token, env?: "sandbox"|"production", appId}`；`pushUnregister {}`。令牌绑定当前 `sid`。**没有 `sid` 的连接（演示、管理接口 token）**：令牌只绑定 `userId`，按"该用户没有任何活跃连接"判断是否推送，退出时由客户端注销（测试环境用）。
2. 同一个令牌只属于一个用户：另一个账号在同一设备登录时，把令牌从旧账号移走。
3. 通道返回令牌失效（APNs 410 / `BadDeviceToken`、FCM `UNREGISTERED`）：删除这条令牌。
4. 退出、改密、强制下线、封禁、注销都删除令牌（F-ACC-04）。
5. 权限：Android 13 及以上和 iOS 都要系统授权。用户拒绝时不注册令牌，"设置 → 通知"显示"系统通知已关闭"和前往系统设置的入口。不在首次启动就弹授权，在首次登录进入会话列表后弹。
6. 令牌不进日志和审计（只记 provider 和令牌的 SHA-256 前 8 位）。

**异常**：`pushRegister` 令牌为空或超长：400 / 4000。App 拿不到令牌（系统错误）：不报错，下次启动重试，设置页显示状态。令牌刷新：客户端重新注册，覆盖旧值。

**验收标准**
- AC-APN-01-1【后端】：输入 u1 注册令牌 T；操作 u2 用同一 T 注册；给 u1、u2 各发消息；预期 T 只归 u2，只收到 u2 的通知；错误码 —。
- AC-APN-01-2【后端】：输入 假通道返回 APNs 410；FCM `UNREGISTERED`；操作 发一次推送；预期 令牌被删除，下一条消息不再调用通道；错误码 —。
- AC-APN-01-3【后端】：输入 u1 有令牌；操作 分别退出、改密（其他设备）、强制下线、封禁；预期 相应令牌被删除，之后的消息不调用通道；错误码 —。
- AC-APN-01-4【后端】：输入 注册令牌；操作 扫描日志和审计；预期 搜不到令牌原文；错误码 —。
- AC-APN-01-5【前端】（Android、iOS）：输入 用户拒绝通知授权；操作 打开"设置 → 通知"；预期 显示"系统通知已关闭"和入口；没有发 `pushRegister`；错误码 —。
- AC-APN-01-6（手工）：输入 Android 13+、iOS 真机；操作 首次登录；预期 进入会话列表后才出现系统授权弹窗；同意后设备收到测试通知；错误码 —。

### F-APN-02 什么时候推（P0）

**规则**
1. 推送的消息：`text`、`image`、`file`。**不推**：`tip`、`custom`、自己发的、撤回和删除事件、系统通知 `push` 帧、好友申请（第 2.4 节）。
2. 按**设备**判断，不按用户：设备有活跃连接就不推；手机后台 + PC 在线，手机照样推（第一批不做"PC 在线手机静音"）。
3. 活跃连接：最近 `IM_PUSH_LIVE_WINDOW`（45 秒）内收到过帧，且没有上报后台状态。原生 SDK 进入后台时发 `presence {state: "background"}`，回到前台发 `foreground`。
4. **断线补推**：连接异常断开（关闭码不是 1000），该设备没有其他连接，断开前 `IM_PUSH_GRACE`（120 秒）内下发过消息且仍有未读 → 补发一条聚合通知"你有新消息"。这是为了覆盖"连接已死但服务端还以为在线"这段时间。
5. 免打扰按 F-MEN-03。被踢下线的设备没有令牌，不推。
6. 合并：同一设备同一会话 5 秒内最多 1 条，后续合并；同一会话使用相同的 collapse id（APNs `apns-collapse-id`，FCM `collapse_key`），在系统通知栏只留最新的。
7. **推送不影响发送路径**：在 `send` 的 ack 之后异步入队；队列在内存里，有界（未校准：10 万条），满了丢弃并计数；进程崩溃丢失的只是通知，消息靠 `sync` 不丢。
8. 重试：可重试的错误（429、5xx）指数退避最多 3 次；通知过期时间 24 小时。

**异常**：通道长时间不可用：重试用尽后丢弃并计数，不积压，不影响消息。用户在通知到达前已读：通知仍可能显示（规则见 F-APN-04 规则 2）。

**验收标准**
- AC-APN-02-1【后端】：输入 u2 无连接、有令牌，u1 发 `text`、`image`、`file`；操作 观察假通道；预期 各 1 次调用（超过合并窗口发送）；错误码 —。
- AC-APN-02-2【后端】：输入 u2 在线（前台活跃）；操作 u1 发消息；预期 2 秒内假通道无调用；错误码 —。
- AC-APN-02-3【后端】：输入 u2 手机连接上报 `background`；PC 连接活跃；操作 u1 发消息；预期 手机令牌有调用；错误码 —。
- AC-APN-02-4【后端】：输入 群提示消息；发送者自己的其他离线设备；撤回事件；操作 观察假通道；预期 都没有调用；错误码 —。
- AC-APN-02-5【后端】[IM 钟]：输入 u2 连接 46 秒没有帧（测试模式下关闭服务端空闲断开）；操作 u1 发消息；预期 假通道有调用；错误码 —。

## 8. C4 撤回、引用、@

### F-RCL-01 发送者撤回（P0，CH-15）

**规则**
1. WS 命令 `recall {convId, msgId}`。发送者可以在消息 `ts` 后 120 秒内撤回（按服务端时间，[IM 钟]）。超时 4097。
2. 适用于 `text`、`image`、`file`、`custom`。`tip` 400 / 4000。自己给自己的消息也可以。
3. 校验顺序：格式 → 会话权限（4032、4033、4043）→ 消息存在（4044）→ 已撤回（幂等成功，不再发事件）→ 已被后台删除（4044）→ 权限和时限。
4. **禁言和被拉黑不影响撤回**（撤回是收回内容，不是发言）。不计入发送限流；单独限制每人每分钟 20 次（未校准，4290）。
5. 服务端：同一事务里清空正文，标记 `recalled=true`、`recalledAt`、`recalledBy`；seq 不变不留空洞；原文进隔离区（CH-17）；如果是最后一条，更新 `conv_seq` 摘要。
6. 未读数公式不变（PRD-core F-CONV-02 规则 1），撤回不减未读；`updatedAt` 不变，会话不重新排序。

## 9. C5 会话置顶、免打扰、删除

### F-CVS-01 置顶（P0）

**规则**
1. WS 命令 `convSet {convId, pinned?, muted?}`，至少一项。幂等。
2. 每人最多置顶 20 个（超出 4220，文案"最多置顶 20 个会话"）。
3. 排序：置顶的在最前（`pinnedAt` 倒序），其余按 `updatedAt` 倒序，时间相同按 `convId`（F-CONV-01 规则 3 扩展）。

### F-CVS-02 免打扰（P0）

**规则**
1. 按会话，单聊和群聊都可以。不做全局免打扰和时段。
2. 不推送，例外见 F-MEN-03。
3. 未读照常计算，`convs` 的 `unread` 不变。
4. **总未读不含免打扰会话**（PRD-ui F-UI-23 变更：标签角标、`document.title`、iOS 角标都不含）。
5. 列表显示：免打扰会话的未读显示为小红点（无数字），摘要前显示"[N 条]"，右侧有免打扰图标。
6. 在线时收到免打扰会话的消息：列表更新，不响铃。

**异常**：设置读取失败时按没有免打扰处理（宁可多推一条，不漏）。

**验收标准**
- AC-CVS-02-1【后端】：输入 u2 免打扰 c2c 会话，离线；操作 u1 发消息；预期 假通道无调用；`unread` 增加；错误码 —。
- AC-CVS-02-2【前端】：输入 普通会话未读 2、3，免打扰会话未读 5；操作 看标签角标和 `document.title`（H5）；预期 显示 5；错误码 —。
- AC-CVS-02-3【前端】：输入 免打扰会话未读 5；操作 看列表；预期 小红点、"[5 条]"、免打扰图标；错误码 —。
- AC-CVS-02-4【前端】：输入 总未读全在免打扰会话；操作 看 H5 标题；预期 `document.title` 为"天听"；错误码 —。

### F-CVS-03 删除会话（P0）

**规则**
1. WS 命令 `convDelete {convId, upToSeq}`，`upToSeq` 是客户端看到的最大 seq，服务端取 `min(upToSeq, maxSeq)`。只影响自己。
2. 效果：从自己的会话列表消失；`clearedSeq = upToSeq`；已读推进到 `upToSeq`；**我这边这段历史也不再可见**（`minSeq = max(原值, clearedSeq + 1)`，`sync` 和文件地址都按这个）。对方和其他成员不受影响；后台查询不受影响。
3. 有新消息（seq > `clearedSeq`）时重新出现，只显示新消息。清除置顶，**保留免打扰**（否则删掉一个免打扰的群，下一条消息又开始响）。
4. 群：删除会话不是退群。还在成员列表，"我的群聊"里还能看到，从那里进入时显示空的聊天页；只有 `tip` 也算新消息，会重新出现。
5. 并发：`upToSeq` 之后到达的消息不会被清除，会话马上重新出现。
6. **`convs` 增加 `deleted: [{convId, clearedSeq}]`（只含群，单聊不需要）**。原因：三套 SDK 把 `convs` 里消失的群当作"你已不在该群"（PRD-core F-GRP-03 规则 4）。SDK 必须先查这个列表，不生成 `removed` 快照；`truncated` 时不推断的规则不变。这条不改会让用户看到错误提示。
7. 客户端确认框"删除后聊天记录不再显示，确定删除？"；清除本地消息、草稿、缓存文件。
8. 不存在的或已删除的再删：幂等成功。

**异常**：`upToSeq` 小于已有的 `clearedSeq`：不回退，幂等成功。写入失败：5000，客户端恢复显示。本地清除失败：下次启动再清，服务端状态不受影响。

**验收标准**
- AC-CVS-03-1【后端】：输入 u1、u2 单聊 10 条；操作 u1 删除（`upToSeq=10`）后 `convs`、`sync`；u2 查询；预期 u1 列表没有；`sync` 空；u2 不受影响；错误码 —。
- AC-CVS-03-2：输入 同上；操作 u2 再发 1 条；预期 u1 列表重新出现，未读 1，只能看到这 1 条；`minSeq=11`；错误码 —。
- AC-CVS-03-3【后端】：输入 `upToSeq=999`，`maxSeq=10`；`upToSeq=8`，`maxSeq=10`；操作 删除；预期 前者清到 10；后者清到 8，未读 2，会话不消失；错误码 —。
- AC-CVS-03-4【后端】：输入 g1 的会话被 u1 删除；操作 查成员、`myGroups`、`send`；预期 仍是成员，能发消息；`convs` 的 `deleted` 含 g1；错误码 —。
- AC-CVS-03-5【前端】（三套 SDK）：输入 u1 在 D1 删除 g1 的会话，D2 这时离线；操作 D2 重连后拉 `convs`；预期 g1 从列表消失，**不出现**"你已不在该群"，从通讯录进入可以正常发言；错误码 —。
- AC-CVS-03-6【后端】：输入 免打扰且置顶的 g1 被删除，然后有新消息；操作 查 `convs`；预期 不再置顶，仍免打扰；错误码 —。
- AC-CVS-03-7【后端】：输入 被清除范围内的图片；操作 u1 申请地址；预期 404；u2 仍可以；错误码 4048。
- AC-CVS-03-8【前端】：输入 有草稿、失败消息和本地缓存的会话；操作 确认删除；预期 都被清除；取消时不变；错误码 —。
- AC-CVS-03-9【后端】：输入 非参与方；操作 删除；预期 错误；错误码 4032。

### F-CVS-04 多端同步（P0）

### F-MOD-02 发送检查（P0，CH-20、CH-21）

**规则**
1. **只拦截，不替换、不做"发送者可见但别人看不到"。** 命中：ack 错误 4510，消息不保存、不投递。替换模式（F-ADM-60 规则）不在第一批，AC-ADM-60-2 作废。
2. 检查范围（**第一批**）：`text`；`image`、`file` 的文件名；注册和修改的昵称；客户端写入的群名、群公告（`groupCreate`、`groupUpdate`）。
3. **不查**：图片内容；文件内容；引用摘要（已经查过）；服务端生成的 `tip`；管理接口写入的内容；后台系统通知。
4. **`custom` 在生产环境禁止客户端发送**（CH-24），否则可以绕过检查：`IM_CLIENT_CUSTOM_MSG=0` 时 `send` 的 `type=custom` 返回 4000，`reason: customDisabled`。只影响客户端 `send`；`protocol/vectors` 里的 custom 帧是格式用例，不受影响。
5. 判定位置见第 4.3 节第 9 步：在已有的所有权限判定之后，避免让被拒绝的用户探测词库。4510 已扣发送令牌。

**异常**：检查超时（未校准：20 ms）：放行并计数（内容治理不能阻塞聊天），指标触发告警。`hits` 写入失败：不影响拦截结果。

### F-MOD-03 举报提交（P0）

**规则**
1. WS 命令 `report {targetType: "message"|"user"|"group", convId?, msgIds?, userId?, groupId?, reason, note?}`。`reason`：`spam`、`abuse`、`porn`、`fraud`、`illegal`、`other`。`note` 0～200 个码点。
2. `message`：单次 1～20 条，同一会话，举报人必须是参与者且能看到这些消息（seq ≥ 他的 `minSeq`）。否则 4040（`reason: reportTargetInvalid`，响应相同）。可以举报已撤回的消息（如果隔离原文还在）。
3. `user`：对象必须是好友、或有共同会话或共同群，否则同样 4040，防止探测。`group`：必须是成员或最近退出的（第一批只要求当前成员）。
4. 限额：每人每天 20 次（4292）；同一举报人对同一对象 24 小时内重复提交：幂等成功，不产生新记录。
5. **保存证据快照**：在同一事务把被举报消息的元数据和正文加密写入 `report_evidence`（AES-256-GCM，独立密钥 `IM_REPORT_KEY`），不依赖消息后续是否被撤回。文件只记引用，并延长文件保留到证据到期。
6. 证据保留 180 天，到期物理删除（`report_purge`）。
7. **被举报人不会收到任何通知**，举报人的身份只有后台审核员可见。
8. 客户端：长按消息"举报"（可以多选到 20 条）；资料卡和群信息页"举报"；提交前提示"所选内容将提交给平台审核"。提交成功后询问是否拉黑（单聊）。

**异常**：证据写入失败：举报失败（5000），不产生记录。消息已物理删除或隔离原文已过期：证据只有元数据，举报仍成功。

**验收标准**
- AC-MOD-03-1：输入 u2 举报 u1 的消息，理由 `abuse`；操作 提交；预期 成功；后台队列出现；u1 2 秒内收不到任何帧；错误码 —。
- AC-MOD-03-2【后端】：输入 不是参与者；其他会话的 msgId；入群前的消息；21 条；操作 分别举报；预期 前三个 4040，响应相同；第四个 4131；错误码 4040、4131。
- AC-MOD-03-3【后端】：输入 同一消息重复举报；操作 提交 3 次；预期 都成功，只有 1 条记录；错误码 —。
- AC-MOD-03-4【后端】：输入 当天第 21 次；操作 提交；预期 错误；错误码 4292。
- AC-MOD-03-5【后端】：输入 举报含特征串 `ZXQ-RPT-1` 的消息后，发送者撤回；操作 查 `report_evidence` 原始字节；审核员读取证据；预期 原始字节搜不到明文；审核员读到原文（群消息）；错误码 —。
- AC-MOD-03-6【后端】[IM 钟]：输入 证据；操作 推进 181 天运行 `report_purge`；预期 物理删除；错误码 —。
- AC-MOD-03-7【后端】：输入 举报用户：完全没有关联的 userId；不存在的 userId；操作 举报；预期 响应相同；错误码 4040。

### F-MOD-04 举报处理（P0，CH-22）

**规则**
1. 后台"举报"队列：按状态（`pending`、`handled`、`rejected`）、理由、时间筛选；相同对象的多条举报聚合显示次数。权限点 `report.read`、`report.handle`（`moderator`）。
2. 查看元数据（举报人、被举报人、时间、理由、消息类型和长度）不需要工单。
3. **查看证据正文**：群消息证据走 F-ADM-08 同样的流程（理由 + 当次动态码，工单号自动用举报 ID；配额合并；水印）。im-server 新 scope `report.evidence`，属于正文类 scope，只能配在 `bodyAccess` 调用方（`console-msgread`）。
4. **单聊证据**：受 `IM_C2C_BODY_ACCESS` 控制（默认关，X-7），关闭时 403 / 4030 `reason: c2cBodyDisabled`，页面显示"单聊正文查看未开启"，审核员只能看元数据和该用户被举报的次数。**这让单聊举报基本无法判定内容**，是否放开要法务和 Frank 定（CH-22）。
5. 处理：填结论（`handled` / `rejected`）和理由，可以跳转已有操作（删除消息、禁言、封禁、强制下线、解散群），**不自动执行**；这些操作沿用各自的权限和审计。
6. 第一批不给举报人发处理结果（避免依赖系统通知开关）。不设自动封禁。
7. 队列超过 24 小时未处理的数量进指标，告警默认不开（没有指定处理人之前没有意义）。

**异常**：读证据时密钥不匹配：显示"证据无法解密"并告警，不影响结案。写审计失败：操作不执行（5031）。

**验收标准**
- AC-MOD-04-1：输入 审核员打开队列；操作 查看群消息举报，填理由和动态码读证据，删除消息，结案；预期 看到原文和水印；消息被删除；状态 `handled`；审计依次有 `report.evidence.grant`、`msg.delete`、`report.handle`；错误码 —。
- AC-MOD-04-2【后端】：输入 `support` 账号；`operator` 账号；操作 读队列、结案；预期 都是 403；错误码 4030。
- AC-MOD-04-3【后端】：输入 `IM_C2C_BODY_ACCESS=off`，单聊消息举报；操作 审核员申请证据授权；预期 403，`reason=c2cBodyDisabled`；元数据照常可看；错误码 4030。
- AC-MOD-04-4【后端】：输入 调用方 `console` 主凭证；操作 调用 `report.evidence` 接口；配置 `console` 同时带 `report.evidence` 和 `msg.meta`；预期 前者 403；后者启动失败；错误码 4030。
- AC-MOD-04-5【后端】：输入 同一条举报；操作 两个审核员同时结案；预期 第一个成功；第二个 409，状态不变；错误码 4098。
- AC-MOD-04-6【前端】（管理后台）：输入 同一用户被 3 人举报；操作 看列表；预期 聚合显示"3 次"，点开看到每条；被举报内容按纯文本渲染；错误码 —。
- AC-MOD-04-7【后端】：输入 结案；操作 观察举报人和被举报人的连接；预期 2 秒内都收不到任何帧；错误码 —。

## 15. 非功能（F-CHAT-90）

**所有数字都未校准**。第一批没有 EP 测试机（PENDING P-12）；开发机结果只作参考，不能作为发布结论。

| 类别 | 要求 |
|---|---|
