## 1. 背景与目标

### 1.1 背景

fx-sport（Flutter）、ab77（iOS）、android 三个 App 的聊天室和站内推送都依赖腾讯云 IM：费用、功能、数据都受第三方约束；三端各自封装腾讯 SDK（合计约 2400 行），逻辑重复；推送"借道"群消息，曾因为监听错回调而收不到推送。

### 1.2 目标

自研 IM 公共库（服务端 + SDK），并基于它做一个独立的 IM 聊天软件。

**一期只做核心业务**：账号接入、用户、连接、单聊、群聊、会话列表、未读数、多端同步、统一错误码。直播聊天室、系统推送、禁言、删消息放到二期（D1）。

### 1.3 成功标准

| 指标 | 目标 | 度量方法 |
|---|---|---|
| 可靠性 | 正常、断网重连、ack 丢失场景下不丢、不重 | 第 4 节对应的验收标准全部通过 |
| 实时性 | 双方在线时端到端延迟 P99 ≤ 1 秒 | 性能用例：本机环境、连续 100 条、同一进程计时 |
| 吞吐 | 单机 ≥ 500 条消息/秒 | 压测 |
| 容量 | 单机 1 万长连接 | 压测 |
| 多端一致 | 同一账号在 web 和 pc 两端同时在线时，消息和未读数一致 | 第 4 节 F-SYNC 的验收标准 |
| 演示 | 分享会上现场演示两个标签页互聊、模拟断网后消息补齐 | 彩排 |

## 2. 角色与场景

| 角色 | 说明 |
|---|---|
| 终端用户 | 使用 IM App（一期为 H5，PC 复用）聊天的人 |
| 业务服务端 | 接入方（如 fx-sport 后端）：维护自己的用户体系；通过管理接口导入用户、签发凭证、建群、管成员、强制下线 |
| 管理员 | 一期通过管理接口操作，不做后台页面 |

核心场景：
1. 小明打开 App，看到会话列表和每个会话的未读数。
2. 小明给小红发消息，小红在线时立刻收到，离线时上线后能看到；给不存在的账号发消息会提示"用户不存在"。
3. 小明的网络断了，恢复后自动重连，期间的消息自动补齐；没发出去的消息可以重发，而且不会重复。
4. 小明 web 端和 pc 端同时在线，消息、未读数在两端一致。
5. 业务方建一个活动群，把参与者拉进来，并设置新成员能否看到之前的聊天记录。

### 3.1 通用约定

| 项 | 约定 |
|---|---|
| ID 规则 | `userId`、`groupId`：字母、数字、`_`、`-`，长度 1～64 |
| 文本计数 | 按 **Unicode 码点**计数；**先去掉首尾空白再计数**（空白包括空格、`\n`、`\t`、全角空格） |
| 时间 | 一律以服务端时间为准（毫秒时间戳），客户端时钟只用于"发送中"消息的临时展示 |
| 单聊会话 ID | `c2c:{较小 userId}:{较大 userId}`，按 **ASCII 字节序**比较 |
| 错误 | 所有错误按 F-SYS-01 返回错误码；客户端按错误码映射文案，不直接展示服务端的 `msg` |
| "在线" | 客户端与服务端之间有一条已鉴权的 WebSocket 连接 |

## 4. 功能需求

> 每个功能点：描述 → 业务规则 → 验收标准（AC）。错误码见 [ERRORS.md](../../protocol/ERRORS.md)。
> 标注【后端】【前端】的 AC 表示主要由哪一层验证；未标注的为端到端验证。

### F-SYS-01 统一错误码（P0）

**规则**
1. 服务端所有错误都使用 `protocol/errors.json` 中定义的错误码；WS 通过 `ack.error` 返回，管理接口通过 HTTP 状态码 + 响应体返回。
2. 凭证类致命错误（4010 无效、4011 过期、4012 被强制下线）：先下发 `kicked` 事件，再用同号关闭码关闭连接。平台不合法（4009）属于开发期缺陷，不发 `kicked`，直接以 4009 关闭。
3. 错误码只增不改；客户端遇到不认识的错误码，按区段兜底处理。
4. 服务端 Go 常量、TS SDK、KMP SDK 的错误枚举必须与 `errors.json` 一致。

**验收标准**
- AC-SYS-01-1【后端】：服务端代码里定义的错误码集合与 `errors.json` 完全一致（一致性测试）。
- AC-SYS-01-2【后端】：第 4 节中每条带错误码的 AC 返回的都是规定的错误码；管理接口的 HTTP 状态码与 `errors.json` 的 `http` 字段一致。
- AC-SYS-01-3【前端】：TS SDK 的错误枚举与 `errors.json` 一致（一致性测试）。
- AC-SYS-01-4【前端】：收到未定义的错误码（如 4999）时，按 4xx 区段兜底：不重试，并提示"请求出错"。

### F-USER-01 用户注册与导入（P0）

**描述**：IM 维护一张用户表，用来判断"用户是否存在"（D5），并存储昵称和头像。

**规则**
1. 业务方可以批量导入用户：每个用户包含 `userId`（必填）、`nickname`（可选，1～32 字）、`avatar`（可选，URL，最长 512）。单次最多 500 个。
2. 导入时 `userId` 已存在：更新昵称和头像（upsert），不报错。
3. 签发凭证（F-AUTH-01）时，用户若不存在则自动注册。
4. 一期不支持删除用户。

**验收标准**
- AC-USER-01-1【后端】：导入 3 个合法用户，返回成功；之后给其中任意一人发单聊不再报 4042。
- AC-USER-01-2【后端】：重复导入同一个 `userId` 并修改昵称，返回成功，昵称被更新。
- AC-USER-01-3【后端】：一次导入 501 个用户返回 HTTP 400 / 4131；500 个成功。
- AC-USER-01-4【后端】：导入的 `userId` 不合法时返回 HTTP 400 / 4004，并且整批都不写入。
- AC-USER-01-5【后端】：为一个从未导入的 `userId` 签发凭证后，该用户即视为存在。

### F-USER-02 用户昵称与头像展示（P1）

**规则**：会话列表、聊天页、群消息的发送者优先显示昵称，没有昵称时显示 `userId`；头像为空时显示首字母占位。

**验收标准**
- AC-USER-02-1【前端】：设置过昵称的用户，在会话列表和聊天页显示昵称；没设置的显示 `userId`。

### F-AUTH-01 签发用户凭证（P0）

**描述**：业务服务端用管理密钥为用户换取 IM 凭证（token），对应腾讯 IM 的 `genUserSig`。

**规则**
1. IM 不维护密码，身份以业务方传入的 `userId` 为准。
2. 有效期参数 `ttlSeconds`：不传、0 或负数时按 7 天；最长 30 天，超过按 30 天；**测试模式下**最小可为 1 秒（见 6.1 节）。
3. 管理接口必须携带正确的管理密钥。
4. 被强制下线（F-AUTH-03）之前签发的凭证全部失效；之后签发的新凭证正常可用。

**验收标准**
- AC-AUTH-01-1【后端】：密钥正确、`userId` 合法时返回 token 和过期时间（毫秒时间戳）。
- AC-AUTH-01-2【后端】：密钥缺失或错误时返回 HTTP 401 / 4013，不签发凭证。
- AC-AUTH-01-3【后端】：`userId` 长度为 1 和 64 时成功；长度为 0、65，或含空格、中文、`.`、`@` 时返回 HTTP 400 / 4004。
- AC-AUTH-01-4【后端】：不传有效期 / 传 0 / 传 -1 时，过期时间 = 当前时间 + 7 天（误差 ±5 秒）。
- AC-AUTH-01-5【后端】：有效期传 30 天时按 30 天签发；传 31 天时按 30 天签发。

### F-AUTH-02 客户端登录与连接（P0）

**规则**
1. 连接地址只携带平台标识（android / ios / web / pc）；**token 不放在 URL 里**，连接建立后的第一帧发送 `auth` 命令携带 token（C-52，防止 token 被代理、CDN、浏览器历史记录）。
2. 同一账号允许多个连接同时在线，包括同一平台的多个连接（见 F-SYNC-01）。
3. 凭证有问题时（在收到 `auth` 之后判断），服务端下发 `kicked`，再用对应关闭码关闭（因为浏览器拿不到握手阶段的 HTTP 401）。
5. 同一账号最多同时保持 10 个连接；第 11 个连接上线时，**最早的**连接被踢下线（C-53）。
6. 浏览器连接的来源（Origin）必须在服务端白名单内，否则握手被拒绝；原生端没有 Origin，不受影响（C-54）。
4. 平台标识缺失或不合法时，用关闭码 4009 关闭。

**验收标准**
- AC-AUTH-02-1【后端】：token 有效时连接成功，可以收发消息。
- AC-AUTH-02-2【后端】：token 无效 / 缺失时，客户端收到 `kicked/tokenInvalid`，随后连接以关闭码 4010 关闭。
- AC-AUTH-02-3【后端】：token 已过期时，收到 `kicked/tokenExpired`，关闭码为 4011。
- AC-AUTH-02-4【前端】：收到 4010 / 4011 后不再重连，弹窗提示"登录已失效"或"登录已过期"，点击"确定"后回到登录页。
- AC-AUTH-02-5【后端】：同一账号以 platform=web 和 platform=pc 各连一次，两个连接都保持在线；以 platform=web 连两次，同样都在线。
- AC-AUTH-02-6【后端】：platform 为空或为 `tv` 时，连接以关闭码 4009 关闭。
- AC-AUTH-02-7【后端】：连接后 5 秒内没有发送 `auth`，或者在 `auth` 之前发送了其他命令，连接以关闭码 4401 关闭。
- AC-AUTH-02-8【后端】：只在 URL 里携带 token、不发 `auth` 的连接不会上线（token 不从 URL 读取）。
- AC-AUTH-02-9【后端】：`auth` 成功返回 ack，包含 `userId` 和服务端时间 `serverTime`；成功后再次发送 `auth` 返回 4000。
- AC-AUTH-02-10：同一账号第 11 个连接上线时，最早的连接收到 `kicked/tooManyConnections` 并以 4429 关闭；SDK 收到后不重连，提示"登录设备过多，当前设备已下线"。
- AC-AUTH-02-11【后端】：Origin 不在白名单内的浏览器握手被拒绝（HTTP 403）；没有 Origin 头的原生端连接正常。

### F-AUTH-03 凭证失效、过期与强制下线（P0）

**规则**
1. 已连接的客户端在 token 到期时，服务端下发 `kicked/tokenExpired` 并关闭（4011）。
2. 业务方可以调用"强制下线"接口：该用户所有在线连接收到 `kicked/banned` 并关闭（4012）；**此前签发的所有 token 立即作废**（D6）。业务方重新签发 token 即可解封。
3. `kicked` 帧必须**完整发送后**再关闭连接。
4. 客户端收到 `kicked` 后不自动重连（例外：`serverShutdown` 表示服务端正在下线，按退避策略重连，C-55）；**停留在当前页面并弹出提示框**说明原因，此时正在发送中的消息标记为发送失败；用户点"确定"后回到登录页并清空数据（C-01）。
5. "单设备登录互踢"（`replaced`）一期不做。

**验收标准**
- AC-AUTH-03-1【后端】：签发有效期 2 秒的 token 并连接，3 秒内收到 `kicked/tokenExpired`，连接以 4011 关闭（测试模式）。
- AC-AUTH-03-2【后端】：调用强制下线后，该用户所有连接收到 `kicked/banned` 并以 4012 关闭；其他用户不受影响。
- AC-AUTH-03-3【后端】：强制下线后，用旧 token 连接收到 `kicked/banned`，并以关闭码 4012 关闭。
- AC-AUTH-03-4【后端】：强制下线后重新签发的 token 可以正常连接。
- AC-AUTH-03-5【前端】：被踢后不再重连，停留在当前页面并弹窗分别提示"登录已过期""账号已被下线"；点击"确定"后回到登录页。
- AC-AUTH-03-6【前端】：被踢后弹窗显示期间，原本发送中的消息在当前页面显示为发送失败。

### F-AUTH-04 演示用登录服务（P0）

**描述**：独立 IM App 和分享会演示没有业务服务端，需要一个模拟业务服务端：输入用户名即可登录。

**规则**
1. 仅用于开发和演示，**默认关闭**，需要显式配置才开启。
2. 前端不持有管理密钥，由模拟服务转调 IM 管理接口。
3. 用户名规则同 `userId`；登录即自动注册。

**验收标准**
- AC-AUTH-04-1：开启后，前端提交用户名，拿到的 token 能连接成功。
- AC-AUTH-04-2【前端】：前端构建产物和登录过程的抓包记录（HAR）中搜不到管理密钥。
- AC-AUTH-04-3【后端】：默认配置下，该接口返回 404。
- AC-AUTH-04-4：用户名不合法（如含空格）时，登录页提示"账号格式不正确"。

### F-AUTH-05 退出登录（P0）

**规则**：主动退出时，用关闭码 1000 断开连接，不触发重连；清空内存中的数据和 `sessionStorage` 里的 token；回到登录页。

**验收标准**
- AC-AUTH-05-1【前端】：点击退出登录后回到登录页；刷新页面仍停留在登录页；服务端日志记录该连接以 1000 关闭。

### F-CONN-01 心跳保活与断线重连（P0）

**规则**
1. 客户端每 30 秒发一次心跳（ping）。服务端 90 秒收不到任何帧就以 4408 关闭连接。客户端发出心跳后 10 秒内没收到 pong，判定断线。（以上时间在测试模式下可以配置。）
2. 断线后自动重连，等待间隔按 1s、2s、4s… 指数增长，最长 30s，并加 ±20% 随机抖动。
3. 浏览器触发 `online` 事件时立即重连，不再等退避。
4. 重连成功后：先拉会话列表（`convs`），再对"服务端 maxSeq > 本地 maxSeq"的会话补拉；某个会话的缺口超过 200 条时，直接加载最新一页，更早的靠向上翻页加载。
5. 被踢（4009～4012）或主动退出（1000）时不重连。

**验收标准**
- AC-CONN-01-1【后端】：客户端按心跳间隔持续发 ping，连接保持 5 分钟不断（测试模式下，用空闲超时的 10 倍时长验证）。
- AC-CONN-01-2【后端】：客户端停止发送任何帧超过空闲超时，服务端以关闭码 4408 关闭连接。
- AC-CONN-01-3【前端】：浏览器离线 10 秒后恢复（Playwright `setOffline`），5 秒内重连成功。
- AC-CONN-01-4：断线期间对方发来 3 条消息，重连后这 3 条按 seq 顺序出现，没有重复。
- AC-CONN-01-5【前端】：服务端持续不可用时，连续 6 次重连的间隔大约为 1、2、4、8、16、30 秒（±20%），之后保持在 30 秒左右。
- AC-CONN-01-6【前端】：网络在线但服务端无响应（假传输层不回 pong）时，10 秒内判定断线并开始重连。
- AC-CONN-01-7：断线期间有人新建群把我拉进去，并在群里发了消息；重连后会话列表里出现这个群，消息也能看到。
- AC-CONN-01-8：断线期间某会话新增 250 条消息，重连后打开该会话，显示最新的 20 条，向上翻页可以加载到全部。

### F-CONN-02 连接状态提示（P0）

### F-MSG-01 单聊发送文本消息（P0）

**规则**
1. 文本长度 1～5000（按 3.1 节的计数规则）；服务端同样会去掉首尾空白后再校验，存储的是去空白后的内容。
2. 每条消息由客户端生成唯一的 `clientMsgId`（建议用 UUID，长度 8～64）。

5. 对方 `userId` 不存在时返回 4042（D5）。

**验收标准**
- AC-MSG-01-1【前端】：输入"你好"点发送，消息立即出现在底部，状态为"发送中"；收到 ack 后变为"已发送"。

- AC-MSG-01-4【后端】：服务端收到去空白后超过 5000 个码点的消息，返回 4006；收到去空白后为空的消息，返回 4005。
- AC-MSG-01-5【后端】：消息"  你好  "存储和下发的内容为"你好"。
- AC-MSG-01-6【后端】：同一会话里连续发送的消息，`seq` 严格递增；ack 中的 `convId` 等于 `c2c:{较小}:{较大}`。
- AC-MSG-01-7【后端】：给自己发消息成功，会话 ID 为 `c2c:{我}:{我}`。
- AC-MSG-01-8【后端】：给不存在的 `userId` 发消息返回 4042，不保存消息。
- AC-MSG-01-9【前端】：收到 4042 时，消息标记为失败并提示"用户不存在"。

### F-MSG-02 接收消息（P0）

### F-MSG-03 发送状态与失败重发（P0）

**发送状态机**

```
            在线：发出 ──────────────▶ 发送中 ──收到 ack──▶ 已发送
输入并发送 ─┤                          │ 10 秒无 ack / 收到错误 / 被踢
            离线：进入待发队列 ─重连后发出（只自动发 1 次）─▶ 发送中
                                       ▼
                                    发送失败 ──手动重发（原 clientMsgId）──▶ 发送中
```

**规则**
1. 在线时从发出开始计时 10 秒；离线时先进入待发队列，重连后发出时才开始计时。
2. 自动重发只做 1 次；之后只能手动重发，手动重发**使用原 `clientMsgId`**。
3. 未确认的消息排在所有已有 seq 的消息之后；收到 ack 后按 seq 移动到正确位置。
4. 失败消息只保存在内存中（D4）；存在待发或失败的消息时，刷新或关闭页面要先弹窗确认（`beforeunload`）。

**验收标准**
- AC-MSG-03-1【前端】：在线状态下，服务端不回 ack（故障注入），10 秒（±1 秒）后消息显示为发送失败。
- AC-MSG-03-2【前端】：离线时发送的消息显示"发送中"；恢复网络后自动发出成功，对方只收到一条。
- AC-MSG-03-3：点击失败消息重发后变为已发送，对方只收到一条。
- AC-MSG-03-4：服务端已保存但 ack 被丢弃（故障注入）后手动重发，对方只收到一条，`msgId` 与服务端第一次保存时一致。
- AC-MSG-03-5【前端】：有发送失败的消息时刷新页面，浏览器弹出离开确认。

### F-MSG-04 消息不丢、不重、有序（P0）

**规则**
1. **不重**：服务端按（发送者，`clientMsgId`）去重；客户端按 `msgId` 去重展示，并用 `clientMsgId` 把服务端回来的消息与本地待发消息合并。同一个 `clientMsgId` 用于另一个会话时返回 4008；内容不同但 clientMsgId 相同时，以第一次保存的为准。
2. **不丢**：客户端记录每个会话的最大 seq，ack 带回的 seq 同样计入。发现缺口后等 500ms，仍未补上就 `sync` 补拉缺口。
3. **有序**：同一会话按 seq 升序展示。
4. 服务端下发的消息（`msg` 帧和 `sync` 结果）一律带 `clientMsgId`。

**验收标准**
- AC-MSG-04-1【后端】：同一 `clientMsgId` 重复提交 5 次，服务端只保存 1 条，每次返回相同的 `msgId` 和 `seq`。
- AC-MSG-04-2【后端】：同一 `clientMsgId` 发到另一个会话，返回 4008。
- AC-MSG-04-3【前端】：先收到 seq=1、seq=3，500ms 内没收到 seq=2 时，客户端发起 sync，最终按 1、2、3 展示。
- AC-MSG-04-4【前端】：收到 seq=1、seq=3，200ms 后 seq=2 到达，客户端不发起 sync。
- AC-MSG-04-5：5 个成员在同一个群里各并发发 20 条，最后一个 ack 之后 10 秒内，所有成员都看到 100 条，seq 为 1～100，连续且不重复。
- AC-MSG-04-6【后端】：服务端返回 ack 后立即被强制杀掉进程（kill -9），重启后 sync 能拉到这条消息。
- AC-MSG-04-7【后端】：`msg` 帧和 `sync` 结果中的每条消息都带 `clientMsgId`。

### F-MSG-05 历史消息与补拉（P0）

**规则**
1. `sync` 支持两种方向，二选一：`afterSeq`（拉取之后的消息，用于补拉）、`beforeSeq`（拉取之前最近的消息，用于翻页）。结果都按 seq 升序排列，并返回 `hasMore`。
2. 单次 `limit` 为 1～200，默认 50；超过 200 返回 4000。
3. 打开会话：用会话列表里的 `maxSeq` 加载最新 20 条（`beforeSeq = maxSeq + 1`）；向上滚动到顶部时，每次再加载 20 条，直到 `hasMore = false`。
4. 只能拉取自己参与的会话：单聊非参与方返回 4032，非群成员返回 4033，群不存在返回 4043。
5. 群的历史可见范围由群设置决定（见 F-GRP-01）：只能拉到 `minSeq` 及之后的消息；翻页到 `minSeq` 时 `hasMore = false`。
6. 一期 H5 不做本地持久化缓存：刷新页面后重新拉会话列表和最新 20 条（D4）。

**验收标准**
- AC-MSG-05-1：B 离线期间收到 5 条消息，上线打开会话能看到全部 5 条。
- AC-MSG-05-2：会话有 100 条消息，打开后显示 seq 81～100；向上翻页依次加载 61～80 … 1～20；加载到第 1 条后不再触发加载，显示"没有更多了"。
- AC-MSG-05-3【后端】：`afterSeq=0, limit=3` 返回 seq 1～3，`hasMore=true`；`beforeSeq=101, limit=20` 返回 seq 81～100，按升序排列。
- AC-MSG-05-4【后端】：`limit=200` 时最多返回 200 条，有剩余时 `hasMore=true`；`limit=201` 返回 4000。
- AC-MSG-05-5【后端】：拉取别人的单聊返回 4032；非成员拉取群消息返回 4033；拉取不存在的群返回 4043。
- AC-MSG-05-6【前端】：加载历史后，当前可视位置不跳动。

### F-GRP-01 群管理（P0，管理接口）

**规则**
1. 建群：业务方指定群 ID、群名（1～50 字）、初始成员（可以为空）、`historyVisible`（新成员能否看入群前的历史，默认 `false`）。
2. 加成员、移除成员；成员总数上限 2000（建群和加成员时都按加完后的总数校验）；**加成员接口**单次最多 500 人（超出返回 4131），建群的初始成员只受 2000 总数限制（C-04）。
3. 修改群设置：群名、`historyVisible`。
4. 查询群信息：群名、设置、成员列表。
5. 群 ID 已存在时返回 4090；群不存在时返回 4043；成员 `userId` 不存在时返回 4042，并且整批都不生效。
6. **历史可见性（D2）**：记录每个成员入群时会话的 maxSeq（`joinSeq`）。`historyVisible=false` 时，成员只能看到 seq > joinSeq 的消息；`historyVisible=true` 时可以看到全部历史。设置在**查询时生效**：修改后，所有成员下次拉取时立即按新设置计算。
7. 被移除后再加入，`joinSeq` 按重新加入的时刻计算。

**验收标准**
- AC-GRP-01-1【后端】：建群成功后，初始成员都能在群里发消息。
- AC-GRP-01-2【后端】：重复建同一个群 ID，返回 HTTP 409 / 4090。
- AC-GRP-01-3【后端】：建群时有 2000 个成员可以成功，2001 个返回 HTTP 400 / 4130；群里已有 1999 人时一次加 2 人，返回 4130 且一人都不加。
- AC-GRP-01-4【后端】：移除成员后，该成员发群消息返回 4033、拉取返回 4033，也不再收到新消息。
- AC-GRP-01-5【后端】：可以查询群名、`historyVisible` 和成员列表。
- AC-GRP-01-6【后端】：群里已有 10 条消息，`historyVisible=false` 时新成员 D 入群，D 只能拉到入群之后的消息，会话列表里 `minSeq=11`、未读为 0。
- AC-GRP-01-7【后端】：同样的场景，`historyVisible=true` 时 D 能拉到全部 10 条，`minSeq=1`。
- AC-GRP-01-8【后端】：把群设置从 `false` 改为 `true` 后，D 下次拉取能看到入群前的消息。
- AC-GRP-01-9【后端】：成员被移除后再加入（`historyVisible=false`），只能看到重新加入之后的消息。
- AC-GRP-01-12【后端】：AC-GRP-01-6 的场景下，把 `historyVisible` 从 false 改为 true 后，D 的未读数仍为 0（C-02）。
- AC-GRP-01-10【后端】：加成员时包含不存在的 `userId`，返回 HTTP 404 / 4042，并且一人都不加。
- AC-GRP-01-11【后端】：群名为空或超过 50 字时返回 HTTP 400 / 4000。

### F-CONV-01 会话列表（P0）

**规则**
1. WS 命令 `convs`（D3）返回当前用户的全部会话，一期上限 500 个；超过时返回最近更新的 500 个，并带 `truncated: true`（C-03）。每个会话包含：`convId`、`type`、`name`（单聊为对方 userId / 昵称，群聊为群名）、`maxSeq`、`readSeq`、`minSeq`、`unread`、`lastMsg`（摘要、发送者、时间）、`updatedAt`。
2. 哪些会话出现在列表里：发过或收到过消息的单聊（包括自己给自己发的）；所在的全部群（包括还没有消息的群）。
3. 排序：按 `updatedAt`（最后一条消息的服务端时间；没有消息的群用入群时间）倒序；时间相同时按 `convId` 排序。
4. 一期不做置顶、删除会话、免打扰。

**验收标准**
- AC-CONV-01-1【后端】：A 和 B、C 各有单聊，且在群 g1（无消息）和 g2（有消息）里，A 拉取 `convs` 返回 4 个会话，排序正确，字段完整。
- AC-CONV-01-2【前端】：收到新消息的会话移到列表顶部，摘要和时间更新。
- AC-CONV-01-3：在新的浏览器上下文登录，会话列表与原设备一致。
- AC-CONV-01-4【后端】：两个会话的 `updatedAt` 相同时，按 `convId` 升序排列。
- AC-CONV-01-5【前端】：客户端时钟比服务端快 1 小时时，排序和显示的时间都不受影响。
- AC-CONV-01-6【前端】：没有任何会话时，显示空状态，并引导"发起单聊"。
- AC-CONV-01-7【后端】：用户有 501 个会话时，`convs` 返回最近更新的 500 个，`truncated=true`；有 500 个时 `truncated=false`（C-03）。

### F-CONV-02 未读数与标记已读（P0）

**规则**
1. 未读数 = maxSeq − max(readSeq, joinSeq)（单聊的 joinSeq 为 0）。未读数**始终从入群时刻算起**，与 `historyVisible` 无关：历史可见只决定能否翻到入群前的消息，不计入未读（C-02）。
2. **发言即已读**：发消息成功时，服务端在同一事务里把发送者的 readSeq 推进到这条消息的 seq；客户端收到 ack 时同步推进本地 readSeq。
3. 已读上报：只有页面可见、并且停在该会话时才上报；节流为最多 1 秒一次；上报的值为当前会话的最新 seq。
4. 已读位置只前进不后退；上报的 seq 大于 maxSeq 时，按 maxSeq 记录。
5. 未读数大于 99 时显示"99+"。总未读数（首页标题、App 角标）为 P1。

**验收标准**
- AC-CONV-02-1：B 离线时 A 发来 3 条，B 登录后与 A 的会话未读数为 3。
- AC-CONV-02-2：B 打开该会话后未读数变为 0；重新登录后仍为 0。
- AC-CONV-02-3【后端】：B 在会话里发 1 条消息后，B 的该会话未读数为 0。
- AC-CONV-02-4【前端】：未读 99 显示"99"，100 显示"99+"。
- AC-CONV-02-5【后端】：先上报已读 seq=5，再上报 seq=3，已读位置仍为 5。
- AC-CONV-02-6【后端】：会话 maxSeq=10 时上报 seq=999，已读位置记为 10，未读数为 0（不会是负数）。
- AC-CONV-02-7【前端】：浏览器标签页在后台时收到新消息，不上报已读，未读数增加；切回该标签页后上报已读，未读数清零。

### F-CONV-03 发起单聊（P0）

**规则**：在首页弹窗输入对方 `userId`，打开与对方的聊天页；先在前端校验格式；还没发消息的会话只在本地临时显示，发出第一条消息后才进入服务端的会话列表。

**验收标准**
- AC-CONV-03-1【前端】：输入合法的 `userId`，进入与对方的聊天页。
- AC-CONV-03-2【前端】：输入格式不合法时提示"账号格式不正确"，不跳转。
- AC-CONV-03-3：给不存在的 `userId` 发第一条消息，提示"用户不存在"，会话不进入服务端会话列表。

### F-SYNC-01 多端消息同步（P0）

**规则**：别人发来的消息，所有在线连接都能收到；自己在某个连接发的消息，自己的其他在线连接也会收到，发送的那个连接只收到 ack。

**验收标准**
- AC-SYNC-01-1：A 用 platform=web 和 platform=pc 两个连接同时在线，B 给 A 发消息，两个连接都收到。
- AC-SYNC-01-2：A 在 web 连接发消息，pc 连接收到这条消息（显示为自己发的）；web 连接不重复显示。

### F-SYNC-02 已读状态多端同步（P1）

**规则**：用户在某个连接上的已读位置前进时（包括发言即已读），服务端向该用户的其他在线连接推送 `event/readUpdated {convId, readSeq}`（C-06）。

**验收标准**
- AC-SYNC-02-1：A 在 pc 端打开有 3 条未读的会话，web 端该会话的未读数在 2 秒内变为 0。

### F-DEMO-01 演示面板（P0）

**描述**：开发和分享会演示用的面板，可以通过 URL 参数 `?demo=1` 打开。

**规则**：显示当前连接状态、各会话的本地 maxSeq；提供"模拟断网"开关：断开连接并暂停自动重连，关掉开关后恢复重连。

**验收标准**
- AC-DEMO-01-1【前端】：打开模拟断网后，连接状态显示为未连接；此时对方发来的消息不显示；关闭开关后自动重连，消息被补齐。
- AC-DEMO-01-2【前端】：不带 `?demo=1` 时不显示演示面板。

## 6. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 单机 1 万长连接；≥ 500 条消息/秒；端到端延迟 P99 ≤ 1 秒（本机环境）；`sync` 返回 200 条的耗时 ≤ 200ms |
| 可靠性 | 返回 ack 的消息已经落盘（SQLite `synchronous=FULL`）；服务端重启后不丢消息；64KB 单帧上限只限制上行，下行不设上限，SDK 不得限制下行帧大小（C-07） |
| 安全 | token 签名校验，强制下线后旧 token 作废；管理接口需要密钥；生产环境必须配置独立密钥；前端不持有管理密钥；上线前开启 WebSocket Origin 白名单；单用户发送限流 |
| 兼容 | H5：最新两个大版本的 Chrome / Safari（含 iOS Safari）、微信内置浏览器 |
| 可观测 | 服务端记录连接建立和断开（含关闭码）、错误日志；提供 `/healthz` |

### 6.1 测试环境要求（R-04）

| 能力 | 要求 |
|---|---|
| 短有效期 token | 测试模式下 `ttlSeconds` 最小可以是 1 |
| 可配置时间 | 心跳间隔、空闲超时、pong 超时、发送超时、退避上限都可以配置 |
| 故障注入（服务端，仅测试模式） | 丢弃指定 `clientMsgId` 的 ack；跳过指定消息的实时投递（用来制造 seq 缺口） |
| 假传输层 / 假时钟（SDK） | SDK 允许注入假的 WebSocket 和时钟，用来测试重连、超时、乱序 |
| 服务端时钟注入 | 测试模式下可以设置服务端时间（`POST /admin/test/clock`），用于验证排序、过期等与时间相关的规则（C-43） |
| 干净环境 | 每个测试用例使用独立的数据库 |
| 生产保护 | 测试模式和故障注入在生产构建中默认关闭，开启时启动日志要打印醒目的警告 |

## 9.1 补充规则（v1.2，来自架构与安全设计）

详细设计见 [ARCH-v1.md](../arch/ARCH-v1.md) 第 4 节。

| 条款 | 适用 | 规则 |
|---|---|---|
| C-52 | F-AUTH-02 | 连接地址为 `/ws?platform={platform}`。连接建立后第一帧必须是 `{"id":…,"cmd":"auth","data":{"token":…}}`；5 秒内没有收到，或第一帧不是 `auth`，以 4401（AUTH_REQUIRED，可以重连）关闭，不发 `kicked`。收到 `auth` 后按 C-08 的顺序（4010 → 4012 → 4011）判断凭证；成功返回 ack `{"userId":…,"serverTime":…}`，之后才算"在线"；再次发送 `auth` 返回 4000。URL 中的 `token` 参数被忽略。平台标识仍在握手时检查（4009 最先） |
| C-53 | F-AUTH-02 | 每个用户最多 10 个连接（`IM_MAX_CONNS_PER_USER`）。超出时踢掉最早的连接：`kicked/tooManyConnections` + 4429（不重连）。不影响 AC-AUTH-02-5 的多端同时在线 |
| C-54 | F-AUTH-02 | 浏览器 Origin 白名单：`IM_ALLOWED_ORIGINS`（逗号分隔，支持 `*.example.com`）。未配置时只允许本机来源（`localhost`、`127.0.0.1`）。被拒绝的握手返回 HTTP 403，SDK 视为网络错误按退避重连 |
| C-55 | F-AUTH-03 | 新增被踢原因 `serverShutdown`（关闭码 1001）：服务端优雅下线前通知在线连接。客户端**按退避策略重连**，不弹窗、不回登录页 |
