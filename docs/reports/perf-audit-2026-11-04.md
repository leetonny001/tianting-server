# 审计性能（2026-11-04）

环境：开发机（Apple 芯片，macOS，本地 Postgres 17.11，默认配置）。**不是生产环境**：macOS 的 fsync 比 Linux 服务器磁盘快得多，写入数字偏乐观，部署后要重测。

复现：`CON_TEST_AUDIT_PERF=1 go test -count=1 -timeout 590s ./e2e/ -run TestPerfAudit -v`（tianting-console-server）。

## AC-ADM-90-4 写入（目标：≥ 200 条 / 秒，P95 ≤ 20ms）

两个 Writer、8 个并发、60 秒，每条一个事务。

| 指标 | 结果 |
|---|---|
| 写入 | 442,677 条，7,378 条 / 秒，错误 0 |
| 延迟 | P50 0.95ms，P95 1.43ms，P99 2.49ms |
| 之后 `audit verify`（库内比对） | 通过，442,677 条用时 4.3 秒（约 10 万条 / 秒） |

## AC-ADM-90-3 查询（目标：1000 万条、31 天按操作人筛选 P95 ≤ 2 秒）

**没有真的灌 1000 万条**：开发机磁盘只剩 19GB（96%），真灌要占约 8GB。查询按时间裁剪分区，只碰窗口内的月份，所以按"每年 1000 万条"的密度灌 73 天（200 万条，库 1285MB），窗口内行数和分区大小与真实规模相同。没有测到的是冷缓存：数据都在内存里，生产冷启动后首次查询会更慢。

| 查询（31 天，limit 50，经 HTTP） | P50 | P95 |
|---|---|---|
| 按操作人 | 1.7ms | 2.2ms |
| 操作人 + 动作 | 31ms | 163ms |
| 操作人（没有匹配） | 0.7ms | 1.3ms |
| 按目标（JSON 包含，没有索引） | 481ms | 551ms |
| 只有时间 | 1.2ms | 1.8ms |

对账扫描（31 天内全部 intent 查是否有 result，这份数据里全部没有，是最坏情况）：325ms。

## 结论

两项都远好于目标，但都是开发机数字。按目标筛选最慢，因为没有索引、要解析 JSON；目前可以接受。如果上线后变慢，再考虑给 `target` 建 GIN 索引（每条写入多一份索引开销）。
