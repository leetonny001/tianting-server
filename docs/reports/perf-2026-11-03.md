## 观察与风险

1. **（已分析并部分修复，见 [内存分析](mem-2026-11-03.md)）吞吐阶段内存峰值偏高**：1 万连接建立后 201 MB，600 条/秒持续 5 分钟后升到 736 MB（峰值 764 MB），压测结束后回落到 290 MB。之后的保持阶段没有继续增长，说明不是泄漏，更像是 Go 堆在高分配率下按 GOGC 扩张后没有立即还给系统。但这个峰值在小内存服务器上可能成为瓶颈。**后续**：用 pprof 做一次内存分析（JSON 编解码、每条消息的帧分配、SQLite 页缓存是主要怀疑对象），并评估 `GOMEMLIMIT`。已记入工作队列。
2. **同机压测的局限**：客户端和服务端抢同一台机器的 CPU，延迟数字偏保守；但网络是本机回环，没有真实网络延迟和丢包。上线前要在目标服务器上、客户端分布在其他机器时复测（C-50）。
3. **SQLite 单连接是吞吐上限的主要因素**：每条消息一个事务并 fsync。目前 600 条/秒下 ack 延迟 P99 约 51ms、最大 218ms，还有余量；再往上提要靠 Postgres（B6，ARCH 3.3）或批量提交。
4. 建立 1 万条连接用了 50 秒，是压测工具按 200 条/秒限速建的（用例要求），不是服务端的上限。

## 压测过程中发现的问题（都已修复）

压测工具在冒烟阶段自己暴露了 3 个 bug，都是工具问题，不是服务端问题：

| 问题 | 怎么发现的 | 修复 |
|---|---|---|
| 预热和加压两个阶段的 `clientMsgId` 序号都从 0 开始，重复了；服务端按去重规则返回第一次的 ack，工具误当成新消息计数 | 吞吐用例结束后的 sync 核对：每个会话 sync 到的条数正好等于预热阶段的发送量 | `clientMsgId` 带上阶段标识 |
| 抽样阶段同一轮随机到同一个发送者两次，`clientMsgId` 相同、收件人不同，被服务端判为 4008 | 抽样失败率约 14%，与"500 人里抽 100 次"的碰撞概率吻合 | `clientMsgId` 带上收件人和序号 |
| 内存增长从"建立连接后"算起，把吞吐阶段正常增加的内存也算成了泄漏 | 冒烟时增长 66% 被判不通过，但保持阶段内存其实在回落 | 改为从吞吐结束时算起，报告里同时列出各阶段的内存 |

这几处也说明：压测结果要能自己核对（sync 核对、按错误码统计），否则工具的 bug 会被当成服务端的问题，或者反过来把服务端的问题掩盖掉。
