# 运维后台性能验收（2026-11-04，BE-321 / CS-120 的开发机部分）

**这是部分验收。** 开发机上没有 Prometheus、Grafana（开发机不装这些软件），所以 AC-OPS-90-1、90-2 只验证了不依赖它们的部分，06-2、06-10、07-8 没有测。结论只在同一轮内比较（C-50）：服务端、压测客户端、console-server、Postgres 都在同一台机器上。

## 环境

- 开发机 Apple M4（10 核）、16GB、macOS；Postgres 17 本机；真实 im-server + console-server。
- 节点运维接口走回环明文（TLS 在 testenv 里单独验过，见 backend-ops.md 的 BE-320）。
- 压测：`im-loadtest -scenarios opsimpact -ops-segment 5m -ops-idle 10000 -ops-phase-file ...`，运维流量：console-server 仓库的 `tools/ops-accept -steps load -accounts 20`。

## AC-OPS-90-1：运维流量对 IM 的影响

1 万条空闲长连接 + 100 个活跃用户，500 条/秒。20 个 `ops_engineer` 账号：每个 0.5 次/秒排查、每 15 秒刷新总览、每 60 秒打开配置检查和数据库页。

| 段 | 运维流量 | P99 | 吞吐 |
|---|---|---|---|
| 1 | 关 | 9.0ms | 500 条/秒 |
| 2 | 开 | 9.2ms | 500 条/秒 |
| 3 | 关 | 9.7ms | 500 条/秒 |
| 4 | 开 | 10.4ms | 500 条/秒 |
| 5 | 关 | 10.1ms | 500 条/秒 |
| 6 | 开 | 9.8ms | 500 条/秒 |

- P99 中位数：开 9.8ms，关 9.7ms，**差 0.1ms**（要求 ≤ 20ms）。
- 每段 P99 ≤ 1 秒、吞吐 ≥ 490、发送失败 0、意外断开 0。
- **没有覆盖**：Grafana 24 小时面板每 30 秒刷新的流量；Prometheus 抓取和查询的开销。

## AC-OPS-90-2：console-server 接口耗时（3 个开段）

| 接口 | 样本 | 错误 | 被限流 | P50 | P99 | 最大 | 要求 |
|---|---|---|---|---|---|---|---|
| 总览 | 1200 | 0 | 0 | 3ms | 8ms | 12ms | P99 ≤ 1 秒 |
| 单节点排查 | 9001 | 0 | 0 | 7ms | 19ms | 665ms | P99 ≤ 500ms |
| 配置检查 | 300 | 0 | 0 | 6ms | 15ms | 23ms | 无 |
| 数据库页 | 300 | 0 | 0 | 2ms | 9ms | 10ms | 无 |

- **总览的数字偏乐观**：没有 Prometheus，消息量、错误率、断开卡片直接返回不可用，没有真实查询的耗时。要在有 Prometheus 的环境里重测。
- **没有测**：Grafana 24 小时面板首次加载（5 次中位数 ≤ 3 秒）。`tools/ops-accept` 还没有实现这部分。

## 这一轮查出的问题

| 问题 | 影响 | 处理 |
|---|---|---|
| `Node.Call` 名额满时立刻失败（testenv 联调查出） | 几个工程师同时排查，正常节点被报成未响应，审计里还有没发到节点的查询 | 最多排队 500ms。这一轮 9001 次排查错误 0 |
| 压测工具的 `pace` 用 Ticker，来不及时丢节拍 | 工具实际只发约 491 条/秒，第一轮第 1 段吞吐 489，被判未通过。服务端没有积压 | 按已过时间补齐。修复后每段 500 条/秒，下限没改 |

## 没有验收

需要真实的 Prometheus、Grafana，放在同一台机器上才有意义：

- AC-OPS-90-1、90-2 的 Grafana 和 Prometheus 部分。
- AC-OPS-06-2（吞吐和 P99 面板读数）、06-10（每连接存活内存面板）。
- AC-OPS-07-8（GOMEMLIMIT 300MiB 15 分钟、800MiB 30 分钟）。

上线前还要在目标服务器上重测（C-50）：这里服务端和压测客户端抢同一台机器的 CPU，而且 macOS 的 fsync 比 Linux 服务器磁盘快得多。

## 复现

```bash
go build -o /tmp/im-server ./cmd/im-server
go run ./cmd/im-loadtest -bin /tmp/im-server -scenarios opsimpact -ops-segment 5m -ops-idle 10000 \
  -ops-phase-file /tmp/phase -ops-pubkey k1:<节点公钥> -ops-addr 127.0.0.1:19091 -server-env IM_NODE_ID=n1
```

同时在 tianting-console-server 里运行（节点表指向 `127.0.0.1:19091`）：

```bash
go run ./tools/ops-accept -tt /usr/bin/true -code <激活码> -admin-key-file <任意文件> -steps load -phase-file /tmp/phase
```
