# 内存分析 2026-11-03（Q5a）

> 起因：[压测报告](perf-2026-11-03.md)"观察 1"——1 万连接 + 600 条/秒时，进程 RSS 峰值 764 MB。
> 方法：在内网指标端口上加 pprof（`/debug/pprof/`，当时挂在 `IM_METRICS_ADDR` 上，现在移到了 `IM_PPROF_ADDR`），复现 1 万连接 + 600 条/秒 2 分钟 + 保持 4 分钟，每 30 秒采集堆快照和 Go 运行时指标。

## 结论

1. **不是泄漏**。修复后，保持阶段的存活内存（强制 GC 后读取）4 分钟内只增长 1.9%。
2. **峰值高的主要原因是 Go GC 的默认策略**：GOGC=100 时，堆允许长到"存活数据 × 2"才回收，而且从 Go 1.18 起 goroutine 栈也计入这个基数。1 万连接时存活约 316 MB，所以峰值在 550～750 MB 之间是预期行为。
3. **找到并修掉一个每连接的固定开销**：每条连接建立时就预分配一个 256 格的发送 channel（约 6 KB），并常驻一个写协程（栈约 8 KB）——空闲连接也一样。改为队列按需分配、写协程按需启动、写空即退出。
4. **macOS 上进程 RSS 不能用来判断泄漏**：同一进程 30 秒内 RSS 在 112 MB 和 557 MB 之间跳（系统内存压缩），而 Go 堆很平稳。压测工具改为用"强制 GC 后的 Go 堆 + 栈"判断增长，RSS 只作参考。之前报告里 TC-PERF-00-03 的"内存增长 −60%"同样是这个噪声。

## 修复前后（1 万连接，600 条/秒）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| goroutine | 20216 | 10115 |
| GC 目标堆（next_gc） | 约 534 MB | 约 390 MB |
| Go 堆 + 栈峰值 | — | 546 MB |
| RSS 峰值（参考） | 755 MB | 590 MB |
| 存活内存（强制 GC 后） | — | 316 MB，约 32 KB / 连接 |
| 吞吐 / 观测延迟 P99 | 600 条/秒 / 30 ms | 600 条/秒 / 36 ms |

每连接约 32 KB 的构成（修复后）：约 17 KB 是 Go 堆（net/http 和 WebSocket 库的读写缓冲各约 3～4 KB、连接对象、定时器、context），约 15 KB 是读循环 goroutine 的栈。再往下降需要换成基于 epoll 的网络库（每连接不占 goroutine），工作量大，集群化前不做。

## GOMEMLIMIT 实验

| | 不设上限 | `GOMEMLIMIT=300MiB` |
|---|---|---|
| Go 内存峰值 | 546 MB | 330 MB |
| 服务端 CPU 平均 | 26% | **493%** |
| ack 延迟最大值 | 66 ms | 225 ms |
| 吞吐 / 意外断开 | 600 条/秒 / 0 | 600 条/秒 / 0 |

300 MiB 低于存活数据（约 314 MB），Go 只能不停地 GC，CPU 涨了约 19 倍。这台机器 10 个核扛住了，小规格服务器会被拖垮。

## 部署建议

- **按每连接约 32 KB 估算存活内存**，再加吞吐带来的临时分配：1 万连接约 320 MB 存活。
- **设置 `GOMEMLIMIT`**，取容器内存的 80% 左右，并且**至少是存活内存的 1.5～2 倍**。例如 1 万连接：容器 1 GB，`GOMEMLIMIT=800MiB`。设得比存活数据还低会让 GC 持续运行、CPU 打满。
- 监控 `go_memstats_next_gc_bytes`、`go_memstats_heap_inuse_bytes`、`go_memstats_stack_inuse_bytes` 和 `go_goroutines`（都在 `/metrics` 里）；不要只看 RSS。
- 需要排查时，在内网用 `go tool pprof http://<IM_METRICS_ADDR>/debug/pprof/heap`。
