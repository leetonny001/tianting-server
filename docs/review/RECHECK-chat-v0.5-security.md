# PRD-chat v0.5 定向安全复审（编号 RS5）

评审方式：只读，走规格序列并核对代码。没有运行服务，没有读取密钥文件，没有改动文件。账号和文件功能都还没有实现，下面的序列都是规格推演，不是实测。

## 结论

**账号会话不能冻结。文件上传在规格层接近可冻结，但要先改 2 项（不考虑对象存储技术验证门）。**

RS4 列出的原始攻击序列，按新规则走基本都断了。问题在新设计自身。

**账号会话必须先改：**
- **RS5-01（阻塞）**：攻击者连续转正，可以一直续开软拒绝窗口，受害者的旧值永远触发不了重放吊销。
- **RS5-02（阻塞）**：攻击者手里有密码，就可以持续压制受害者的 `recover`。三个新规则叠加后，7 天保护实际可能用不上。
- **RS5-03（严重）**：调换操作顺序就能让受害者看不到找回截止日期，RS4-07 没有真正关闭。
- **RS5-04（严重）**：refresh MAC 和恢复码 HMAC 的密钥生命周期没有定义。按现有轮换流程操作，会让全员下线，恢复码也可能永久失效。
- **RS5-05（严重）**：`gen` 没有规定单调分配。代号一旦复用，已作废的 access token 会复活。

**文件上传必须先改：**
- **RS5-06（严重）**：崩溃或删除失败留下的随机键，没有任何机制清理。
- **RS5-07（一般）**：规则没写失败后释放租约，和 AC-FILE-01-13、01-20 直接矛盾。

## RS4 逐条状态

| 编号 | 状态 | 理由 |
|---|---|---|
| RS4-01 | 关闭（原序列） | 走一遍：攻击者改密得 C2，`recover{C2}`。规则只作废比 C2 更新的代，C1 保留，`retire_until` 不延长。第 6 天用 C1 找回，C2 及之后的代全部作废，符合 AC-ACC-05-17。先改密再注销的路径，靠规则 5a 也能救回。但攻击者可以改用压制手段，见 RS5-02。 |
| RS4-02 | 关闭（原序列） | R1→(A2,R2)→(A3,R3)，3 分钟后 A2 不在 `pending`，`auth` 和 `/v1/*` 都拒绝且不转正。窗口内用 A2 会转正并踢掉受害者，不再隐蔽。"一转正，受害者旧值就触发吊销"这个推论不完全成立，见 RS5-01；代号复用见 RS5-05。 |
| RS4-03 | 关闭 | A：改密吊销 `sid1`，共用 `sid1` 的攻击者被清除。B：响应丢失时，旧 refresh 返回 `credentialsChanged`，不算重放。C：SDK 串行；服务端的条件更新带 `revoked_at IS NULL`，失败重读后走吊销原因。前提是吊销判定排在重放判定之前，规则没写明，见 RS5-18。SDK 的边角见 RS5-15。 |
| RS4-04 | 部分 | 甲：Q1、Q2 的结果都留在 `pending`。乙：窗口内是 `superseded`，不吊销。这两条都断了。遗留：晚于窗口的重复请求仍会误吊销（PRD 已写明，频率未测）。另有一个 PRD 没写的路径：R3 已落盘但还没转正时，Q1 迟到超过 2 分钟，R3 按年龄被丢弃，客户端回来后被按重放吊销（见 RS5-21 的第 3 点）。 |

| RS4-07 | 部分 | 只有"离线设备 + 改密是第一个吊销原因"这条路径通了。在线、`logout-others`、注销这些路径仍然没有截止日期，`kicked` 帧也没有放日期的字段。见 RS5-03。 |
| RS4-08 | 部分 | ② 每次刷新都比较 IP 前缀，已改。④ 旧代 access 被拒绝，已改。① 和 ③ 如实写成盲区（R-19）。检测依赖受害者回来时触发重放，这一点受 RS5-01 影响。 |
| RS4-16 | 关闭 | 并发靠租约挡住。租约过期后的两个尝试分别写自己的随机键，`WHERE state='pending'` 只有一个提交成功，败者只删自己的键。"跳过"已取消，AC-FILE-01-20 覆盖。内容和记录来自同一次尝试，这一点成立。遗留见 RS5-06、RS5-07。 |
| RS4-17 | 关闭（规格层，厂商行为待验证门） | PUT 签入 Content-Type，Copy 用 REPLACE，AC-FILE-01-21 带恶意头。标签另算，见 RS5-21。 |
| RS4-18 | 关闭（规格层） | AC-FILE-90-1 的清单已补齐，Copy 后按响应 ETag 核对，412 已定义。验证门本身没跑。 |

## 查过、没发现问题的项目

1. **崩溃和转正的交错**：响应落盘前被杀时重用 R1，落盘后被杀时用 A2。用 `pending` 刷新已转正但响应丢失时，再用这个值（现在是 `current`）重试。都不会误吊销。
2. **转正踢线的循环**：两个持有同一条链的客户端不会无限循环，最终以重放吊销结束（攻击者主动续窗口的情况除外，见 RS5-01）。旧连接迟到的踢线被 `connGen` 挡住（`connection.ts` 第 189～194 行，Kotlin `Connection.kt` 第 181～183 行，Swift `Connection.swift` 第 181～192 行）。
3. **窗口内旧值**：攻击者拿不到新凭证。
4. **恢复码并发**：旧码和新码同时 `recover`。旧码先提交，新码那一行已作废，新码失败。新码先提交，旧码随后仍成功并作废新码。旧码都赢（在 RS5-02 改掉版本条件之后也成立）。
5. **旧码被窃取**：持旧码的人 7 天内能抢走账号，受害者换码也无法立即废掉，R-1 ③ 已如实写明，属于已接受的取舍。多次改密不延长，AC-ACC-05-17 覆盖。
6. **攻击者改密后立即注销**：7 天窗口和冷静期相同，受害者窗口没有被缩短。
7. **改密或退出响应丢失后留下的新 `sid`**：没人持有 token，只是多算一个"其他会话"，到期清理，没有安全影响。
8. **`logout-others` 不递增 `credentials_version`**：在途的登录可能留下，但它不改密码，攻击者本来也能再次登录，不算新漏洞。
9. **`recover` 的等时**：未命中路径对存在和不存在的账号都只算一次 HMAC 并查一次，AC-ACC-05-11 逻辑上可达；命中路径只有持码人能观察到。
10. **额度复查**：提交事务内原子检查时，确实最多超额一个文件。第二天额度重置不会放大。
11. **文件竞态**：两个尝试写不同随机键，败者不会覆盖或删除对方。`pending→purging` 和 `complete` 只有一个生效。头像绑定前公开桶没有对象。
12. **现有代码的支撑**：
    - 都是新增工作，但没有结构障碍。`Claims` 和 `jwtClaims` 要加 `sid`、`gen`（`token.go` 第 23～34 行）。`Hub` 按用户索引，每用户连接数有上限，按 `sid` 过滤踢线容易做（`hub.go` 第 147～158 行）。入表后复查的位置已有（`gateway.go` 第 166 行，确实是 `err == nil &&`，RS4-09 的引用正确）。
    - `clientIP` 还在 gateway 内部（`guard.go` 第 86 行），要提出来。对外端口还没有 `/v1/` 路由（只有 `/internal/v1/`）。
    - SQLite 只有 1 个连接（`sqlite.go` 第 51 行），Argon2 和 Copy 必须在事务外，规则已这样写。
    - 三套 SDK 现在收到 4011 都不重连并结束（`connection.ts` 第 280～285 行），规则 7 要改三套 SDK。

## 没能验证的事情

- **对象存储行为一项都没有实测**：条件 Copy、REPLACE 是否清除头部、标签、加密下的 ETag、生命周期取整。结论都建立在"厂商符合规范"之上（凭规范和记忆）。
- **Postgres 下的条件更新语义未验证**：`server/internal/store` 里没有看到 Postgres 实现。规则 8 依赖"UPDATE 阻塞后重新评估 WHERE"，这是 READ COMMITTED 的知识，不是实测。
- **SDK 没有逐行审**：只读了 TS 的连接和踢线部分，Kotlin、Swift 只用搜索确认了 `connGen` 和关闭码。各 App 的 `fatal` 处理、token 存储的写入方式（是否同步落盘）都没查。
- **没有测量**：Argon2 实际耗时（RS5-02 的命中率是估算，甲序列的碰撞概率随耗时变化）、响应丢失和迟到请求的真实频率。文中建议的所有数字都未校准。
- **待确认**：SDK 超时和网关超时之和是否真的小于 2 分钟（OkHttp、URLSession 的隐式重试没查）；RS5-21 的 Copy 复制标签行为。
- **范围外未审**：F-ACC-03 规则 7～13 只看了相关部分；F-ACC-03 规则 9（`navigator.locks`）只顺带读过，页面刷新时旧页释放锁和新页抢锁的时序没有审，但 AC-ACC-03-9 依赖它，建议实现时注意；F-FILE-02～05 只看了和规则 3b、Content-Type 相关的部分。第 16 节没看。
- **之前的评审**：没有复核 RS4-09～15、19～25 的处理是否正确，只在和本次范围相交时提到。
