## 1. 结论汇总

| 视角 | 阻塞 | 重要 | 建议 | 合计 |

（一条问题可能涉及多个视角，按主视角计数。）

整体评价：安全基座的骨架是对的：独立 BFF、浏览器拿不到管理密钥、服务端会话 + `__Host-` Cookie、RBAC 白名单、正文默认不可见、审计只追加。这一版比大多数后台 PRD 完整。主要问题有四类：
1. **BFF 的存储和凭证没想清楚**：AC 实际上要求 BFF 一开始就用支持 GRANT 的网络数据库，但 PRD 没写，也没有拍板项。另外，旧的 `X-Admin-Key` 和公网端口上的 `/admin/*` 能直接调用所有新的敏感接口，后台的全部管控都能被绕开。
2. **悄悄改了已冻结的约束**：禁言、删消息、系统推送在 PRD-core 第 7 节和 D1 中是二期，这里直接定为 P0；ARCH 的 S8 从 P1 提前；errors.json 的号段规则被打破。这些都没有作为变更列出来。
3. **错误码与会话交互互相打架**：4017（需要重新验证）返回 401，前端又规定"任何 401 都跳登录页"，结果是每次需要重新验证都会被踢回登录页。
4. **和 PRD-ops 在账号、审计、部署形态上冲突**：共用一个 BFF 还是分两个进程、单角色还是可叠加、哈希链 P0 还是 P1、审计写失败后怎么处理、保留期多长，两份都不一样。双方共用审计存储，不对齐的话两份都没法冻结。

**结论：修改后提交拍板**（见第 6 节）。

## 5. 范围与分批

- **工作量粗估**（以现有代码为基准）：BFF 安全基座（登录、TOTP、会话、锁定、RBAC、两阶段审计 + 哈希链、启动保护）约 12～15 人日；im-server 缺口（凭证与内网监听、搜索和分页、封禁、解散、删除、禁言、Presence 接口和迁移）约 15～20 人日；两套 SDK（删除、禁言、解散、兼容）约 8～10 人日；后台前端约 12～15 人日；推送另计（依赖二期协议）。整体是**一个中等里程碑**，而 PRD 第 3 节把这些全部列为 P0，又没给排期，不现实。
- **建议的顺序**：D-ADM-09 / 10 / 12 拍板 → 凭证、内网监听、存储迁移 → 第一批（不改协议）→ PRD-core v1.3 和协议 Schema 定稿（含兼容规则 R-ADM-18）→ 服务端加两套 SDK 同时实现 → PRD-ui 补齐 → 第二批 → 二期 push 协议 → 第三批。
- P1 / P2 的划分基本合理。只有两处要调整：G-ADM-19（原文隔离保存）要提前到 P0，或者换成别的 P0 做法（R-ADM-19）；"锚定链头"要提前到 P0（R-ADM-08）。
