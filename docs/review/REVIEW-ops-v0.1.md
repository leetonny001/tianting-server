## 1. 结论汇总

| 视角 | 阻塞 | 重要 | 建议 | 合计 |

> 每条问题只按主视角计数一次；表中"视角"一栏可能列出多个。

整体方向是对的：只读为主、不进公网、用户级数据只放在自己能控权限和审计的系统里、图表和告警交给 Prometheus / Grafana / Alertmanager、不给 im-server 加 HTTP 备份接口。规则写得细，AC 大部分有具体输入和预期。

主要问题集中在五处：
1. **节点运维接口的服务凭证太弱**：一把静态共享 token、明文传输、操作人请求头可以伪造、会把 token 发给注册表里自报的地址。拿到 token 就能绕开"填原因 + 审计"直接查任意用户的连接。同期的 PRD-admin 对同类调用要求 HMAC 签名 + TLS，两份文档的安全级别不一致。
2. **与 PRD-admin 的"共用"只是口头上的**：账号、审计、部署形态都说"与 PRD-admin 对齐"，但两份文档的具体规定互相冲突。按 D-OPS-02 推荐的共用身份，管理后台超管可以重置运维账号的密码和 TOTP，直接接管运维权限，与 F-OPS-02 规则 3 矛盾。
3. **"请求备份"与"只读凭证"互相矛盾**：F-OPS-13 要 `ops-server` 往备份存储写标记，而 AC-OPS-12-5 要求它的凭证不能写。如果给了写权限，`ops-server` 被攻破后还能伪造"备份成功"清单，让"备份过期"告警失效。
4. **断开记录覆盖不到最常见的掉线原因**：握手阶段的关闭（4401、4010～4012）不进 `conn closed` 日志，也不进 `im_disconnects_total`。AC-OPS-09-3 在现有设计下做不到，因为 4401 发生时服务端还不知道 userId。
5. **工作量估算明显偏低**：11～13 人日没算 im-server 改造、部署、测试，以及一套完整的登录 / TOTP / 审计。按功能点重估约 28～40 人日。

## 5. 结论

**修改后提交拍板。**

不需要重写。功能范围、只读边界、混合建设方式、"用户级数据只放在自研系统里"这些判断都站得住。6 个阻塞项集中在两类：一是安全设计（节点凭证、共用身份接管、请求备份的写权限），二是与 PRD-admin 的"共用"没有真正对齐（审计、部署形态）。另外有一条 AC 在现有架构下做不到（握手阶段的断开记录）。

阻塞项的修改工作量（产品侧）：
- R-OPS-01、05、06：只改本 PRD，约 1 人日。
- R-OPS-02、03、04：需要先与 PRD-admin 一起拍板 D-OPS-09 / 10（可以和 D-ADM-01 / 02 / 08 在同一次会上定），然后两份 PRD 同步修改，约 1～1.5 人日。
- 合计约 **2～2.5 人日**。把 25 条重要问题一起改掉，再加约 2 人日。

对开发排期的影响：总估算应从 11～13 人日上调到约 **28～40 人日**；如果与管理后台共用 BFF 的账号、会话、审计模块，可以省约 6～8 人日。R-OPS-01 选 mTLS 时 im-server 侧另加约 1～2 人日。

建议的顺序：先开一次会，合并拍板 D-OPS-02 / 09 / 10 和 D-ADM-01 / 02 / 08；产品据此修订 PRD-ops 和 PRD-admin 到 v0.2；再由测试复核附录中标为"不可测"和"需双节点"的 AC。
