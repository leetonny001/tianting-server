三方都认可整体方向和核心消息链路（seq、去重、补拉、多端同步）。主要问题集中在：**会话列表缺数据模型和协议**、**历史消息不能往前翻页**、**浏览器读不到 401**、**缺测试开关**、**未读数公式错误**。

合并重复项后，共 **31 个问题**（R-01～R-31），产品回应如下。

## 2. 阻塞问题

| 编号 | 来源 | 问题 | 产品回应 | 处理 |
|---|---|---|---|---|
| R-01 | BR-1、FR-2、FR-4、BR-7 | 没有会话列表协议，服务端也没有"用户 → 会话"的索引；重连只补拉本地已有的会话，离线期间新出现的会话会漏掉 | **接受** | 新增 WS 命令 `convs`，返回 `{convId, type, name, maxSeq, readSeq, minSeq, unread, lastMsg, updatedAt}`，一期全量返回，上限 500 条。服务端新增 `user_conv`、`conv_last` 两张表，在 send 事务里维护。重连流程改为：先拉 `convs`，再只对 `服务端 maxSeq > 本地 maxSeq` 的会话 `sync`；缺口超过 200 条时直接拉最新一页，再往前翻 |
| R-02 | FR-3、BR-13、Q3 | `sync` 不能往前翻页，打开会话显示的是最早的消息而不是最新 20 条 | **接受** | `sync` 增加 `beforeSeq`，与 `afterSeq` 二选一；返回 seq < beforeSeq 的最近 limit 条，按升序排列，带 `hasMore`。打开会话时用 `beforeSeq = maxSeq + 1, limit = 20` |
| R-03 | FR-1 | 浏览器的 WebSocket 拿不到 HTTP 401，token 失效和断网分不清，客户端会无限重连 | **接受** | token 无效时服务端**先完成升级**，下发 `event/kicked`（原因新增 `tokenInvalid`），再用 close code 4010 关闭。客户端收到 `kicked` 或 4010 后不重连 |
| R-04 | QR-1、BR-14 | 没有测试开关：token 不能几秒就过期；心跳、超时写死；没法制造"已保存但 ack 丢失"和"seq 缺口" | **接受** | PRD 新增"6.1 测试环境要求"：测试模式下 `ttlSeconds` 最小可以是 1；心跳、空闲超时、发送超时、退避上限都可配置；服务端测试模式提供故障注入（丢弃指定 `clientMsgId` 的 ack、跳过指定消息的实时投递），**生产构建默认关闭**；SDK 支持注入假传输层和假时钟；每个用例都从干净的库开始 |
| R-05 | BR-2、FR-7 | "maxSeq − readSeq"会把自己发的消息算进未读 | **接受** | 规则改为"**发言即已读**"：send 成功时，服务端在同一事务里把发送者的 readSeq 推进到新 seq；客户端在收到 ack 时同步推进本地 readSeq |
| R-06 | QR-7、BR-Q2、FR-Q2 | 新成员能看到哪些历史没定，未读数和翻页都写不出验收标准 | **建议采用方案 B，待你拍板（D2）** | 入群时记录 `join_seq`（当时会话的 maxSeq）；sync、翻页、未读都只算 `seq > join_seq` 的消息；`convs` 返回 `minSeq = join_seq + 1`，翻到这里时 `hasMore = false`；被移出后再加回来，`join_seq` 重置 |

## 3. 严重问题

| 编号 | 来源 | 问题 | 产品回应 | 处理 |
|---|---|---|---|---|
| R-07 | BR-3、QR-6 | 已连接时 token 到期不会被踢；被封禁后旧 token 仍可立即重连；先入队 kicked 再关闭连接，kicked 帧可能发不出去 | 接受 | 连接上记录 token 过期时间并挂定时器；新增用户维度的 `tokens_valid_after`，"强制下线"时更新为当前时间，之前签发的 token 全部失效（解封方式 = 业务方重新签发 token）；kicked 帧**写完再关闭** |
| R-08 | BR-6、FR-19 | 被拉进群、被移出群时客户端收不到通知 | 接受 | 新增事件 `convAdded`、`convRemoved`，并同步更新 Schema 和用例 |
| R-09 | BR-4、BR-5 | 群人数上限只按单次请求校验，多次加人可以超过 2000；空群会误报 4040；sync 对不存在的群返回 4030；409 的响应体里 code 是 4000 | 接受 | 先查群是否存在：不存在一律 4040，非成员 4030；加成员时在事务里校验总人数；群名 1～50 字、建群时成员可以为空；冲突新增错误码 4090 |
| R-10 | QR-2、FR-12 | "断网"有两种：浏览器离线，和网络在线但服务端不可达，检测时间差很多；"500ms 内反映"和"1 秒内的闪断不显示"互相矛盾 | 接受 | 区分场景 A（浏览器离线，用 Playwright 的 `setOffline`，3 秒内提示）和场景 B（服务端不可达：客户端发心跳后 10 秒收不到 pong 判定断线，用 SDK 假传输层测试，不引入 toxiproxy）；提示条统一为"**断开持续超过 1 秒才显示**" |
| R-11 | QR-3 | "1 秒内"没说明是单次还是 P99、样本多少、在什么环境 | 接受 | 功能用例只验证"收到了"；延迟单独写成性能用例：本机环境、连续 100 条、P99 ≤ 1 秒，由同一个测试进程计时 |
| R-12 | QR-4、FR-13、BR-8 | 文本长度的计数单位不明确；服务端不去首尾空白 | 接受 | 统一按 **Unicode 码点**计数，**先去首尾空白再计数**（包括 `\n`、`\t`、全角空格）；服务端同样去空白后校验并存储；补充边界用例：1、5000、5001 个字符，5000 个 emoji，空白字符 |
| R-13 | QR-5 | F-AUTH-01 的边界值和有效期默认值没有验收标准 | 接受 | 补充：`userId` 长度 0、1、64、65；含空格、中文、`.`、`@`；不传有效期 / 0 / 负数按 7 天；30 天、31 天 |
| R-14 | FR-9、QR-8 | 发送状态的"10 秒超时"和"离线排队、重连后自动重发"冲突；待发消息在列表中的位置没定义 | 接受 | 新增发送状态机：在线时从发出开始计 10 秒；离线时先进队列，重连后发出才开始计时，只自动重发 1 次；未确认的消息排在已有 seq 的消息之后，收到 ack 后按 seq 归位 |
| R-15 | FR-8 | 实时消息本来就可能乱序，一出现缺口就补拉会频繁误触发；ack 带回的 seq 算不算进 maxSeq | 接受 | 出现缺口后等 500ms，还没补上再 `sync`；ack 带回的 seq 也更新 maxSeq，并参与缺口判断 |
| R-16 | FR-10 | 重发时，同一条消息可能先经 `sync` 回来，需要靠 clientMsgId 和本地待发消息合并，但 Schema 里它是可选字段 | 接受 | `msg` 和 `sync` 里的消息**一律带 `clientMsgId`**，Schema 改为必填 |
| R-17 | FR-5、FR-6、Q5 | "先显示本地缓存"和"只存内存"矛盾；刷新、多标签页的行为没定义 | 接受 | 一期 H5：不用 IndexedDB；token 存在 `sessionStorage`（每个标签页独立，方便同一浏览器开两个标签页演示互聊）；刷新后自动重连，重新拉会话列表和最新 20 条；`/chat/:convId` 刷新后留在原会话；有待发或失败的消息时，`beforeunload` 提示"刷新会丢失"；IndexedDB 放到 P1 |
| R-18 | QR-9 | 约 20 条业务规则没有验收标准 | 接受 | PRD v1.0 逐条补齐（见附录：规则 → AC 对照） |

## 4. 一般问题和建议

| 编号 | 来源 | 处理 |
|---|---|---|
| R-19 | QR-10、BR-10 | 同一个 `clientMsgId` 发到另一个会话时返回 4000；内容不同但 clientMsgId 相同，按第一次的结果返回（以 clientMsgId 为准） |
| R-20 | QR-11 | 补充边界：2000 人可以，2001 人不行，1999 人时一次加 2 人不行；未读 99 显示"99"，100 显示"99+"；验收标准里注明是 HTTP 状态码还是 WS 错误码 |
| R-21 | QR-12 | 把捆绑了多项检查的验收标准拆开；"最终"改为"最后一个 ack 之后 10 秒内" |
| R-22 | QR-13、BR-12 | 多端用例改为"两个浏览器上下文，分别用 platform=web 和 platform=pc"；非法 platform 返回 400 |
| R-23 | QR-14 | 时间一律以服务端为准；时间相同时按 convId 排序；客户端时钟偏差不影响排序 |
| R-24 | BR-9 | `read` 上报的 seq 截断为 min(seq, maxSeq) |
| R-25 | BR-11 | 补充吞吐指标 ≥ 500 条/秒；群成员缓存在内存里，成员变更时失效；SQLite 设置 `synchronous=FULL`，保证"已确认即落盘" |
| R-26 | FR-11 | 单聊会话 ID 按 ASCII 字节序比较（补充用例）；send 的 ack 增加 `convId` |
| R-27 | FR-14、FR-18、FR-17 | 纯文本渲染，禁止 innerHTML（补充 XSS 用例）；保留换行，长串自动断行；PC 上 Enter 发送、Shift+Enter 换行。时间：间隔 5 分钟以上才显示；今天显示 `HH:mm`，昨天显示"昨天 HH:mm"，今年显示 `MM-DD HH:mm`，更早显示 `YYYY-MM-DD`。距底部不超过 100px 算"在底部"；"↓ 有新消息"显示条数；加载历史后可视位置不跳动。**iOS 键盘弹起的行为只做手工验证** |
| R-28 | FR-15、FR-20、FR-21、FR-22 | 补齐空、加载中、出错状态和对应文案；退出登录时清空内存和 token，不重连；发起单聊时校验格式，空会话只在本地临时显示；被踢文案：tokenExpired 显示"登录已过期"，banned 显示"账号已被下线"，tokenInvalid 显示"登录已失效" |
| R-29 | FR-16 | 只有页面可见、并且正停在该会话时才上报已读，上报做节流（1 秒） |
| R-30 | QR-15 | 演示登录服务默认关闭；验证方法：在构建产物和抓包记录里搜索管理密钥 |
| R-31 | BR-15、Q6 | 给不存在的 userId 发消息照常成功，会话出现在发送方的列表里（写成验收标准）；一期加单用户发送限流：每秒 20 条，超出返回 4290 |

**页面调整（前端建议，接受）**："我的"页并入会话列表右上角菜单；"发起单聊"改成弹窗；聊天页顶栏显示会话名，群聊加成员数；新增**演示面板**（连接状态、各会话 maxSeq、"模拟断网"开关），现场演示断网重连比拔网线可靠。PC 三栏布局放到 M4。

### 5.1 拍板结果（Frank，2026-10-31）

| # | 决定 | 与产品建议 | 带来的变化 |
|---|---|---|---|
| D1 | 不提前 | 一致 | — |
