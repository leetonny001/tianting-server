## 二、阻塞

### RC2-01 响应丢失超过 30 秒就吊销会话，且放行理由是错的
- **位置**：F-ACC-03 规则 3、4（L308、L309）；AC-ACC-03-2、03-13；23.1（L1816、L1817）；20.2（L1758）
- **问题**：
  - 服务端先轮换，响应没到，客户端手里只有 R1。超过 30 秒再用 R1，就按重放吊销。
  - 触发场景：刷新请求发出后切后台被挂起、进电梯后几分钟才恢复、请求途中进程被杀。每台设备约每 18 小时刷新一次，这是常见路径。
  - L1817 写"新 token 先落盘已经解决了进程被杀的情况"，**这不对**。落盘只覆盖"响应已到达之后被杀"（AC-ACC-03-13），响应到达前被杀没有覆盖。
  - 后果比"重新登录"重：吊销时同一事务删除推送令牌（L706）。用户不打开 App 就不再收到通知，也不知道原因。
  - L1817 说"上线后看数据"，但只有 `im_refresh_grace_total`（L1534），只统计 30 秒内的重试。误吊销完全不可见。真被盗也没有 `securityNotice`（L281 不含这一类）。
  - L1758 把它列为"技术问题"，Frank 看不到这个体验代价。
- **证据**：L308、L309、L706、L1534、L1817；评审 R-CF-09 第 2 点（REVIEW L457）
- **建议**：
  - 改成"新一代被首次使用才生效"。R1 保持有效，发出 R2 作为待确认，R2 或它的 access token 首次使用时才转正。
  - R2 待确认期间再次收到 R1：作废 R2、发 R3，不限时长。始终只有一条链，同时满足 R-CS-05 的单链要求和 R-CF-09 第 2 点的不误吊销。
  - 代价：R1 的有效期延长到新 token 首次使用，这一点要安全复审。
  - 增加 AC：响应丢失 5 分钟后重试不吊销；响应到达前杀进程。
  - 增加重放吊销指标和用户提示。
  - 如果坚持现方案，要把"弱网会被踢下线"写进 CH-26 或新的 CH，并删掉 L1817 的错误理由。

### RC2-02 改密码同时作废恢复码：密码被盗等于账号永久丢失，CH-01 没说
- **位置**：F-ACC-04 规则 3（L347）；F-ACC-05 规则 5（L376）；AC-ACC-04-9；F-ACC-08 规则 2（L449）；CH-01（L1728）；R-1（L1697）
- **问题**：
  - R-CS-18 的修法只防了"丢手机"。反向场景更严重：撞库拿到密码（用户名公开，R-17）→ 改密，受害者的恢复码随即作废 → 受害者没有任何手段，也没有客服。
  - "重新生成恢复码"同样只要密码（L376）。
  - 注销冷静期的目的是防密码被盗后账号被毁（L449）。但攻击者先改密再申请注销，受害者既登录不了也撤销不了，这个目的落空。
  - R-1 只写了"恢复码被拿到"，CH-01 只写了"恢复码丢了"，都没写密码被盗这条路径。这直接影响 CH-01 的取舍。
- **证据**：L347、L376、L449、L1697、L1728；评审 R-CS-18 原文是"强提示重新生成**或**直接换新"（REVIEW L1145 起），不是唯一方案
- **建议**：
  - 改密和重新生成都不立即作废旧码，旧码保留 7 天（未校准）并在可信设备上提醒；找回优先于改密。
  - 把这条路径写进 R-1 和 CH-01 的"影响"栏。
  - 定义冷静期内是否能走 `recover`。

## 三、严重

### RC2-03 恢复码换代后，确认状态的处理没有定义
- **位置**：F-ACC-05 规则 1、3、5（L372～L376）；F-ACC-04 规则 3（L347）
- **问题**：
  - ① `recovery_acked_at` 只写了注册场景。改密、找回、重新生成时，响应丢失就是旧码已废、新码没人见过，而状态仍是"已确认"。用户悄悄失去了找回能力，这正是 R-CF-10 要修的那类问题。
  - ② `recovery-code/ack` 不绑定是哪一个码。D1 停在保存页显示 C1，D2 登录生成 C2，D1 点"我已保存"后状态变成已确认，但用户保存的是废码。
  - ③ L277"响应没有 `recoveryCode`"和 L372 矛盾。
- **证据**：上述行；AC-ACC-05-6 只测注册响应丢失
- **建议**：每次换码都清空 `recovery_acked_at`；ack 带码的代号；补两条 AC；修正 L277。

### RC2-04 refresh 的并发规则缺失
- **位置**：F-ACC-03 规则 4、5、7；AC-ACC-03-3；L1816
- **问题**：
  - 启动、回前台、定时器、`kicked/tokenExpired` 四个入口都会触发刷新，正文没有 SDK 单飞（全文搜不到）。
  - 客户端超时重试后，迟到的第一个响应如果覆盖了新值，下一次刷新就会吊销。
  - 服务端没有要求比较并交换（CAS）。Postgres 下两个并发的 R1 可能都通过。`prevHash` 在二次重试时怎么变也没写。
  - 没有"同一 R1 并发"的 AC，AC-ACC-04-8 只测和改密的并发。
- **建议**：写明 SDK 单飞、丢弃已放弃请求的响应；服务端用条件更新；补两条 AC（并发 R1、连续重试 3 次）。

### RC2-05 注销流程有矛盾：撤销接口用户根本调不到
- **位置**：L1313；AC-ACC-08-1、08-4；F-ACC-08 规则 2 和异常（L449、L463）；L1304
- **问题**：
  - L1313 把 `delete/cancel` 列为 Bearer + `sid`。但冷静期会话全部吊销，AC-ACC-08-1 又要求登录响应"没有 token"，所以调不了。
  - 登录响应的形状和错误码都没定义。
  - 踢线原因三处不一致：L1304 新增 `accountDeleted`，正文没人用；L463 写 `kicked/banned`；冷静期吊销按 L307 是 `sessionRevoked`。
- **建议**：改成匿名 + 用户名密码，或发一个只能用于撤销的短期凭证；定义响应；三处统一。

### RC2-06 待退出补发无法鉴权
- **位置**：F-ACC-04 规则 1（L345）；L1313；AC-ACC-04-6
- **问题**：`logout` 要 Bearer，但待退出只保留 `sid` 和 refresh token，AC 要求恢复网络后吊销成功。
- **建议**：`logout` 接受 refresh token。

### RC2-07 `complete` 期间有竞态，临时键 + Copy 没有堵住 TOCTOU
- **位置**：F-FILE-01 规则 3（L507）；AC-FILE-01-9；第 21 节必需能力（L1777）
- **问题**：
  - HEAD、嗅探、Copy 是三次独立请求，PUT 地址 15 分钟内一直有效。持续 PUT 可以在检查通过后、Copy 之前换掉对象。
  - 进入最终键的就是没检查过的内容，可绕过大小、配额和禁止类型。
  - L507 的"`complete` 之后再覆盖没有意义"只覆盖事后，AC-FILE-01-9 也只测事后。
  - 响应头由服务端固定，所以不是 XSS，但 R-CB-08 和 R-CS-11 没有完全关闭。
- **建议**：
  - Range 读和 Copy 都绑定 HEAD 得到的 ETag（`x-amz-copy-source-if-match`）。Copy 后再 HEAD 核对最终键，不符就删除。
  - 这条要进第 21 节必需能力和冻结前技术验证。目标厂商是否支持**未核实**。
  - 假 S3 增加这个竞态场景的 AC。

### RC2-08 Copy 的失败路径和临时键残留
- **位置**：L507、L508；L648；L1777
- **问题**：
  - ① "Copy 到最终键，再删除临时键"没说删除时机。原图删了、缩略图 Copy 失败后重试，原图 HEAD 就会失败。AC-FILE-01-10 没有覆盖这个分支。
  - ② `complete` 后 PUT 地址仍有效，重新 PUT 会在临时键上生成新对象。状态已是 `attached`，`file_purge` 只清 `pending` / `ready`，临时键删除失败也一样。这些对象不计配额，也没有人清理。
  - ③ L1777 把"限制上传大小"列为必需能力，结尾又写"不依赖强制校验大小"。L505 也没要求签入 Content-Length。
  - ④ 配额只在申请时检查（L510），`complete` 不复查，并发上传最多超额 20 × 100 MiB。这一点没有说明。
- **建议**：所有变体 Copy 成功并提交事务后才删临时键；临时前缀的生命周期规则改为必需；预签名固定 Content-Length；写明允许的超额。

### RC2-09 未完成上传数 20 个 + 24 小时清理 + 没有取消接口：弱网用户会被锁
- **位置**：L510；L516；L648；L1314；L1450；AC-FILE-01-11；AC-FILE-07-7
- **问题**：
  - 失败重传用新的 `fileId`（L516），旧的 `pending` 要等 24 小时才清。
  - 一次最多选 9 个，弱网下失败 3 轮就到 20 个，之后最长 24 小时不能发文件。
  - 这个错误是可重试的 4290（`errors.json`），SDK 还可能反复重试。
  - SDK 有 `cancelUpload`，但 L1314 没有对应的服务端接口。
  - 这是 R-CS-21 和 R-CF-01 合并后产生的新矛盾，23.1 判断"互不冲突"不成立。
- **建议**：只统计 PUT 未过期（15 分钟内）的 `pending`；增加取消接口或让新申请顶掉最老的；单独给 `reason`；补 AC。

### RC2-10 "服务端覆盖本地值"会让已清除的内容复活
- **位置**：F-RCL-03 规则 2a（L898）
- **问题**：

- **证据**：`store.ts:63-64, 91-99, 119-124`；`Store.kt:150-157, 187-190`
- **建议**：`deleted`、`recalled`、`expired` 只能从假变真；`quote.state` 只能从 `normal` 往后走；`deletedIds` 继续优先。向量和 AC 增加"迟到的旧 `sync`"。
