# PRD-chat v0.7 定向安全复审（编号 RS7）

评审方式：只读，走规格序列。只读了 RS6 报告、MinIO 结果、PRD 的相关规则和第 27 节，以及合同测试工具的片段。没有读全文，没有运行任何东西，也没有读密钥文件。账号和文件功能还没实现，下面的序列都是规格推演，不是实测。

## 结论

**账号会话和文件上传现在都不建议冻结，但差距很小。没有阻塞项，有 3 个严重项，每项改一两句规则加 1 条 AC 就能解决，改完可以冻结，不需要再审一轮完整的。**

RS6-01～05 的原序列按新规则走，RS6-01、03、05 关闭，RS6-02、04 的主序列关闭，但修法各留一个缺口：
- **账号会话**：RS7-01（RS6-01 的同类竞态，只是没有写恢复码的事务没被覆盖）、RS7-02（`recover` 成功次数上限反过来压制受害者）。
- **文件上传**：RS7-03（公开键先写库后，崩溃且不重试时公开对象仍然永久残留）。

另外，第 21 节第 4 行写的是云厂商验证要在冻结前做，而 CH-05 还没选，AC-FILE-90-2 又写的是上线前。这条要先改口径，否则按 PRD 自己的条件冻结不了。

## 逐项状态

| 编号 | 是否关闭 | 理由 |
|---|---|---|
| RS6-01 | 关闭（设计成立，未运行） | 按 READ COMMITTED 走原序列：`recover` 第一条语句锁 `accounts` 并递增版本后，攻击者的 `UPDATE … WHERE credentials_version=?` 会等待，重新求值后影响 0 行，返回 401，Cx 不会产生。改密先提交的话，`recover` 等到锁后，后续语句是新快照，能看到 Cx 并作废它。两个不同代的 `recover` 也被这把锁串行：C1 先提交，Cn 随后检查失败；Cn 先提交，C1 随后作废 Cn+1。没写码的事务有同类缺口，见 RS7-01。 |
| RS6-02 | 部分 | 原序列关闭：同一个码只算 1 个，老码优先，受害者持最老的码时不受上限限制，排队最多等一轮。受害者的码不是最老时，新加的上限会拒绝它，见 RS7-02。 |
| RS6-03 | 关闭（只在 MinIO 上验证） | 第 11.3 节给了最终前缀的 List，`file_purge` 不再得到 403，也不用退回只删记录里的键。合同测试用真实权限的凭证通过了 3 项：按前缀列举、全桶列举被拒绝、按前缀列举并逐个删除。规则 9 和第 21 节的"禁止列举"已限定为匿名和预签名。云厂商还没验证。 |
| RS6-04 | 部分 | 甲关闭：换头像 7 天后和注销清理都进入 `purging`，同时删 `public_key` 和 `final/{fileId}/`，`files` 行也清除，AC-ACC-06-12 有检查。乙只在重试时关闭：重试复用同一个键，公开桶只有 1 个对象。崩溃后不重试的路径没有覆盖，见 RS7-03。 |
| RS6-05 | 关闭 | 攻击者转正并用满 20 次后，受害者的 R1 在第 ⑤ 步就得到 `superseded` 或 `replayDetected`，到不了第 ⑥ 步。AC-ACC-03-48 能区分两种顺序。这个修法没有引入新的严重问题。 |

## 新问题

| 编号 | 严重度 | 位置 | 序列 | 后果 | 建议改法 |
|---|---|---|---|---|---|
| RS7-01 | 严重（只在 Postgres 下可达，取决于实现） | F-ACC-04 规则 6、8；第 4.3 节；AC-ACC-04-18、04-29 | RS6-01 的修法只要求"写恢复码的事务"按顺序加锁，第 4.3 节也只写了顺序，没写谁必须拿锁。`logout-others` 不改 `accounts` 的任何字段，没有东西可以"条件写"，自然的写法是先 SELECT 版本。① 受害者 `recover` 锁行、递增版本，未提交。② 攻击者在途的 `logout-others`（已过 Argon2）读到旧版本（未提交的改动看不到），校验通过，插入新 `sid`，未提交。③ `recover` 吊销全部会话，这条语句看不到未提交的新行，然后提交。④ 攻击者提交。登录如果用 `INSERT … WHERE EXISTS` 或 SELECT 校验版本，同样可达。 | 找回成功后，攻击者仍持有用旧密码换来的有效会话。`auth` 只查 `sid` 是否吊销，这条会话可以滑动续期到 365 天，受害者以为已经清除。AC-ACC-04-18 现在在 SQLite 上跑，事务串行，测不出来；AC-ACC-04-29 只测改密。 | 规则 8 写明：**所有用密码的提交事务，第一条语句都锁 `accounts` 行（`SELECT … FOR UPDATE`，或不改值的条件 UPDATE），持锁后再校验版本和 `sid`**，不只是写恢复码的事务。AC-ACC-04-29 扩展到登录和 `logout-others`：放行后预期 401，`recover` 提交后这个账号只有受害者的会话。 |
| RS7-02 | 严重 | F-ACC-05 规则 2；AC-ACC-04-30 | 上限的豁免只给"账号里最老的有效码"。第 0 天，受害者怀疑泄露，改密得到 C2 并确认，丢弃 C1（C1 第 7 天到期）。第 1 天，攻击者改密得到 C3，C2 第 8 天到期。攻击者脚本 `recover{C3}`→C4→…，每小时开始就用完 6 次。用新代找回不作废旧代，所以 C1 仍然是最老的，只有它豁免。受害者的 C2 不是最老，被上限拒绝，第 7 天 C1 到期后才豁免。两次改密间隔越短，这段时间越短，间隔 0.1 天时只剩约 2.4 小时。规则 6a 已经承认"受害者持有的码比这个更新"是存在的情况。AC-ACC-04-30 只测了 C1 比 Cn 老。规则 2 也没写被上限拒绝时返回什么；如果和未命中一样返回 401，受害者会以为码错了。 | 受害者手里的有效码有接近 7 天用不了，最后只有很短的窗口，账号很可能永久丢失。最容易中招的正是刚因为担心泄露而改过密的人。反过来，这个上限对攻击者的单码账号也不起作用：每次找回后，新码就是唯一的有效码，也就是"最老"，永远豁免。 | 把上限改成**只约束账号当前最新一代，其余有效的旧代都不受限**。受害者的码一旦不是最新就不受限；受害者的码就是最新时，攻击者手里没有这个账号的码，也用不掉这个额度。单码账号也受上限约束。写明被上限拒绝的响应（429 / 4290，可以和 4018 区分，因为只有持有效码才走到这一步）。补 AC：受害者持非最老、非最新的码，攻击者用满上限，受害者仍成功。 |
| RS7-03 | 严重 | F-ACC-06 规则 4；F-FILE-06 规则 2、7；AC-ACC-06-10、06-12 | ① `PATCH profile` 把 `public_key` 写库，状态还是 `ready`，Copy 到公开桶成功。② 绑定提交前进程崩溃，客户端不再重试（用户退出，或换了别的图）。③ 24 小时后 `ready` → `purging`。规则 7 只写按 `final/{fileId}/` 前缀删除，"同时删除 `public_key`"只写在换头像和注销的句子里。④ 删行后，公开键的唯一记录也没了。AC-ACC-06-12 只测"重试成功"，AC-ACC-06-10 只测没有发过 `PATCH`。 | 公开桶里留下一张用户图片，永久、匿名可读（地址是随机的），也不再有任何记录，注销也删不掉。这正是 RS6-04 乙原来的后果，"先写库"只解决了有记录，还没接到清理路径上。 | F-FILE-06 规则 7 改成：**任何路径进入 `purging` 的文件，`public_key` 不为空就先删公开对象，成功后才能删行**。补 AC：Copy 到公开桶后杀进程，不重试，推进 25 小时运行 `file_purge`，公开桶、私有前缀和 `files` 行都已清除。 |

## 其他问题（不展开）

- 第 21 节第 4、15 行还写着"没有实验""都没实测"，和 MinIO 结果不符；第 4 行的云厂商"冻结前"和 AC-FILE-90-2 的"上线前"矛盾。
- `file_purge` 的条件 `completing_until < now` 照字面写，遇到 NULL 不匹配，从未 `complete` 的 `pending` 会清不掉。要写 `IS NULL OR`。AC-FILE-06-1 能发现。
- 取消也套用"只匹配租约已过期"时，`complete` 进行中的取消会返回成功但实际没有生效，文件靠 24 小时清理兜底。
- `files` 表没有"换头像时间"字段，规则又写头像 `retain_until` 为空，换头像 7 天的计时没有落点。
- 换头像后 7 天内绑回旧文件（F1→F2→F1）没有定义，F1 可能按原计时被删，当前头像失效。
- 公开键复用后，"绑定失败删除自己写的公开对象"可能和并发重试撞键，删掉已绑定的对象，头像变成 404。
- `recover` 专用位的数量和排队时限没有数值，AC-ACC-04-30 的"排队时限"没法判定。
- 多实例下，"同一个码同时只算 1 个"和账号轮转只能按实例生效（第 11.4 节提到集群）。公平性仍有上界，但规格要写明范围。
- 每 IP 每分钟 20 次在办公室 NAT 下，同网的人可以短时压制找回；换移动网络可以绕开。
- AC-ACC-04-29 标了【C1】，但要等 Postgres（B6）才能跑。C1 验收时这条要明确算未执行，不能算通过。
- 合同工具的最小权限比第 11.3 节多了 `tmp/` 的 List，要么工具收紧，要么第 11.3 节补上。

## 没能验证的事情

- 所有序列都没有运行。RS6-01 和 RS7-01 是按 Postgres READ COMMITTED 语义推演的，仓库现在没有 Postgres 实现可以核对。
- 云厂商的 List 按 prefix 授权、列举和删除的一致性、生命周期的实际清除都没有验证。MinIO 结果只代表 MinIO，而且这次按前缀删除只有 1 个键，没有覆盖分页。
- 我没有逐行读合同工具，只看了按前缀删除那段和 `run-local-minio.sh` 里的权限策略（输出被截断）。MinIO 的结果直接采信了 GATE 报告，没有复跑。
- Argon2 耗时和 `recover` 位数没有定值，所以没有算 RS6-02 的公平调度在多少个攻击账号下会超过排队时限。
- 邀请码能限制多少个攻击账号没有评估。
- 没有读 `protocol/` 的 Schema 和 SDK 代码，也没有逐节通读 PRD。"其他事务是否都拿了 `accounts` 锁"只核对了规则 8 和第 4.3 节的文字。
