# PRD-chat v0.4 定向安全复审（账号会话、文件上传）

**编号**：RS4 ｜ **日期**：2026-11-06 ｜ **方式**：只读，走规格流程并核对现有代码。账号和文件功能还没有实现，也没有运行任何服务。

## 结论

**两块都不能冻结。**

**账号会话**有 3 个阻塞项，都要先改：
- **RS4-01**：7 天旧码保护几秒钟就能被绕过。攻击者改密拿到新码，再用新码找回，受害者的旧码随即作废。
- **RS4-02**：规则没有定义"被替换的待确认代"的 access token。按字面实现，攻击者可以一直用账号却不转正，受害者也不会触发重放检测，所以"没有检测盲区"这句话不成立。
- **RS4-03**：改密和"退出其他设备"保留当前 `sid`，新旧链的关系也没有定义。如果偷来的令牌属于当前设备，攻击者不会被清除；响应丢失或和刷新并发时，用户自己可能被误吊销。

冻结前还要处理这些严重项：
- RS4-04：迟到请求造成误吊销，正好违背 RC2-01 的目标。
- RS4-05：只知道 `sid` 就能吊销会话。
- RS4-06：Argon2 计算前后的竞态。
- RS4-07：离线设备看不到 7 天找回提示。
- RS4-08：检测盲区。

**文件上传**：单次 `complete` 和 PUT 的竞态，ETag 方案在逻辑上成立；RC2-07 的主体可以保留。但有 3 个严重项：
- RS4-16：并发或重试的 `complete` 没有定义。
- RS4-17：Copy 会带上上传者设置的元数据，公开头像桶受影响最大。
- RS4-18：合同测试 AC-FILE-90-1 没有覆盖技术验证门要验证的能力。

技术验证门本身也还没过。

## 查过、没发现问题的项目

**账号会话**
- **两个客户端持有同一代并交替刷新**：不会分叉出两条可长期共存的链。一方转正后，另一方再刷新就吊销整条会话（被替换代的问题见 RS4-02）。
- **攻击者转正后受害者上线**：受害者用旧值触发吊销，攻击者的 refresh、access 和在线连接都按 `sid` 失效。前提是受害者还会上线（RS4-08）。
- **响应丢失后单独重试**（5 分钟、3 天）：按 AC-ACC-03-19 不吊销，逻辑成立。
- **刷新和改密、找回、退出、注销交错**：就算刷新晚于吊销提交，返回的 token 也因 `sid` 已吊销而不可用，满足 AC-ACC-04-8。规则里的 SQL 条件没有 `revoked_at IS NULL`，建议加上，但不构成绕过。
- **无 `sid` token**：规则 11 的 `credentials_changed_at`、账号接口拒绝无 `sid` token，逻辑成立（复查点见 RS4-09）。
- **冷静期内找回**（规则 5a）和注销撤销：流程逻辑成立（并发见 RS4-06）。
- **token 不进 URL**：WS 的 token 在第一帧（`gateway.go` 第 247～256 行），新接口用 Bearer 和请求体。admin key 不进浏览器：第 11.6 节都在管理端口，文件走 console-server 代理（只查了规格，没读代码）。
- **IP 判定**：`guard.go` 第 86～110 行从右往左取第一个不可信地址，可以共用。
- **吊销优先于过期**：`gateway.go` 第 267～287 行的顺序正确，`sid` 检查要放在同一位置。
- **原生端跨设备共享 token**：iOS 用 `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`（`SessionStore.swift` 第 52 行），Android `allowBackup=false`（Manifest 第 9 行），不会靠备份复制到另一台设备。
- **老 SDK**：TS 收到 4012 不重连（`connection.ts` 第 280～286 行）。

**文件上传**
- **单次 `complete` 和 PUT 竞态**：`If-Match` 的 Range 和条件 Copy 能挡住 HEAD 之后换对象，失败方向安全（前提是厂商按规范工作，未验证）。
- **`complete` 后再 PUT**：只影响临时键，不影响最终键。
- **MD5 碰撞换内容**：理论上能绕过前 64 KB 嗅探，但嗅探本来就不看后面的内容，防线在响应头，没有新增能力。
- **顺序重复 `complete`**：幂等、只扣一次额度（并发见 RS4-16）。
- **跨用户引用 `fileId`**：`complete`、头像、`send` 都校验 owner，绑定 SQL 带 `owner`。`custom` 里写别人的 `fileId` 不产生绑定，发地址只看 `files.msg_id` 对应消息的访问权。
- **同一 `fileId` 绑定两条消息**：`state='ready'` 条件更新只有一个成功，和 `purging` 也互斥。
- **撤回、删除、退群、`minSeq`**：立即不再发新地址，响应和"不存在"相同。残留风险已如实写在规则 4、R-6（补充见 RS4-24）。
- **预签名范围**：SigV4 把 `response-*` 参数和方法、键都纳入签名，客户端改不了（规范知识，未实测）。
- **多格式文件（前面是合法 PNG、后面是 HTML）**：固定 `image/*`，`nosniff` 作为优先项可以接受（浏览器行为凭知识，未实测）。
- **嗅探链**：缩略图走同一流程（AC-FILE-01-13）；真实类型取服务端值，不用声明值。

## 没能验证的事情

- **对象存储行为全部没有实测**：条件 Copy、`If-Match` Range、加密下的 ETag、未签名头的处理、Copy 默认保留元数据、Content-Length 强制、生命周期取整、TTL 只约束开始、`response-*`。这些都是凭规范或记忆，厂商未定。MinIO 也没跑（开发机不装，CI 被 P-21 卡住）。
- **浏览器行为**：冻结页面的 `BroadcastChannel`、`sessionStorage` 的恢复和落盘、Web Locks 兼容性。
- **网络**：迟到重复请求的真实频率；OkHttp、URLSession、网关的隐式重试。RS4-04 的序列逻辑上成立，频率未知。
- **性能**：Argon2 实际耗时、窗口大小、压制闸门需要多少 IP。
- **`IS NOT DISTINCT FROM`**：`modernc.org/sqlite` v1.61.1 打包的 SQLite 版本没有确认，不确定是否支持。
- **代码范围**：账号和文件功能都还没实现，以上是规格推演。Kotlin、Swift SDK 的踢线路径没有读（搜索命令失败，只读了 TS），`tianting-console-server` 的文件代理只看了规格。
- **没有逐条审**：F-APN 的令牌规则只看了不变量；F-ACC-06、F-ACC-10 只看了和头像相关的部分；第 16 节没看。
- **之前的评审**：RECHECK 只细读了 RC2-01～09，REVIEW 只细读了 R-CS-05～11，其余只看了标题或第 24 节的处理记录。没有复核其他已处理条目是否正确。
- **文中的 2 分钟、5～15 分钟、1024 像素等建议值都未校准。**
