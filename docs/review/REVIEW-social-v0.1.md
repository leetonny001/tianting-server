（一条问题可能涉及多个视角，按主视角计数。）

整体评价：这份 PRD 的骨架是对的，而且比前三份草稿更"落地"：核实了单租户现状、`group_members` 缺 `user_id` 索引、`memberCache` 只在 admin 包失效等代码事实（均已复核属实）；关系同步沿用"版本号 + 增量拉取、事件只是提醒"的思路，与 ARCH 2.2 约束 4 一致；大部分 AC 带了具体输入和错误码，抽查 59 条中 32 条可以直接写成用例。主要问题有四类：

1. **关系版本号的语义自相矛盾，增量同步按现在的写法会丢数据**：规则说"每个变化的行都写新 ver"，AC 又按"每个操作加 1"来断言；分页按 `ver > sinceVer LIMIT 1000` 时，同一个 ver 的多行会被切开；续拉用哪个 ver、全量是否分页都没定义。
2. **防枚举的结论不成立**：新会话限流排在 4042 之后，发消息仍可以每秒 20 次探测账号；拉黑接口对不存在的用户返回 4042，且没有每日配额；"好友申请 + `users` 可见范围"可以绕过"不可被搜索"。PRD 成功标准里"三条路径都无法批量确认账号是否存在"不成立。
3. **悄悄改了已冻结的需求**：业务方加人生成提示消息，改变了 AC-GRP-01-6 / 7 / 12（未读数、maxSeq）；"最后一人退群自动解散"与 AC-GRP-02-3（允许空群）冲突；默认陌生人限额 3 条、无法关闭的新会话限流，改变了 F-MSG-01 和 S-1"开放模式任何人都能私聊"的含义，也会打断 TC-PERF。0 节"默认 `open` 保证 PRD-core 现有 AC 和 e2e 不变"的说法不对。
4. **并发正确性只在 SQLite 下成立**：现在 SQLite 是单连接（`sqlite.go` 第 50 行 `SetMaxOpenConns(1)`），所有事务天然串行；PRD 声称可迁移到 Postgres、可按用户分片，但没有定义任何加锁规则，分片方案和"好友上限原子""互相申请自动通过"互相矛盾，契约测试在 SQLite 上也测不出问题。

**结论：修改后提交拍板**（见第 6 节）。

### 8.1 阻塞项结论

| 编号 | 结论 | 依据 |

| R-SOC-01 关系版本号 | **已关闭** | 采用"每操作一个 ver、同操作同 ver"（与原推荐不同但自洽），并用 `(ver, 类型, 对方 userId, 方向)` 严格大于的游标分页（F-SOC-06 规则 1～3）。逐条推演的反例都不丢不重：① 同一 ver 3 行、`limit=2`：游标在 ver 内部续接，AC-SOC-06-4 覆盖。② 同步中途有新操作：被改的行 ver 只会变大且 > `untilVer`，在排序键上只会"往后挪出本轮"，不会挪到游标之前，所以已返回的旧值由下一轮（从 `untilVer` 开始）覆盖、未返回的不会重复；`latestVer` 与 `untilVer` 拆开，轮末触发下一轮（AC-SOC-06-6）。③ 清理与同步交错：增量轮后续页发现 `purgedVer > sinceVer` 即 `restart`，重来时按第一页规则判为全量（AC-SOC-06-8）；全量轮不返回墓碑、申请按 30 天过滤，清理不影响其结果。④ 多端同时操作：ver 在持有用户锁的事务内分配（L1），锁持有到提交，提交顺序 = ver 顺序，READ COMMITTED 下读到 V 时 ≤ V 的行都已可见；发起端靠 ack（`ver = 本地+1` 才直接推进，否则补一轮）。AC 与 5.4 节表格一致：AC-SOC-03-7（+1）、06-1（3 个 ver / 4 项）、06-9（10 个 ver × 2 项）、06-11、02-3、04-4 逐一核对无矛盾；9.1 节 ack 字段与规则 7 一致；申请清理推进 `purgedVer`（原问题 ⑥）。残留只有建议 S-1 |

### 8.3 建议（不影响冻结）

| S-1 | F-SOC-06 规则 8；10.2 节 | 轮末"再起一轮"的条件补上"本轮期间自己修改的 ack 的 `ver > untilVer`"。现在的规则在同一连接串行处理帧时（`gateway.go` 现状）是对的——自己的修改若早于最后一页，最后一页的 `latestVer` 会反映出来；但这是隐含前提，原生 SDK 多线程处理应答时可能失效。全量轮期间收到的 ack 被整体替换覆盖后，也要靠这一条找回 |
