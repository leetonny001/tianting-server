## 一、发现的问题

### 阻塞

**RC-01 阻塞｜L1 过关标准按字面过不了**
- 位置：3.2 节 L362、L371～377；AC-PUSH-03-16（L904）；AC-PUSH-08-7（L979）；AC-PUSH-11-5（L1015）；F-PUSH-11 规则 2（L1008）；AC-PUSH-06-6（L947）；AC-PUSH-04-2（L921）
- 问题：L1 要求"归属 L1 的 AC 全部通过"，交付物是 im-server、sdk-ts、H5。下面这些在 L1 交付物上验不了：
  - AC-03-16 标"原生"，但 F-PUSH-03 整组归 L1，没有例外。
  - AC-08-7 只针对原生。归属表写"L1（sdk-ts）"，sdk-ts 没有持久化，这条在 L1 是空的。
  - AC-11-5 和 F-PUSH-11 规则 2 要求跑 Postgres，但 im-server 只有 SQLite：`store/migrations/` 下只有 `sqlite`，`go.mod` 没有 pgx 或 pq，`store.go:1` 写"后续可换 Postgres"。
  - AC-06-6 要 console-server（CS-044），而 3.2 节说 ADM 系列不作为前提，L1 交付物也不含 console。
  - AC-04-2 同时标开发机和目标机，8.1 节说发布结论要目标机（P-12 未解决），L1 过关到底看哪个没写。
- 复现：L1 收尾时对照归属表逐条勾选，上述 AC 都勾不上。
- 建议：
  - 归属表补行：AC-03-16、08-7 归 L3。
  - AC-06-6 归"随 CS-044"，不计入 L1 门槛。
  - AC-11-5 和规则 2 改为"im-server 有 Postgres 实现后再跑"，L1 只跑 SQLite，并补充 SQLite 下如何断言加锁顺序（`sqlite_social.go:38` 已有类似断言）。
  - AC-04-2 写明 L1 只要开发机结果，目标机结果归发布门槛。
- 这说明 R-LQ-02 只改了一半。

### 严重

**RC-02 严重｜C8 备份恢复后会静默丢推送，且和 C7 冲突**
- 位置：C7（L454）、C8（L455）、AC-PUSH-03-10（L898）
- 问题：
  - C8 把游标重置为 `latestSeq`，但恢复之后新写入的推送序号都不大于这个值。`afterSeq=旧游标` 又查不到它们，所以这些推送永远补不到。
  - C7 写 `max(游标, latestSeq)`，字面上游标仍是 100，和 C8 冲突，文档没写优先级。
- 复现：
  1. 客户端游标 100，服务端恢复到 50，恢复后又推了 51～55，都是新 `pushId`。
  2. 客户端连上，`pushSync {afterSeq:100}` 返回空，`latestSeq=55`。
  3. 按 C8 游标变 55，51～55 永远收不到。
- 建议：
  - C8 改为 `latestSeq < afterSeq` 时重新 `pushSync {afterSeq:0}`，靠 `pushId` 去重（LRU 2000 大于收件箱 1000，够用）。
  - 写明 C8 优先于 C7，同步改 AC-03-10。
  - 恢复后序号已长过旧游标（如恢复到 50 后长到 110，旧游标 100）时客户端无法察觉。要么写进 4.6 节作为已接受风险，要么在 ack 带一个恢复纪元（epoch）。

**RC-03 严重｜"分页游标"和"交付游标"混成一个，无订阅者时规则走不通**
- 位置：C6（L453）、C7（L454）、4.8 节 L523～525、AC-PUSH-08-5（L977）
- 问题：
  - C6 要求游标等于本页最大 `pushSeq` 并继续拉。4.8 要求交付给订阅者之后才前进。没有订阅者时两者矛盾。
  - C7 的"交付后游标 = max(游标, latestSeq)"还会越过暂存溢出丢掉的条目。
  - `pushId` 何时记为"见过"也没写。如果收到就记，丢掉的条目补拉回来会被当成重复丢弃，AC-08-5 过不了。
- 复现：App 不订阅 `pushes`，或订阅得晚（`App.kt:71` 启动、`MainActivity.kt:208` 才接），收件箱有 1000 条。
  - 用交付游标翻页：`afterSeq` 不变，反复拉同一页，直到撞上 30 次/分钟的 4290。
  - 用分页游标翻页：拉完 1000 条，丢 500 条。之后走到 `hasMore=false`，C7 把游标推到 `latestSeq`，丢的 500 条再也补不回。
- 建议：
  - 明确两个变量：内存里的 `fetchAfter` 只管翻页，持久化的 `cursor` 只在连续交付后前进，并且有未交付或已丢弃条目时不越过它。
  - 暂存满或无订阅者时停止翻页。
  - `pushId` 在交付时才记入"见过"。
  - 这些都写进 `push-sync.json`。

**RC-04 严重｜`T0` 和去重集合按"SDK 实例"定义，同实例换号时错误**
- 位置：4.5 节规则 4（L486）、4.4 节 SDK 去重（L468）、AC-PUSH-07-3（L962）
- 问题：三套 SDK 都支持同一实例换号：`client.ts:409`、`IMClient.kt:845-849`、`Client.swift:466` 都有"换了账号"分支，`disconnect()` 之后实例可继续用。4.9 只给游标按 userId 分键，没有覆盖下面三项：
  - `T0`：u2 使用的还是 u1 登录时的 `T0`。
  - 内存去重集合：按实例去重，sdk-ts 尤其没有分键。
  - 暂存帧：u1 的暂存帧可能交给 u2。
- 复现：
  1. u1 在实例上登录（`T0`=第 1 天）。第 3 天退出，u2 在同一实例登录。
  2. u2 离线期间的第 2 天推送满足 `ts ≥ T0`，得到 `replayed=false`。按 L-4 会弹横幅、计未查看，一次连接最多 1000 条。
  3. 批量推送 p1 同时发给 u1、u2 时，u2 的 p1 被当作重复丢弃，业务收不到。
- 说明：H5 不受影响，`ImProvider.tsx:60,68-69` 每次登录都新建实例，退出时销毁。问题出在 SDK 契约，以及长驻单例的接入方。
- 建议：
  - `T0` 改为"本实例上该 userId 第一次 auth 成功"，账号变化时重置。
  - 去重集合和暂存帧按 userId 隔离，退出时清除。
  - 扩展 AC-07-3，断言 `replayed` 和同 `pushId` 的跨账号交付。

**RC-07 严重｜5040 重放路径落不了地，AC-PUSH-06-6 本身不成立**
- 位置：4.7 节 L515、L1223、AC-PUSH-06-6（L947）、8.2 节 L1148、`tianting-console-server/internal/imclient/client.go:103-110`、CS-014（`console.md:268`）
- 问题：
  - **注入手段不对**：`imLatencyMs` 在发请求之前等待，等到超时就直接返回 `ErrResultUnknown`，请求根本没发到 im-server。所以"调用超时 5040，实际已投递"用这个工具造不出来，重放得到的是 `created=true`，不是 AC 预期的 `false`。
  - **结论对不上**：CS-014 只有两种对账结论：im-server 有结论就补写，im-server 也没有就是 `notExecuted`。没有"未确认投递"。im-server 只有 intent 没有 result 的情况（`audit.go` 先写 intent 后写 result）正好是 `pending` 崩溃，CS-014 没有定义如何处理。
  - **前提矛盾**：AC 写"实际已投递"又写"结论未确认"。正常投递后 result=200，按 4.7 不该重放。
  - **没写谁来重放**：没写是对账任务自动重放还是运营手动，全员推送是否要再次双人复核，超过幂等保留的 8 天怎么办。
- 复现：按 8.2 节设置 `imLatencyMs=15000`（默认超时 10 秒）调用，im-server 收不到任何请求。
- 建议：
  - 写一张对照表：result=2xx 不重放；只有 intent（含 `pending`）或 `notExecuted` 用同号重放。
  - 明确重放发起方，全员重放不重走复核，并写明过期处理。
  - AC 改成两条，并新增一个"im-server 处理完后断开响应"的注入手段。可以复用 `client.go` 对连接中断返回 `ErrResultUnknown` 的现有路径。

### 一般

**RC-09 一般｜4.8 接口形态和现有 SDK、AC 有冲突**
- 位置：L522～525、AC-PUSH-08-5
- 问题：
  - Kotlin 写"`emit` 挂起等到有订阅者"，和同一节"暂存 500、溢出丢最旧"直接矛盾。AC-08-5 要丢最旧。
  - `IMClient.onFrame` 是同步函数（`IMClient.kt:240`、`:942`），挂起发送需要一条独立的交付协程，否则顺序或读帧都有问题。
  - Swift 的 `on` 只有接收全部事件的一种形式（`Client.swift:215`），没有 `on(.push)`。任何已有监听器都会被算作"有订阅者"，导致不暂存、游标照常前进。
  - `pushStart` 没有写进签名。
- 复现：Kotlin 无订阅者时到达 501 条，两条规则结果不同。Swift App 只有一个界面状态监听器时，推送被"交付"且游标前进，但业务根本没处理。
- 建议：定稿前把三端签名写全。Kotlin 改为有界队列 + 单独协程。Swift 增加专用订阅入口。

**RC-10 一般｜C5、C6、C7、C9 的边界留白**

  - C7 没写暂存帧怎么处理。
  - 没写连接断开时进行中的 `pushSync` 算失败、退避要清零。
- 复现：
  1. 游标 41，暂存 200，页范围 42～91。按字面 200 先于 92 交付。
  2. 读快照 `latestSeq=43` 后 44 提交，44 的帧先于 ack 到达，C7 没说 44 怎么交付。
  3. 退避 30 秒等待期间连接重连，C9 和"每次连接成功调一次"冲突。
- 建议：
  - C6 只合并 `pushSeq ≤ 本页最大值` 的帧。
  - 所有分支结束后重新按 C1、C2 评估暂存。
  - 断开时清掉单飞和退避状态。

**RC-11 一般｜`target=room` 在 L1 的 AC 和错误优先级矛盾**
- 位置：AC-PUSH-02-8（L877）、F-PUSH-02 规则 7（L867）、第 10 节 L1188、`adminauth/scope.go`
- 问题：`push.room` 排在 L2，未知 scope 的配置启动时被拒。规则 7 先查 scope，所以 L1 里 `target=room` 得到的是 403 / 4030，不是 AC 要求的 400 / 4000。

**RC-12 一般｜重新广播时 `ts` 未定义**
- 位置：4.2 节 L405、4.4 节 L477、4.5 节规则 4
- 问题：`pending` 重播可能发生在 5～15 分钟之后（CS-014 的对账节奏），最晚 8 天。`ts` 用原受理时间还是重播时间没写，直接决定 `replayed`。
- 复现：全员推送崩溃，15 分钟后重放。按原 `ts`，这 15 分钟内新启动的实例得到 `replayed=true`，不弹横幅。
- 建议：明确用哪一个，并在 AC-06-7 断言。8 天窗口内重播旧广播是否允许，也一起定。

**RC-13 一般｜幂等保留依赖清理顺序，同号再用会被 SDK 吞掉**
- 位置：L479、AC-PUSH-06-12（L953）
- 问题：
  - 收件箱读取靠过滤、物理删除靠任务。清理落后或被关闭时，幂等记录已删而收件箱行还在，同号提交撞唯一键，变成 5000。
  - 就算写入成功返回 `created=true`，设备持久化的 2000 个 `pushId` 也可能把它当重复丢弃。
- 复现：`push_purge` 关闭 9 天，只清了幂等表，再用同号提交。
- 建议：幂等清理以"无对应收件箱行"为条件。文档写明 `pushId` 过期后也不应复用。

**RC-14 一般｜限速和 AC、分页数字对不上**
