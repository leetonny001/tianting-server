# PRD-chat v0.6 定向安全复审（编号 RS6）

评审方式：只读，走规格序列。只读了 RS5 的 01～06 和 PRD 的相关规则，没有读全文，没有运行服务，也没有读密钥文件。账号和文件功能还没实现，下面的序列都是规格推演，不是实测。

## 结论

**账号会话和文件上传现在都不能冻结，但差距不大。没有阻塞项，有 5 个严重项，每项改一两句规则加 1 条 AC 就能解决。**

RS5-01～06 的原序列按新规则走，大多已经断了。RS5-01、03、04、05 的设计成立，RS5-01 还要写明限流的位置（RS6-05）。没有关闭的是两项：
- **RS5-02**：甲、乙已关闭，丙换了个形式还在（RS6-02）。这个修法还去掉了原来串行化 `recover` 提交的条件（RS6-01）。
- **RS5-06**：按前缀删除需要 List，而 PRD 写明的权限不给 List（RS6-03）。头像路径也不受"残留不超过保留期"这个上限约束（RS6-04）。

## 逐项状态

| 编号 | 是否关闭 | 理由 |
|---|---|---|
| RS5-01 | 关闭（有前提） | T0 攻击者转正 gen2，`overlapMinGen`=1，受害者用 R1 得到 `superseded`。T0+1:50 转正 gen3，`overlapMinGen`=2，R1 的 gen1 低于它，立即 `replayDetected`。受害者持有更新的废弃 pending（如 gen2，攻击者转正 gen3）时，第二次转正同样让它低于下限。`overlapUntil` 只能靠转正延长，转正必然抬高下限，所以窗口续不了。前提见 RS6-05。 |
| RS5-02 | 部分 | 甲（版本活锁）关闭，`recover` 不看版本。乙（单哈希）关闭，命中的请求不受限制。丙（专用位被占）只对改密位关闭，`recover` 位本身可以被占，见 RS6-02。修法的副作用见 RS6-01。 |
| RS5-03 | 关闭 | 甲、乙、丙、丁、戊走一遍：日期按账号状态算，和吊销原因、操作顺序都无关；`kicked` 已加字段；第 5 天再改密仍显示第 7 天。遗留的是一般级问题，见文末。 |
| RS5-04 | 关闭 | 甲：独立密钥、带 `kid`、365 天退役，正确（access 和 refresh 到期都受绝对上限约束）。乙：恢复码改用 SHA-256 后没有密钥生命周期，128 位随机码离线猜不动。配置检查的落地细节见文末。 |
| RS5-05 | 关闭 | R1→A2、A3（gen2、gen3），受害者转正 gen2，下一代是 gen4。A3 不等于 `current`，也不在 `pending`，一直被拒绝。 |
| RS5-06 | **未关闭** | 键结构和 AC-FILE-01-26 的逻辑成立，孤儿确实能按文件定位。但写明的权限下执行不了（RS6-03），头像路径也没有覆盖（RS6-04）。 |

## 新问题

| 编号 | 严重度 | 位置 | 序列 | 后果 | 建议改法 |
|---|---|---|---|---|---|
| RS6-01 | 严重（只在 Postgres 下可达） | F-ACC-04 规则 8；F-ACC-05 规则 5；AC-ACC-04-19 | 规则写的顺序是：先条件更新恢复码行，"然后递增版本"。按 Postgres 默认的 READ COMMITTED：① 受害者 `recover{C1}` 的事务更新 C1 为已用，作废比 C1 新的代（语句快照里还没有 Cx）。② 这时 `accounts` 行还没被锁、版本没变，攻击者在途的改密提交成功：条件写通过，插入新一代 Cx，返回给攻击者。③ `recover` 继续，改密码、递增版本（不带条件），吊销会话，生成 C4，提交。④ Cx 没有被作废。之后攻击者 `recover{Cx}`：C4 作废，C1 已用完。两个不同代的码并发 `recover` 也有同样的交错，新生成的码可能留下来。攻击者本来就可以脚本循环改密（RS5-02 甲），能反复撞这个窗口。 | 受害者用恢复码找回后，攻击者仍持有有效的码，可以再抢回账号，受害者手里已没有可用的码，账号永久丢失。这违反 AC-ACC-04-19 的"攻击者没有拿到恢复码"和第 12.2 节的"找回优先"。现有 AC 的钩子停在 Argon2 之后，抓不到提交内部的交错。现在的 SQLite 用 `SetMaxOpenConns(1)`（`store/sqlite.go` 第 51 行），事务是串行的，所以不可达，测试也会全过。 | 写明 `recover` 提交事务的**第一条语句**先锁 `accounts` 行（`SELECT … FOR UPDATE` 或先递增版本，且不带版本条件），然后才检查恢复码、作废新代。所有写恢复码的事务都按"`accounts` → `recovery_codes`"的顺序加锁，并加进第 4.3 节的加锁顺序。补 Postgres 契约测试：钩子停在 `recover` 改完恢复码行之后，放行改密，预期改密 401。 |
| RS6-02 | 严重 | F-ACC-05 规则 2；F-ACC-01 异常；AC-ACC-04-24 | 任何持有自己账号恢复码的人（注册就有，或者攻击者已改密拿到受害者账号的 Cn）：① 并发发 N 个 `recover{自己的码}`，提交前都算"命中"，不受锁定和单哈希限制，全部排进 `recover` 专用位。② 其中一个提交，响应带新码。③ 用新码再来一轮。受害者的 `recover{C1}` 排队超时，得到 503 / 5030。持续到第 7 天。规则写了命中免"用户名 + IP"锁定和单哈希限制。每 IP 限流只在 F-ACC-02 写给登录，是否覆盖 `recover` 命中没写；就算覆盖，换 IP 也能绕过。 | RS5-02 丙换了个位置：专用位是全局资源，占用它只需要一个有效码，不需要任何额外权限。受害者手里的旧码有效却算不了哈希，第 7 天后账号永久丢失。攻击需要持续 7 天，日志里看得出来，所以定严重，不定阻塞。AC-ACC-04-24 只测了占改密位。 | 专用位按 `(userId, gen)` 公平调度：同一个码同时只算 1 个，队列按账号轮转，**同账号里代号更老的码优先**。不能只按 `userId` 单飞，否则攻击者用 Cn 就能压住受害者的 C1。进入位之前重查一次码是否还可用，同一个码的并发请求不再白算。对每账号的 `recover` 成功次数设上限，但账号里最老的有效码不受这个上限限制。补 AC：循环 `recover` 自己的码占位，同时其他账号和同账号的旧码找回都能在排队时限内成功。 |
| RS6-03 | 严重 | F-FILE-01 规则 3、9；F-FILE-06 规则 7；第 11.3 节；AC-FILE-01-26 | S3 风格的接口没有"按前缀删除"，必须先 List 再逐个删。第 11.3 节写"List（只用于孤儿对账）"，服务端凭证只列了最终前缀"读、写、删"。按这个配置：① 第 180 天，`file_purge` 把文件改成 `purging`，List 得到 403。② 规则是"删除失败保留 `purging` 下次重试"，这个文件永远卡住。③ 实现者如果改成只删记录里的键，List 问题就绕过去了，崩溃残留的键也重新变成永久孤儿。AC-FILE-01-26 用的假 S3 不一定校验权限，测试可能全过。 | 二选一：要么所有到期文件都删不掉，每批都报错，"留 180 天"不成立；要么 RS5-06 的原问题原样回来。 | 第 11.3 节改成：服务端凭证带最终前缀的 List（按 prefix 条件授权），`file_purge` 和提交后清理都用；全桶 List 仍只给对账任务。规则 9 和第 21 节的"禁止列举"明确是**匿名和预签名禁止**。AC-FILE-90-1 用真实权限的凭证跑一遍前缀删除。如果不想给 List，就改用 RS5 建议的方案 ②（尝试记录表）。 |
| RS6-04 | 严重 | F-ACC-06 规则 4、5；F-FILE-06 规则 2、7；F-ACC-08 规则 3、5；AC-ACC-06-8、08-7 | **甲**：u1 绑定头像，文件 `attached`，`retain_until` 为空。换头像 8 天后或注销清理时，规则只写"按 `public_key` 删除"。私有的 `final/{fileId}/` 和 `files` 行进不了任何到 `purging` 的路径（状态机里 `attached` 只能走撤回或过期），`file_purge` 永远不处理它。**乙**：`PATCH profile` Copy 到公开桶后、提交 `public_key` 前进程崩溃。公开键是随机的，没有记录，也不在 `final/{fileId}/` 前缀下，重试又生成一个新键。 | 甲：已注销用户的头像原图永久留在私有最终键，同一路径下的崩溃残留也永远清不掉，RS5-06 写的"残留不会超过文件的保留期"对头像不成立，也违反 F-ACC-08 "头像删除"的说明。乙：公开桶里有永久孤儿，没人知道地址，但注销也删不掉。 | 换头像 7 天后和注销清理时，把头像文件改成 `purging`，走同一条清理路径，同时删 `public_key` 和 `final/{fileId}/`。公开键改成由 `fileId` 确定，或者**先把 `public_key` 写进数据库再 Copy**，重试复用同一个键。AC-ACC-06-8、08-7 增加检查：私有前缀和 `files` 行都已清除。补 AC：Copy 到公开桶后杀进程，重试后公开桶只有 1 个对象。 |
| RS6-05 | 严重（规格没写死，取决于实现顺序） | F-ACC-03 规则 4（判定顺序、限流）；AC-ACC-03-38、03-45 | 判定顺序 ①～⑤ 里没有"每小时 20 次"的位置。如果实现成进入处理就先查限流：① 攻击者转正。② 用自己的 `current` 刷新，几秒内把这条会话的 20 次用完（access 有效 24 小时，他不急着用新值）。③ 受害者用 R1 刷新得到 4290，到不了代号判定，SDK 按规则 6 留在当前页面退避。④ 每小时重复一次。 | RS5-01 的结果等于回来了：受害者触发不了 `replayDetected`，攻击者一直不被吊销。`securityNotice` 要连续 6 小时才发，而且只发给其他在线设备，单设备受害者什么也收不到。现有 AC 在两种顺序下都能通过。 | 在判定顺序里写明：**⑥ 限流只在将要签发 token 的分支检查**，`mac` 错误、已吊销、已过期、`superseded`、`replayDetected` 都不受它影响。补 AC：会话已用满 20 次时，用旧值刷新立即得到 `replayDetected` 并吊销。 |

## 一般和建议（不展开）

- `recoverBefore` 取"最早"：受害者持有的码比账号里最老的旧码新时，显示的日期偏早。规则 6a 写的是"未过期"，要明确排除已用和已作废的码，否则找回成功后还会提示截止日期。
- 配置检查发现不了已被删掉的密钥，需要持久化的密钥台账（`kid`、`retiredAt`）；另外要写清密钥泄露时的应急绕过。
- 恢复码的规范化规则（大小写、分隔符）和 `SHA-256(userId, code)` 的拼接方式没写。
- `recover` 命中才免限，所以已被锁定的未命中请求也要先查一次库，要有不依赖命中结果的总量限流。
- `file_purge` 没有避开进行中的 `complete`。卡住的尝试在清理后才 Copy，又恰好崩溃时，会留下无记录的孤儿（要连续两次故障）。
- F-FILE-06 规则 8 提到"版本"：桶如果开了版本控制，删除只写删除标记，需要写明要清除旧版本。
- 改密后在保存页杀 App，磁盘上留的是已吊销的旧 token，重启时用户会看到"如果不是你本人操作"的提示。

## 没能验证的事情

- 所有序列都没有运行。RS6-01 是按 Postgres READ COMMITTED 的语义推演的，仓库现在只有 SQLite（`server/go.mod`），没有 Postgres 实现可以核对。如果实现时用了别的语句顺序或隔离级别，结果会不同。
- 云厂商的 List 授权是否支持按 prefix 条件、删除和列举的一致性都没核实，属于还没跑的技术验证门。S3 没有按前缀删除的接口是凭记忆，没有查文档。
- Argon2 实际耗时和 `recover` 位的数量、排队时限都没有定值，所以 RS6-02 需要的请求量没有算过。
- 没有读 `protocol/` 的 Schema，也没有读 SDK 代码，`recoverBefore` 只核对了第 11.1 节的文字。
- PRD 其他章节里是否有 `recover` 的 IP 限流，我只用关键词搜过，没有逐节读。
