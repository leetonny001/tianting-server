# 架构与安全设计 v1（可扩展、可迁移、安全优先）

- 状态：**已确认**（2026-11-02，A1～A4 按建议通过）；B2.5 已实现，实现中的调整见第 7 节
- 来源：用户要求（2026-11-02）——"后端架构要方便后期扩展分布式部署，数据库要方便后期迁移、备份、扩展；聊天软件应该把安全放第一位"
- 范围：服务端。客户端受影响的只有第 3.2 节 S1（WS 鉴权方式），需要同步修改协议和 PRD。

原则：**一期仍是单进程单文件部署（演示简单），但凡是"以后换成分布式要推倒重来"的地方，现在就隔一层接口、定好约束。**
安全项分两档：上线前必须完成（P0），和集群化 / 正式运营阶段完成（P1）。

## 1. 现状盘点（B2 完成时）

### 1.1 已经做对的

| 项 | 现状 |
|---|---|
| 存储隔离 | 业务代码只依赖 `store.Store` 接口，没有直接写 SQL |
| 分片友好的数据模型 | 消息、seq、sync 查询全部以 `conv_id` 为键；msgId 用 UUIDv7，全局唯一不依赖节点 |
| 无状态鉴权 | JWT 校验不查库；强制下线用令牌版本号（每次连接查一次库），多节点下仍然正确 |
| 时间可注入 | 所有时间走 `clock.Clock`，便于测试和以后的跨节点时钟问题排查 |
| 基础防护 | JWT 固定 HS256（防 alg 混淆）；管理密钥常量时间比较；单帧 64KB、管理接口请求体 1MB 上限；`ReadHeaderTimeout`；日志不打印 token 和消息内容；单用户发送限流 |

### 1.2 差距

| # | 问题 | 影响 |
|---|---|---|
| G1 | 在线表 `hub` 在进程内，`logic` 直接调用它投递 | 多节点时，A 节点上的用户收不到 B 节点发出的消息；强制下线踢不到其他节点 |
| G2 | 限流器在进程内 | 多节点时同一用户的配额会乘以节点数 |
| G3 | 建表语句写死在代码里（`CREATE TABLE IF NOT EXISTS`） | 没有版本号，加字段、改索引无法有序升级，也无法回滚 |
| G4 | 只有 SQLite 实现，SQL 里有 `?` 占位符等方言 | 换 Postgres 需要重写；没有统一的契约测试来证明新实现行为一致 |
| G5 | 没有备份和恢复手段 | 磁盘损坏 = 全部聊天记录丢失 |
| G6 | 去重索引 `(from_uid, client_msg_id)` 跨会话 | 按 `conv_id` 分片后，这个唯一约束会跨分片（见 2.3） |
| G7 | token 放在 WS URL 的 query 里 | URL 会被反向代理、CDN、浏览器历史记录下来，**token 泄露的头号途径** |
| G8 | 不校验 Origin；没有配置密钥时自动用开发密钥 | 跨站 WebSocket 劫持；生产误配置时静默使用公开的开发密钥 |
| G9 | 管理接口只有一把静态密钥，没有防重放、没有审计 | 密钥泄露后可以冒充任何用户签发 token，事后无法追查 |
| G10 | 没有连接数限制、按 IP 的握手限流 | 单个客户端可以耗尽服务端连接和内存 |
| G11 | 依赖没有漏洞扫描 | 供应链风险 |
| G12 | （2026-11-03 PRD-social 复审 N-03）社交关系的分片方案：好友关系的权威记录不含拉黑状态，拉黑与对方申请并发时可能在拉黑后写出待处理申请；ack 要同步返回新 ver，而分片方案里副本的 ver 异步分配 | 分片（M3 / M4 / B6 之外）之前要重新设计 |

即将开始的 B3 的"群成员内存缓存"（BE-033），如果按单机写，集群化时一定会读到其他节点改过的过期数据。**所以这次调整要排在 B3 之前。**

## 2. 可扩展：从单进程到分布式

### 2.1 目标形态

```
             ┌─────────── 负载均衡（TLS 终止，WS 无需会话保持）───────────┐
             ▼                       ▼                        ▼
       im-server 节点 1        im-server 节点 2   …     im-server 节点 N    ← 无状态，可水平扩容
       gateway + logic         gateway + logic          gateway + logic
             │  ▲                    │  ▲                     │  ▲
             │  └──── 消息总线 Bus（NATS）：按用户投递、踢线、缓存失效 ────┘
             │
             ├── 在线路由 Presence（Redis）：userId → 所在节点
             ├── 限流 Limiter（Redis 令牌桶）
             └── 数据库（Postgres 主从 + 连接池；消息表按 conv_id 分区 / 分片）
```

一期全部用**进程内实现**跑在一个二进制里；接口定好后，集群化只需要新增实现、改配置，`logic` 一行不改。

### 2.2 要抽象的接口（本次就做，只提供本地实现）

| 接口 | 职责 | 一期实现 | 集群实现 |
|---|---|---|---|
| `delivery.Router` | `DeliverToUser(uid, frame, exceptConn)`、`KickUser(uid, reason)` | 直接调本机 `hub` | 查 Presence 得到用户所在节点，经 NATS 发给对应节点，节点再调本机 `hub`；或每个用户一个 subject，节点订阅本机在线用户 |
| `delivery.Presence` | 连接上线 / 下线登记、查询用户在哪些节点 | 本机 `hub` 自身 | Redis（带 TTL 心跳续期，节点宕机自动过期） |
| `ratelimit.Limiter` | `Allow(key)` | 现有内存令牌桶 | Redis + Lua 原子令牌桶 |
| `cache.Invalidator` | 群成员等缓存的变更广播 | 直接删除本机缓存 | 经 NATS 广播失效事件，所有节点删除 |
| `store.Store` | 持久化 | SQLite | Postgres（见第 3 节） |

约束（写进代码规范）：
1. `logic` 不允许 import `hub`，只能依赖 `delivery.Router`。
2. **任何进程内缓存都必须通过 `cache.Invalidator` 失效**，并且有 TTL 兜底（例如 60 秒），宁可多查一次库，也不能长期读到旧数据。
3. 节点之间不共享内存状态；每条连接的状态只在它所在的节点上。
4. 正确性不依赖总线：总线丢了一条投递，客户端靠 seq 断档 + `sync` 补齐（现有机制）。总线只影响实时性，不影响"不丢不重"。

### 2.3 seq 分配与去重在集群下的做法

- **seq**：继续在数据库事务里分配（Postgres 对 `conv_seq` 行加锁）。同一会话的写入天然串行，不同会话可以并行。单个会话的写入速度上限远高于聊天场景的需要。只有聊天室需要更高吞吐，而聊天室消息不持久化，不走这条路径。
- **去重（G6）**：现在的唯一约束 `(from_uid, client_msg_id)` 是按发送者建的，要求跨会话检测冲突（4008）。分片时拆成单独一张表 `client_msg_dedup(from_uid, client_msg_id → conv_id, msg_id, seq, ts)`，**按 `from_uid` 分片**；消息表按 `conv_id` 分片。两次写入通过"先写去重表占位，再写消息"保证幂等。一期仍然是单库，先不拆，但 Store 接口的语义不变，拆的时候上层无感。

### 2.4 部署与运维约束（现在就遵守）

- 配置只通过环境变量和文件传入，节点本身不写任何本地状态（SQLite 文件除外，那是单机模式）。
- `/healthz`（存活）和 `/readyz`（数据库可用、总线已连接才算就绪）分开，供负载均衡和 K8s 使用。
- 优雅退出：收到 SIGTERM 后先从负载均衡摘除，再给在线连接下发 `kicked`（原因 `serverShutdown`），客户端退避后自动连到其他节点。

## 3. 数据库：可迁移、可备份、可扩展

### 3.1 版本化迁移（替换 G3）

- `server/internal/store/migrations/{sqlite,postgres}/0001_init.sql`、`0002_xxx.sql`……用 `embed` 打包进二进制。
- 表 `schema_migrations(version, applied_at, checksum)`；启动时按顺序执行未执行的迁移，**每个迁移在一个事务里**；已经执行过的文件内容被修改（checksum 不一致）时拒绝启动。
- 只做"向前兼容"的变更：先加列（允许为空或有默认值），代码双写，再回填，最后才删除旧列。这样滚动升级时，新旧两个版本的节点可以同时运行。
- 命令：`im-server migrate up | status`；生产环境默认**不自动迁移**（`IM_AUTO_MIGRATE=0`），由发布流程显式执行。

### 3.2 存储契约测试（替换 G4）

- `store/storetest` 包：一套测试函数，参数是 `func() store.Store`，覆盖每个方法的语义（seq 连续、去重、翻页边界、事务原子性、并发分配 seq 不重复）。
- SQLite 实现在每次 `go test` 都跑；Postgres 实现在 CI 和本地 `IM_TEST_PG_DSN` 存在时跑。
- **新的存储实现必须通过同一套契约测试才能上线**。这是"方便迁移"的核心保证。

### 3.3 目标生产数据库

推荐 **PostgreSQL**（见决策 A1）。理由：事务和 `RETURNING`、`ON CONFLICT` 语义与现在的 SQLite 代码一致，改动最小；原生声明式分区，可以按时间分区消息表，旧分区直接归档或删除；有成熟的 PITR（时间点恢复）备份方案；开源许可宽松。

SQL 编写约束（现在就遵守，换库时几乎不用改）：
- 只用 SQLite 和 Postgres 都支持的语法：`INSERT … ON CONFLICT … DO UPDATE`、`RETURNING`、标准 `LIMIT`。
- 时间统一用 `BIGINT` 毫秒；不用数据库的时间函数和自增主键（主键用 UUIDv7 或业务 ID）。
- 占位符由各实现自己处理，不在共享代码里拼 SQL。
- 不使用触发器、存储过程。

### 3.4 备份与恢复（替换 G5）

| 模式 | 方案 | RPO（最多丢多少） | RTO（多久恢复） |
|---|---|---|---|
| 单机 SQLite（一期） | 在线备份：`VACUUM INTO` 生成一致性快照，由 `im-server backup` 触发（服务运行中也可执行；不提供 HTTP 接口，见第 7 节）；定时任务每小时一次，保留 48 份；备份文件**加密**后上传对象存储。可选 Litestream 持续复制 WAL 到 S3 / MinIO，RPO 降到秒级 | 1 小时（Litestream：约 1 秒） | 分钟级 |
| Postgres（集群） | 托管服务或 `pgBackRest`：每天全量 + WAL 持续归档，支持恢复到任意时间点；跨可用区副本 | 秒级 | 30 分钟以内 |

**恢复演练写成自动化测试**：备份 → 删库 → 恢复 → 校验每个会话的消息条数和最大 seq 与备份前一致。没有演练过的备份不算备份。

### 3.5 数据迁移工具（SQLite → Postgres）

`im-server export` / `import`：按表流式导出 JSON Lines，导入到新库；导入后逐会话校验 `count(*)` 和 `max(seq)`，以及抽样比对消息内容的哈希。切换步骤：停写（或只读模式）→ 导出 → 导入 → 校验 → 改配置 → 启动。

### 3.6 扩展路径

1. 单机 SQLite（一期，万级用户）
2. Postgres 单主 + 只读副本（`sync` 历史查询走副本，读写分离由 Store 实现内部处理）
3. 消息表按月分区（便于设置保留期和冷数据归档）
4. 按 `conv_id` 哈希分片（Citus 或应用层路由）。所有消息查询都已经带 `conv_id`，不需要改查询。

## 4. 安全（第一优先级）

### 4.1 威胁模型（STRIDE 摘要）

| 威胁 | 场景 | 对策 |
|---|---|---|
| 冒充（S） | 窃取 token 冒充用户；窃取管理密钥签发任意用户的 token | S1、S5、S7、S8 |
| 篡改（T） | 中间人修改消息 | S2（全链路 TLS） |
| 抵赖（R） | 管理员否认执行过强制下线、导出数据 | S8 审计日志 |
| 信息泄露（I） | token 进入日志；越权读取别人的会话；备份泄露 | S1、S9、S10；权限检查（已有：4032 / 4033） |
| 拒绝服务（D） | 大量连接、超大帧、刷消息 | S6、S7、限流（已有） |
| 提权（E） | 普通用户调用管理接口；测试模式在生产开启 | S4、S8 |

### 4.2 安全需求清单

**P0：上线前必须完成（建议本次调整就完成大部分）**

| # | 需求 | 说明 |
|---|---|---|
| S1 | **token 不进 URL**（G7） | WS 握手只带 `platform`；连接建立后**第一帧必须是 `auth`**（携带 token），5 秒内没有收到就以 4401 关闭（可以重连）。收到 `auth` 之前不处理任何其他命令。见决策 A2。协议、PRD、前端任务需要同步修改 |
| S2 | 全链路 TLS | 生产环境只允许 `wss://` / `https://`；TLS 可以在负载均衡终止，但服务端要求 `X-Forwarded-Proto=https`，并且只信任配置好的代理 IP（`IM_TRUSTED_PROXIES`）；HSTS |
| S3 | Origin 白名单（G8） | `IM_ALLOWED_ORIGINS`；没有配置时只允许本机来源。原生 App 没有 Origin 头，按平台标识放行 |
| S4 | 生产启动保护（G8） | `IM_ENV=production` 时：没有配置密钥、密钥长度小于 32 字节、密钥等于开发默认值、开启了测试模式或演示登录，**都拒绝启动**。非 production 才允许使用开发默认密钥 |
| S5 | JWT 密钥轮换 | token 头部带 `kid`；服务端可以同时配置多把验证密钥（新密钥签发，旧密钥只验证），轮换期间不需要让用户重新登录。仍然固定算法（已有） |
| S6 | 资源上限 | 已有：单帧 64KB、请求体 1MB、`ReadHeaderTimeout`。补充：`ReadTimeout` / `WriteTimeout` / `IdleTimeout`（HTTP）；单用户最多 10 个连接（超出后踢掉最早的连接，原因 `tooManyConnections`）；握手阶段的 auth 超时 |
| S7 | 握手限流（G10） | 按 IP 的令牌桶限制新建连接和鉴权失败次数；鉴权连续失败时临时封禁该 IP |
| S9 | 日志脱敏 | 规定：日志中禁止出现 token、管理密钥、消息正文；用测试扫描日志输出来保证（发送带特征串的消息和 token，断言日志里不出现） |
| S11 | 依赖与代码扫描（G11） | CI 跑 `govulncheck`、`go vet`、`gosec`、`go mod verify`；已知高危漏洞阻断合并 |
| S12 | 客户端约定 | 消息正文只按纯文本渲染（禁止 `innerHTML` / 富文本解析），防 XSS；H5 token 存 sessionStorage（D4 已定）；SDK 日志不打印 token |

**P1：集群化 / 正式运营阶段**

| # | 需求 | 说明 |
|---|---|---|
| S8 | 管理接口加固（G9） | 每个业务方一把独立密钥，并区分权限（签 token、导入用户、强制下线、建群）；请求签名 `HMAC(密钥, 方法 + 路径 + 时间戳 + nonce + body 哈希)`，时间戳超过 5 分钟或 nonce 重复即拒绝（防重放）；可选来源 IP 白名单 / mTLS；**审计日志**：谁在什么时间、从哪个 IP 调用了什么接口，结果如何，单独存放且只能追加 |
| S10 | 数据加密 | 磁盘加密由基础设施负责；**备份文件必须加密**（age 或 KMS 信封加密）；消息正文字段级加密（信封加密、按会话分配数据密钥）作为可选项 |
| S13 | 隐私与合规 | 消息保留期可配置（到期自动删除）；用户注销时删除或匿名化其数据；数据导出接口；符合《个人信息保护法》的最小必要原则 |
| S14 | 内容安全 | 敏感词 / 审核回调（Webhook），由业务方决定拦截还是放行（对齐腾讯 IM 的"发消息前回调"） |
| S15 | 安全测试 | 每个阶段的 e2e 增加安全用例（`TC-SEC`）；上线前做一次渗透测试 |

**明确不做：端到端加密（E2EE）。** 原因：它和服务端的离线同步、多端历史漫游、内容审核（S14）、业务方推送都冲突。体育类 App 的聊天室和站内推送也不需要。把它记录为一期不做的决定，而不是遗漏。

## 5. 决策（已确认）

| # | 问题 | 建议 | 备选 |
|---|---|---|---|
| A1 | 生产环境数据库 | **PostgreSQL** | MySQL 8（如果公司运维只支持 MySQL，也可以：只需新增一个 Store 实现并通过契约测试，代价是 `RETURNING` 等语法需要改写） |
| A2 | WS 鉴权方式（S1） | **连接后第一帧 `auth`** | ① `Sec-WebSocket-Protocol` 头携带 token（不进 URL，但部分代理会记录这个头）；② 先用 HTTP 换一次性短期票据（30 秒内有效、只能用一次）再放进 URL |
| A3 | 排期 | **新增 B2.5「架构与安全基座」，排在 B3 之前**；Postgres、NATS、Redis 的集群实现放在新的 B6 | 先完成 B3、B4，再统一做基座（缺点：B3 的群成员缓存要返工） |
| A4 | 集群依赖 | NATS（投递总线）+ Redis（在线路由、限流） | 只用 Redis（Pub/Sub + 数据结构），少一个组件，但 Pub/Sub 不保证送达（对正确性没有影响，见 2.2 约束 4） |
