# 自主工作规则

> Frank 的要求（2026-11-02）："一步一步来，先做好核心业务，并且分工……做好定时任务，每天给我上一天的工作汇报和当天的计划安排，需要我授权和确认的内容；自己工作。"
>
> 这份文件是 AI 自主推进时的行为准则。定时任务每次都是全新会话，**开始工作前必须先读这份文件、[工作队列](QUEUE.md) 和 [待授权清单](../reports/PENDING.md)**。

## 1. 每天的节奏

| 时间 | 定时任务 | 做什么 |
|---|---|---|
| 每天 09:00 | `im-daily-report` 日报 | 汇总上一天的提交和完成项；按工作队列列出当天计划；列出需要 Frank 授权 / 确认的事项。写入 `docs/reports/daily/YYYY-MM-DD.md` 并推送 |
| 每天 09:30、14:30 | `im-autodev` 自主开发 | 从工作队列取下一项，按流程完成，提交推送；遇到需要授权的事项记入待授权清单，然后跳到下一个不受阻的项 |

定时任务只在 Claude 桌面应用打开时运行；应用关闭期间错过的任务会在下次打开时补跑。

## 2. 可以自己做（不用问）

- 在本仓库内写代码、测试、文档；按流程产出 PRD 草稿、评审记录、任务单、测试用例。
- 运行测试、压测、本地服务。
- 每完成一项就 `git commit` 并推送到 `leetonny001/im-mvp` 的 `main`（Frank 已要求代码提交到 GitHub）；推送后确认 CI 通过，不通过就修。
- 用独立子代理做评审、写测试用例（避免"自己审自己"）。
- 安装项目内的依赖（`go get`、`pnpm add`），限于主流、维护良好的开源库；在提交说明里写明理由。

## 3. 必须等 Frank 授权或拍板（记入待授权清单，不自己做）

| 类别 | 例子 |
|---|---|
| 产品决策 | PRD 评审结论（"评审通过、冻结 v1.0"）、需求取舍、评审里标为"需拍板"的问题。**评审完成后停在这里**，Frank 确认前不进入需求分发和开发 |
| 账号与凭证 | 任何需要登录、令牌、密钥、权限范围变更的操作（如 `gh auth refresh`） |
| 系统级改动 | 用 `brew` 等安装系统软件（Rust、Docker、Android SDK 组件等）、修改系统或全局配置 |
| 对外 / 不可逆 | 改 GitHub 仓库设置、公开仓库、发布版本、删除远端分支或数据、强推（`--force`）、改写已推送的历史 |
| 花钱 | 任何付费服务、云资源 |
| 范围变化 | 偏离工作队列的大改动、推翻已拍板的决定 |

遇到这些情况：写进 [待授权清单](../reports/PENDING.md)（写清楚要做什么、为什么、不做的影响、建议），然后继续做队列里**不受阻**的下一项。

## 4. 质量底线（每一项都要满足才算完成）

1. 遵守研发流程：新的需求范围必须先有 PRD → 评审 → 分发 → 测试用例；`python3 tools/trace.py --check` 通过（每条验收标准都有任务和用例）。
2. 服务端：`gofmt`、`go vet`、`go test -race ./...` 全过；gosec 中危及以上为 0。
3. 新功能要有对应的测试；关键逻辑做一次变异测试（故意改坏，确认测试会失败，再恢复）。
4. 更新 `docs/tasks/*.md` 的进度表；在 `docs/PLAN.md` 第 9 节"演示记录"补一行（分享会素材，如实记录 AI 出错和被纠正的地方）。
5. 不降低安全基线（[ARCH-v1](../arch/ARCH-v1.md) 第 4 节）；不为了让测试通过而放宽服务端校验。

## 5. 开工前检查

1. `git status` 必须干净，`git pull --ff-only` 同步远端。如果有不是自己留下的未提交改动（可能是 Frank 或其他会话在改），**不要动它们**，记入待授权清单后结束本次运行。
2. 如果队列里当前项已经被标为"进行中"超过一天，先检查是否有残留改动，再决定继续还是重来。
3. 每次运行结束前：工作区干净（已提交或已回退），队列状态已更新。
