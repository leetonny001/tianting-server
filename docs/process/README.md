# 研发流程与分工

> 一步一步来：每个阶段有明确的产出和"过关标准"，过关后才进入下一阶段。
> 每个阶段由 AI 扮演对应角色产出，**你（Frank）是最终拍板人**。

## 1. 角色

| 角色 | 职责 | 产出 |
|---|---|---|
| 产品（PM） | 梳理业务、定义需求和验收标准、排优先级 | PRD（需求文档） |
| 评审人 | 从后端、前端、测试三个视角挑问题：遗漏、歧义、不可测、不可实现 | 评审记录 + 结论 |
| 后端 | 接口与协议设计、服务端实现、单测和 e2e | 后端任务单、代码、接口文档 |
| 前端 | 页面与交互、SDK 接入、各端实现（先做 H5） | 前端任务单、代码 |
| 测试（QA） | 按功能点写测试用例、执行、提缺陷 | 测试用例、测试报告、缺陷单 |
| 拍板人（你） | 每个阶段的放行决定、需求取舍 | — |

评审和测试由**独立的 AI 子代理**执行，不复用写需求或写代码的上下文，避免"自己审自己"。

## 2. 流程

```
① 产品规划 ──▶ ② 需求评审 ──▶ ③ 需求分发 ──┬─▶ ④a 后端开发 ──┐
   PRD v0.x      评审记录        任务单       ├─▶ ④b 前端开发 ──┼─▶ ⑤ 测试执行 ──▶ ⑥ 验收发布
                  ↓ 不通过                    └─▶ ④c 测试用例 ──┘     报告/缺陷
                回到 ① 修改
```

| 阶段 | 输入 | 产出 | 过关标准 |
|---|---|---|---|
| ① 产品规划 | 业务目标、现有腾讯 IM 用法 | `docs/prd/` 下的 PRD | 每个功能点都有编号、业务规则、异常场景、可验证的验收标准 |
| ② 需求评审 | PRD | `docs/review/` 下的评审记录 | 所有"阻塞"级问题关闭；你确认通过；PRD 升为 v1.0 并冻结 |
| ③ 需求分发 | PRD v1.0 | `docs/tasks/backend.md`、`frontend.md`；`docs/testcases/` | 每条验收标准都能追溯到后端任务、前端任务和测试用例 |
| ④ 开发 | 任务单 | 代码 + 自测 | 后端 e2e 全过；前端页面可用 |
| ⑤ 测试 | 测试用例 + 可运行版本 | 测试报告、缺陷单 | P0 用例 100% 通过，无未关闭的严重缺陷 |
| ⑥ 验收 | 测试报告 | 你的验收结论 | 你确认 |

需求冻结后要改，走**变更**：PRD 升小版本（v1.1），在文末的变更记录里写明原因，并同步更新任务单和测试用例。

## 3. 编号与追溯

| 类型 | 格式 | 例子 |
|---|---|---|
| 功能点 | `F-模块-序号` | `F-MSG-01` 单聊发送文本 |
| 验收标准 | `AC-功能点-序号` | `AC-MSG-01-3` |
| 后端任务 | `BE-序号` | `BE-012` |
| 前端任务 | `FE-序号` | `FE-007` |
| 测试用例 | `TC-功能点-序号` | `TC-MSG-01-05` |
| 缺陷 | `BUG-序号` | `BUG-003` |

追溯矩阵放在 `docs/testcases/traceability.md`：每行一条 AC，后面跟着对应的 BE / FE / TC 编号。哪一栏空着，说明有遗漏。

## 4. 目录

```
docs/
├── PLAN.md            整体技术方案与里程碑
├── process/           本流程说明
├── prd/               需求文档（按版本）

```

## 5. 优先级与严重程度

| 需求优先级 | 含义 |
|---|---|
| P0 | 没有它产品不能用，本期必须做 |
| P1 | 重要，本期尽量做 |
| P2 | 以后再说 |

| 评审问题 / 缺陷级别 | 含义 |
|---|---|
| 阻塞 | 不解决就无法开发或无法上线 |
| 严重 | 功能错误或体验明显受损 |
| 一般 | 有影响但有替代方案 |
| 建议 | 优化项 |
